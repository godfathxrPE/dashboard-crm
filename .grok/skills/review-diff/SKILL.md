# Cold Review (dashboard-crm)

Независимая проверка **кода** перед мержем. Существует ровно потому, что гейт
проверяет «дифф = план», а ошибку самого плана он не увидит: тест по спецификации
не ловит дефект спецификации.

Ты — не второй гейт. Ты — тот, кто впервые видит этот код и спрашивает:
«он правда делает то, что заявлено, и что он ломает?»

## Железное правило: без плана

**Не читать ни при каких условиях:**

| Путь | Почему |
|------|--------|
| `_analysis/sprint-*.md`, `_analysis/fix-*.md`, `_analysis/handoff-*.md` | Задание — это и есть план, чью ошибку ты ищешь |
| `_analysis/review-*.md`, `_analysis/cold-review-*.md` | Чужой вывод анкорит |
| `crm-architect/references/journal.md` | Хроника рассуждений прошлых спринтов |
| Тело PR, commit message сверх заголовка | Пересказ намерения, не доказательство |

Если во входном файле оказался кусок спринт-задания — игнорируй его и скажи об этом
в шапке вывода.

**Читать можно и нужно:** сам дифф, рабочее дерево репозитория (grep/read вокруг
изменённых строк, вызывающий код, соседние политики и миграции), `docs/schema.md`.

## Вход

```
.grok/cold-review/cold-<branch>.md      ← вход, локальный, вне git
```

Собирает `.grok/skills/review-diff/scripts/cold-review.sh prepare`. Две секции:

- `## ACCEPTANCE` — что должно получиться, **в терминах наблюдаемого поведения**,
  5–10 строк, написано человеком, без деталей реализации.
- `## DIFF` — `git diff main...HEAD` без lock-файлов и сгенерированных типов,
  плюс `--stat` по всем файлам (там видно, менялись ли типы).

## Выход

```
_analysis/cold-review-<branch>.md
```

## Что ищем — по убыванию ценности

1. **Дефект поведения** — код делает не то, что описано в ACCEPTANCE. Самое дорогое:
   именно это гейт пропускает системно.
2. **Регресс** — изменение ломает работающий рядом сценарий. Ищи вызывающих
   (`grep` по имени функции/хука), а не только изменённые строки.
3. **Дыра доступа** — RLS-политика шире, чем заявлено; RPC доступна роли, которой
   не должна; UI-гейт без серверного.
4. **Гонки и атомарность** — два запроса там, где нужна транзакция; оптимистичное
   обновление без отката; повторный вызов даёт второй эффект.
5. **Edge case** — пусто, ноль, `null`, граница суток/DST, первый запуск, отказ сети.

## Что НЕ находка — стоп-лист

Инварианты проекта. Не предлагать, не считать находками, не упоминать в выводе:

- Hard delete + CASCADE. Soft delete / `deleted_at` в проекте нет и не будет.
- `pipelines` / `pipeline_stages` — глобальные словари, не org-scoped.
- `SECURITY DEFINER` c `EXECUTE` у `authenticated` на RPC проекта — норма, guard
  внутри функции.
- Миграции не применяются из кода: в PR лежит только `.sql`-файл.
- `src/types/supabase.gen.ts`, `src/types/database.ts` — генерируются. Не предлагать
  правку типов руками.
- `window.confirm` / `alert` / `prompt` отсутствуют намеренно; подтверждение —
  `InlineConfirm`.
- CSS: только переменные, хардкод-цветов нет. Единицы rem/em/clamp.
- Эмодзи в UI нет — иконки Lucide.
- Отсутствие тестов на разметку и стили.
- Стилистика: имена, порядок импортов, «можно короче», «вынести в константу».
- Смена стека, замена библиотеки, новая зависимость.

## Порядок работы: сначала находка, потом фильтр

**Не читать `learnings.md` до анализа** — свежий взгляд дороже, чем сэкономленная
минута. Сформулировал находку — только тогда сверься с
`crm-architect/references/learnings.md` и разделом «Что уже починено» в `CLAUDE.md`:

| Что нашёл в памяти | Что делать |
|--------------------|------------|
| Описано как осознанное решение | Отбросить молча |
| Описано как грабля, и код в неё наступил | Повысить severity, сослаться на строку памяти |
| Не описано | Оставить как есть |

## Формат находки

Каждый пункт — целиком, без пропусков:

````
### F1 · 🔴 · src/lib/hooks/use-deals.ts:142

**Что:** одно предложение — что именно неверно.

**Цитата:**
```diff
<3–8 строк из диффа, дословно>
```

**Отказ:** <конкретный вход или состояние> → <неверный результат>.

**Проверка:** <команда, SQL-запрос или шаг в UI, которым это подтверждается за минуту>
````

Severity: 🔴 блокер · 🟡 важное · ⚪ на подумать.

Жёсткие требования:

- **Нет воспроизводимого «Отказа» — нет находки.** «Может привести к проблемам»,
  «потенциально небезопасно», «стоит рассмотреть» — не отказ. Выброси такой пункт.
- **Цитата — дословно из диффа.** Не пересказ, не реконструкция.
- **Лимит ≤ 8 находок.** Больше — значит фильтр не отработал: оставь 8 самых дорогих
  и напиши, сколько отбросил.

## Формат документа

Пиши по-русски.

```markdown
# Cold review: <branch>

**Дата:** YYYY-MM-DD
**Ревьюер:** Grok (cold — без спринт-файла)
**Дифф:** `main...<branch>`, N файлов, +A/-B строк
**Acceptance:** <одна строка — как ты понял задачу из ACCEPTANCE>

---

## Вердикт

| Аспект | Оценка |
|--------|--------|
| Поведение соответствует acceptance | ✅ / 🟡 / ❌ |
| Регрессы | … |
| Доступ и RLS | … |
| Гонки и атомарность | … |
| Edge cases | … |

**Оценка: NN/100 (MERGE | FIX | REJECT).** <одна строка>

---

## Находки

### F1 · … 

---

## Что проверил и счёл верным

- …

---

## Чего не смог проверить

- <что требует прогона, живой БД или контекста, которого в диффе нет>
```

Шкала:

| Балл | Значение |
|------|----------|
| **≥ 85** | **MERGE** — можно мержить (🟡/⚪ допустимы) |
| **70–84** | **FIX** — правки обязательны, потом повторный прогон |
| **< 70** | **REJECT** — переработка |

Открытый 🔴 → максимум 84.

## «Находок нет» — валидный ответ

Если дифф чистый — так и напиши, с оценкой ≥ 85 и заполненной секцией
«Что проверил и счёл верным». Выдуманная находка дороже пропущенной: она тратит
час на разбор и подрывает доверие ко всем остальным.

Секция «Чего не смог проверить» — обязательна и честна. Пустой она не бывает:
у тебя нет живой БД и прогона.

## Headless CLI mode

При вызове из `.grok/skills/review-diff/scripts/cold-review.sh` Grok работает в single-turn stdout-режиме и
**не пишет файлы инструментами**:

- Печатай **только** готовый markdown в stdout.
- Первая строка — `# Cold review: <branch>`.
- Ни преамбулы, ни постскриптума, ни общего code fence вокруг документа.

Скрипт сам сохранит stdout в `_analysis/cold-review-<branch>.md`.

## Правила

- **Read-only** на `src/`, `supabase/`, `tests/`. Ничего не править, не коммитить.
- Разведка в репозитории приветствуется: `grep` вызывающих, чтение соседних политик,
  сверка с `docs/schema.md`.
- Ветку брать из входного файла, не из `git branch` — сессия может быть на другой.
- Если дифф пустой или файл входа не содержит `## DIFF` — сказать об этом одной
  строкой и выйти, ничего не выдумывая.
