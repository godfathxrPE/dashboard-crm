# worktree-isolation

Адаптация `using-git-worktrees` (obra/superpowers, MIT) под dashboard-crm.

**Принцип:** сначала обнаружить существующую изоляцию, потом использовать нативный
инструмент, и только потом — руками через git. Не воевать с харнессом.

**Объявить в начале:** «Использую worktree-isolation для изолированного пространства.»

## Шаг 0. Обнаружить существующую изоляцию

До создания чего-либо — проверить, не находимся ли мы уже в изолированном дереве.

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
git rev-parse --show-superproject-working-tree 2>/dev/null   # непусто = submodule
```

`GIT_DIR != GIT_COMMON` истинно и внутри submodule, поэтому третья команда
обязательна.

- **Разные, и не submodule** → мы уже в linked worktree. Второй не создавать,
  сразу Шаг 2. Отчитаться: путь + ветка (или «detached HEAD, ветку заводить
  на финише»). **Сверить имя папки с веткой** (`basename "$PWD"` против `$BRANCH`):
  расходятся — папка переиспользована под чужую ветку, путь врёт про содержимое,
  см. правило в Шаге 1b.
- **Совпадают или submodule** → обычный чекаут, идём дальше.

## Шаг 0.4. Код или документы — worktree только под код

Worktree заводится под ветку **с кодом**. Документные ветки — STATUS, `learnings.md`,
`journal.md`, файлы `_analysis/` — ведутся в основном чекауте.

Изолировать в них нечего: параллельной работы, от которой worktree защищает, у
документной ветки не бывает. Цена при этом реальная — worktree держит **вторую копию
`_analysis/`**, и она расходится с основной **молча**: ни `git status`, ни `tsc`, ни
lint расхождения двух копий не видят.

06.09 это стоило двух вещей разом:

- **спринты закоммичены в редакции ДО ревью** — правки жили в основной копии, worktree
  про них не знал, и в Claude Code уехали бы блокеры, снятые часом раньше;
- **пакет скилла собрался от вчерашнего дня при ЗЕЛЁНОМ `skill-verify`** — раскатка из
  worktree обновляла копию рядом с собой, а в основном чекауте пакет остался прежним
  (разбор — PR #61).

Признак документной ветки: в диффе только `.md` / `.html`, каталога `src/` нет.
Сомнительный случай (код + документы одним спринтом) — это ветка с кодом, worktree нужен.

Цикл документной ветки (ветка → коммит → пуш → PR → авто-мерж → возврат) автоматизирован
`scripts/docs-pr.sh` — запускать из основного чекаута, не отсюда.

## Шаг 0.5. Согласие

Предпочтение по worktree уже заявлено в инструкциях? Действовать по нему молча.
Не заявлено — спросить один раз:

> «Завести изолированный worktree? Это защитит текущую ветку от правок.»

Отказ — работать на месте, перейти к Шагу 2. Не переспрашивать.

## Шаг 1. Создать пространство

### 1a. Нативный инструмент — приоритет

Если у харнесса есть свой механизм (`EnterWorktree`, `/worktree`, флаг
`--worktree`) — использовать его и перейти к Шагу 2. Нативный инструмент сам
управляет размещением, веткой и уборкой; `git worktree add` в обход него создаёт
состояние, которого харнесс не видит. Это ошибка №1 в этом скилле.

### 1b. Fallback: git worktree

Только если нативного инструмента нет.

**Каталог**, в порядке приоритета:
1. Явно заданный в инструкциях
2. Существующий `.worktrees/` (приоритетнее) или `worktrees/`
3. По умолчанию `.worktrees/` в корне репозитория

**Обязательная проверка до создания:**
```bash
git check-ignore -q .worktrees || { echo ".worktrees" >> .gitignore; git add .gitignore; }
```
Неигнорируемый каталог worktree утащит в коммит всё дерево целиком.

**Создание:**
```bash
git worktree add ".worktrees/$BRANCH_NAME" -b "$BRANCH_NAME"
cd ".worktrees/$BRANCH_NAME"
```

Имя ветки — по конвенции проекта: `feat/`, `fix/`, `chore/`, `refactor/`.

**Имя папки обязано совпадать с веткой.** Не «похожее», не «по задаче» — то же самое
(слэш заменяется на `+`, если вложенный каталог нежелателен: `feat/deal-chz-1` →
`feat+deal-chz-1`). Папку **не переиспользовать** под следующую ветку: 06.09 папка
`feat+deal-zones-1a` прожила три ветки подряд, и на четвёртой уже никто не помнил, что
в ней лежит — путь врал про содержимое, а сессия считала себя изолированной под ветку,
которой в этой папке не было. Ветка закончена — worktree убрать и завести под следующую
новый по её имени; порядок уборки — Шаг 4.

**Отказ по правам (песочница):** сказать об этом прямо и работать на месте,
прогнав baseline здесь же. Не пытаться обойти.

## Шаг 2. Настройка

```bash
[ -f package.json ] && npm install
```

`.env` **копировать нельзя** — секреты не читаем и не размножаем. Но и без него
сборка не пройдёт: `.env.local` живёт только в основном чекауте, а первый
`npm run build` в новом worktree падает на пререндере страницы логина —

```
Error occurred prerendering page "/login"
@supabase/ssr: Your project's URL and API key are required to create a Supabase client!
```

Это **не** дефект кода и не регрессия ветки. Лечится симлинком — файл не читается
и не дублируется, worktree просто смотрит в оригинал:

```bash
ln -s <основной-чекаут>/.env.local .env.local
```

`.gitignore` (`.env*.local`) держит его вне коммита — проверить можно
`git check-ignore -v .env.local`. Если такого файла нет и в основном чекауте —
брать переменные из окружения Vercel/локального механизма, а не переносить файл.

## Шаг 3. Чистый baseline

**До первой правки** прогнать быстрые проверки:

```bash
npx tsc --noEmit
npm run lint
```

**`npm run build` в baseline не гонять.** Билд при живом `next dev` убивает
dev-сервер — грабля, стоившая времени. Сборка идёт последней, перед PR, а не
первой. Детали и полный набор проверок — `references/baseline-checks.md`.

**Baseline красный** → сообщить и спросить: чинить сначала или идти дальше.
Не начинать фичу поверх сломанного baseline: тогда любое последующее падение
неотличимо от унаследованного.

**Baseline зелёный** → отчёт:

```
Worktree: <полный путь>, ветка <name>
tsc --noEmit: чисто · lint: чисто
Готов к реализации <фича>
```

## Шаг 4. Уборка после мержа

Worktree живёт ровно столько, сколько открыт его PR. PR смержен — worktree убрать тем же
заходом, а не «когда-нибудь»:

```bash
git worktree list                        # если помечен locked — сначала снять замок
git worktree unlock  ".worktrees/$BRANCH_NAME"
git worktree remove --force ".worktrees/$BRANCH_NAME"
git worktree prune                       # подчистить записи о папках, снесённых руками
```

**Почему не «потом».** В брошенном worktree остаётся собранный `.next`: 07.09 в
`feat+deal-pulse-1` накопилось **1,1 ГБ**. Место — меньшая часть цены. Каталог worktree
лежит ВНУТРИ репозитория, поэтому `npm run lint` заходит в него и линтует сборочные
артефакты: **1261 «ошибка»** на файлах, к коду отношения не имеющих. Красный lint без
причины читается как «сломал я», и на его разбор уходит время — ровно то, ради экономии
которого уборку и откладывали.

**Ветка после мержа не нужна ни локально, ни на origin.** Сквош-мерж не делает коммит
ветки предком `main`, поэтому `git branch -d` откажется, а `git branch --merged` её не
покажет — удалять `-D`, предварительно убедившись, что содержимое влито (искать в логе
`main` сквош-коммит по subject; `--merged` и дифф против `main` для этого НЕ годятся:
общие файлы вроде STATUS.md ушли вперёд и дают ложное «не влита»).
Разово на репозитории: `gh repo edit --delete-branch-on-merge` — тогда удалённая ветка
уходит сама при мерже PR, и чистить придётся только локальные.
⚠️ Список веток к удалению строить ПОСЛЕ `git fetch --prune`: локальный кэш
remote-ветвей помнит уже удалённые, и `push --delete` падает на них
(07.09 — восемь из двадцати пяти).

## Шпаргалка

| Ситуация | Действие |
|---|---|
| Ветка документная (STATUS, learnings, journal, `_analysis/`) | Worktree НЕ заводить — основной чекаут (Шаг 0.4) |
| Уже в linked worktree | Не создавать, Шаг 2 |
| Имя папки worktree ≠ ветка | Папка переиспользована: не работать в ней, завести новую по имени ветки |
| PR смержен, worktree остался | Убрать тем же заходом (Шаг 4): `unlock` → `remove --force` → `prune` |
| Ветка смержена сквошем | `git branch -D` (у `-d` и `--merged` сквош-коммита нет); список для origin — после `fetch --prune` |
| Внутри submodule | Считать обычным репо |
| Есть нативный инструмент | Использовать его (1a) |
| Нет нативного | git worktree в `.worktrees/` (1b) |
| Есть и `.worktrees/`, и `worktrees/` | Побеждает `.worktrees/` |
| Каталог не в .gitignore | Добавить и закоммитить до создания |
| Отказ по правам | Работать на месте, сказать об этом |
| Baseline красный | Отчитаться и спросить |
| `build` падает на `/login` («@supabase/ssr: URL and API key are required») | Нет `.env.local` — симлинк на основной чекаут (Шаг 2), не дефект кода |

## Типовые самооправдания

| Отговорка | Реальность |
|---|---|
| «Очевидно, что я не в worktree» | Прогнать Шаг 0. Изоляция от харнесса и submodule обманывают на глаз |
| «`git worktree add` быстрее, чем искать нативный» | Нативный владеет размещением и уборкой. Обход = фантомное состояние |
| «Каталог наверняка игнорируется» | `git check-ignore`. Цена ошибки — всё дерево в коммите |
| «Пространство свежее, baseline подождёт» | Грязный baseline делает любое падение неоднозначным |
| «Прогоню build, заодно проверю» | Убьёт живой `next dev`. Build последним |
| «Ветка документная, но worktree уже есть — поработаю в нём» | Вторая копия `_analysis/` расходится молча: коммит уедет в редакции до ревью |
| «Папка называется иначе, но задача та же» | Так одна папка переживает три ветки, и на четвёртой её содержимое — загадка |
| «Worktree пустой, места не жалко» | Внутри собранный `.next`: 1,1 ГБ и 1261 ложная ошибка в `npm run lint` |
| «Ветку удалю потом, она же слита» | `--merged` сквош-ветку не показывает — «потом» превращается в 25 веток на origin |

## Источник и раскатка

Источник этого скилла — папка `worktree-isolation/` в репозитории dashboard-crm. Копии в
`~/.claude/skills/worktree-isolation/` (Claude Code) и в аккаунте Claude.ai (Cowork, гейт) —
производные: правки в них не переживают раскатку и не попадают в ревью.
Цикл: правка в репо → PR → мерж → `scripts/skill-deploy.sh worktree-isolation` → загрузить
`worktree-isolation.skill` в Claude.ai → Customize → Skills. Повод для правки — изменение
самого процесса (новое правило, фаза, линза), не итог спринта: состояние
проекта живёт в crm-architect, здесь его нет намеренно.
