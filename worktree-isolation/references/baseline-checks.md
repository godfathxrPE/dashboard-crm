# Baseline и порядок проверок

Цель baseline — сделать так, чтобы любое падение после начала работы
однозначно принадлежало вашим правкам.

## Порядок: от дешёвого к дорогому

| Этап | Команда | Когда |
|---|---|---|
| Типы | `npx tsc --noEmit` | baseline и перед каждым коммитом |
| Линт | `npm run lint` | baseline и перед коммитом |
| Типы БД | `scripts/gen-types.sh` | только после миграции |
| Смоки RLS | ролевые прогоны | после правки политик/функций |
| Сборка | `npm run build` | **последней**, перед PR |

## Почему build последним

`npm run build` при живом `next dev` убивает dev-сервер. Это не теория —
уже стоило времени. Правило: либо остановить dev, либо гнать build в самом
конце, когда dev уже не нужен.

## Реген типов

`src/types/supabase.gen.ts` и `src/types/database.ts` руками не правятся.
Реген через MCP не отдаёт блок `graphql_public`, который отдаёт CLI: в диф
придут ~28 ложных удалений. Сверять диф, а не принимать вслепую.

## Смоки RLS

Проверять под клиентом с JWT нужной роли, не под service_role — под ним
политики не применяются. Корректный отказ на SELECT — **пустая выборка**,
а не ошибка; на INSERT/UPDATE — `42501`.

Смоки на INSERT→UPDATE→DELETE гнать отдельными statement'ами: CTE не видит
собственный INSERT из-за snapshot транзакции, и UPDATE обработает 0 строк.

## Миграции

Из рабочей сессии миграции **не применяются**. Пишется файл
`supabase/migrations/0NN_name.sql` и коммитится; применяет гейт.
Номер следующей миграции берётся запросом к
`supabase_migrations.schema_migrations`, а не из имён файлов в папке:
в папке номера теряются, а 069–073 записаны в ledger без числового префикса.

## Что не входит в baseline

Advisors и производительность — это проверки гейта, не старта. На baseline
достаточно типов и линта: они дешёвые и ловят 90% унаследованной красноты.
