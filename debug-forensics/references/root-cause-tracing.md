# Обратная трассировка до источника

Баг проявляется глубоко в стеке: пустой список в таблице, `null` в поле, запись
ушла не в ту организацию. Инстинкт — починить там, где видно ошибку. Это симптом.

**Принцип: трассировать вызовы назад до исходного триггера и чинить в источнике.**

## Когда

- Ошибка возникает не на входе, а глубоко в исполнении
- Длинная цепочка вызовов или несколько слоёв (UI → хук → supabase-js → политика → триггер)
- Непонятно, откуда взялось некорректное значение
- Нужно понять, какой именно сценарий/смок вызывает проблему

## Процесс

**1. Наблюдаемый симптом.**
`Список проектов пуст, хотя в таблице 40 строк`

**2. Непосредственная причина.** Какой код прямо её порождает?
```ts
const { data } = await supabase.from('projects').select('id, name, stage_id')
```
Ошибки нет, `data = []`. Значит отфильтровала политика — RLS возвращает пустоту,
а не отказ. Это ключевая особенность: **пустой результат и отсутствие прав
выглядят одинаково**.

**3. Кто вызвал?** Проследить вверх:
```
useProjects() → ProjectsTable → страница → layout → провайдер сессии
```

**4. Какое значение передано?** Проверить каждое звено:
- какой `org_id` в JWT / что вернёт `current_org_id()` в этом контексте
- какая роль у пользователя в `organization_members`
- не `NULL` ли `current_org_id()` — в DEFINER-контексте это штатно возможно

**5. Исходный триггер.** Например: пользователь состоит в двух организациях,
активная не выставлена, `current_org_id()` вернул `NULL`, политика
`org_id = current_org_id()` отсекла всё. Root cause — в выборе активной
организации, а не в запросе и не в политике.

## Инструментирование, когда вручную не трассируется

**На стороне БД** — не гадать, а спросить:
```sql
select current_org_id() as org, current_org_role() as role, auth.uid() as uid;
select * from pg_policies where tablename = 'projects';
explain analyze select id from projects limit 1;   -- видно, как политика вошла в план
```

**На стороне клиента** — логировать до операции, а не после падения:
```ts
console.error('DEBUG projects fetch', {
  orgId: activeOrgId, userId: session?.user.id, stack: new Error().stack,
})
```

`console.error`, не логгер: логгер может быть подавлен в том окружении,
где воспроизводится баг.

## Защита в глубину — после того, как источник найден

Найденный источник чинится, но чинится не в одиночку. На каждом слое ставится
проверка, делающая баг невозможным:

1. UI/Zod — не отправлять запрос без активной организации
2. Хук — явная ошибка вместо тихого пустого результата
3. БД — `not null` там, где значение обязательно; `freeze_org_id()` на смену `org_id`
4. Наблюдаемость — лог с контекстом до опасной операции

Один слой ловит регресс; четыре делают его невозможным.

## Главное

```
Нашёл непосредственную причину
  → можно шагнуть на уровень выше? → шагай
  → это источник? → нет: шагай дальше
                    да:  чини здесь + поставь проверки на каждом слое
```

**Никогда не чинить только там, где видно ошибку.**
