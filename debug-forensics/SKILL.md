# debug-forensics

Адаптация `systematic-debugging` (obra/superpowers, MIT) под стек dashboard-crm.
Оригинал построен на обязательном TDD-цикле; здесь роль «падающего теста» играет
воспроизведение — SQL-смок, ролевой прогон под JWT или браузерный сценарий.

## Железное правило

```
НИ ОДНОГО ФИКСА ДО ЗАВЕРШЁННОЙ ФАЗЫ 1
```

Симптомный фикс — это провал, а не быстрая победа. Если Фаза 1 не закрыта,
предлагать правку нельзя, даже однострочную.

## Когда применять

Любая техническая проблема: падение смока, баг в проде, странное поведение
компонента, пустой список там, где данные есть, медленный запрос, красная сборка,
расхождение типов после регена.

**Особенно — когда соблазн угадать максимален:**
- «очевидно же, что дело в X»
- уже сделано 1–2 попытки фикса
- горит демо или гейт
- проблема кажется тривиальной

## Depth и формат отчёта

- **D1** — root cause найден за один проход Фазы 1, фикс локален (одна функция,
  одна политика, один хук). Формат: Диагноз → Патч → Почему → Verification Labels.
- **D2** — потребовалась Фаза 2 (сравнение с рабочим аналогом) или фикс задевает
  несколько слоёв. Формат: WHY → WHAT → HOW → Edge cases → Verification Labels.
- Три неудачных фикса переводят задачу в **D3**: это разговор про архитектуру,
  а не четвёртая попытка.

## Фаза 1. Root cause

**1. Прочитать ошибку целиком.** Не по диагонали. Код ошибки Postgres несёт
половину ответа: `42501` — RLS/ACL, `23503` — FK, `23505` — unique, `42809` —
попытка `pg_get_functiondef` на агрегате (см. грабли в CLAUDE.md), `PGRST116` —
`.single()` на нуле строк.

**2. Воспроизвести стабильно.** Каждый раз? Под какой ролью? На каком org?
Не воспроизводится — собирать данные, а не гадать.

**3. Проверить, что изменилось.** `git diff`, последние коммиты, последняя
применённая миграция (**запросом к `supabase_migrations.schema_migrations`,
не грепом по папке** — 069–073 записаны без числового префикса и грепом не
находятся), версия Edge-функции, редеплой Vercel.

**4. Собрать evidence на границах слоёв.** Стек многослойный, и «не работает»
почти никогда не означает «сломан тот слой, где видно ошибку». Границы:

```
UI (RHF/Zod) → TanStack Query → supabase-js → PostgREST
   → RLS policy → триггеры → функция → данные
```

Инструментирование до предложения гипотез — деталь в
`references/evidence-supabase.md`. Один прогон, который показывает, ГДЕ рвётся,
дороже трёх гипотез о том, ПОЧЕМУ.

**5. Проследить данные назад.** Ошибка глубоко в стеке — трассировать вверх до
исходного триггера, чинить в источнике. Техника: `references/root-cause-tracing.md`.

## Фаза 2. Анализ паттерна

1. **Найти рабочий аналог в репозитории.** Соседний хук `use-*.ts`, соседняя
   RLS-политика, соседняя миграция. В этом проекте почти любая сущность имеет
   работающего близнеца.
2. **Прочитать эталон целиком**, не по диагонали. Частичное понимание паттерна
   гарантирует баг.
3. **Выписать все различия**, включая те, что «не могут иметь значения».
   Порядок триггеров алфавитный; `( select current_org_role() )` против прямого
   вызова; `owner_id` против `user_id`; наличие `trg_aa_freeze_org_id`.
4. **Проверить зависимости**: гранты, `search_path`, initplan-обёртка, индексы
   под предикатом политики.

## Фаза 3. Гипотеза

1. **Одна гипотеза, сформулированная письменно**: «Причина — X, потому что Y».
2. **Минимальная проверка**: одна переменная за раз. Не чинить попутно.
3. **Подтвердилась → Фаза 4. Не подтвердилась → новая гипотеза, а не второй
   фикс поверх первого.**
4. Не понял — сказать «не понимаю X», а не изображать понимание.

## Фаза 4. Реализация

1. **Зафиксировать воспроизведение.** До фикса, не после. Чем именно:
   - БД: SQL-смок отдельными statement'ами. **Не одним CTE** — `with ins as
     (insert …), upd as (update … where id = (select id from ins))` даст 0 строк
     в UPDATE из-за snapshot транзакции.
   - RLS: прогон под клиентом с JWT нужной роли; корректный отказ — пустая
     выборка, а не ошибка.
   - UI: сценарий в браузерном смоке. Помнить, что `window.confirm` в проекте
     запрещён в том числе потому, что блокирует смоки.
2. **Один фикс, адресующий root cause.** Без «раз уж я здесь». Без попутного
   рефакторинга.
3. **Проверить**: воспроизведение больше не воспроизводится; соседние смоки
   зелёные; advisors не дал новых WARN; типы регенерированы, если менялась схема.
4. **Отчёт назвать отчётом** — не планом с распределением ответственности.

## Правило трёх попыток

Фикс не сработал → вернуться в Фазу 1 с новой информацией.
**Три неудачных фикса = проблема в архитектуре, а не в гипотезе.**

Признаки: каждый фикс вскрывает новую связанность в другом месте; фикс требует
«массового рефакторинга»; починка одного ломает другое.

Тогда — стоп и разговор с Олегом: паттерн вообще жизнеспособен, или его тянут
по инерции? Четвёртая попытка без этого разговора запрещена.

## Красные флаги — немедленно назад в Фазу 1

- «Быстрый фикс сейчас, разберусь потом»
- «Давай поменяем X и посмотрим»
- «Скорее всего дело в X, чиню»
- «Вот основные проблемы: …» — список правок без единого следа расследования
- «Пропущу смок, проверю руками»
- Предложение решения раньше, чем прослежен поток данных
- «Ещё одна попытка» при двух уже сделанных

## Проектные ловушки, где симптомный фикс особенно вероятен

| Симптом | Что кажется | Что на самом деле |
|---|---|---|
| «Миграция не применена» (грепом не нашлась) | нужно написать миграцию заново | 069–073 в ledger без префикса; сверять ledger целиком. Ложный вывод делался дважды |
| Клиент пишет `status`, а в БД другое | баг апдейта | `trg_sync_deal_stage_fields` и `trg_sync_project_stage` пересекаются, второй выигрывает по алфавиту. `status`/`probability`/`actual_close_date` из клиента не писать никогда |
| Права «вроде есть», а отказ | политика | `relacl` — массив `aclitem`; `like` по склейке матчит права соседней роли. Разбирать `unnest` поэлементно |
| `MAINTAIN` не виден в грантах | привилегии не выданы | `information_schema.role_table_grants` нестандартную привилегию не показывает вовсе |
| Правило автоматизации сработало дважды | гонка | ключ идемпотентности из `timestamptz` через `::text`: session TimeZone разводит cron-прогон (UTC) и ручной (MSK) |
| Off-by-one на границе суток | часовой пояс в UI | ключ дня — MSK (`mskDateKey`), бакеты Ганта — UTC-полдень |
| Кнопка «не нажимается» | обработчик | disabled сделан серым цветом, а не настоящим `disabled` — клик молча уходит в никуда |
| Живое тело DEFINER-функции короче файла миграции | миграция применилась частично | Postgres не хранит комментарии в `prosrc`. Сверять по логике |

## Когда root cause честно нет

Бывает: внешний сервис, гонка вне нашего кода, окружение. Тогда — задокументировать,
что именно проверено, поставить обработку (retry/timeout/внятная ошибка) и логирование.
**Но в 95% случаев «нет root cause» означает незавершённое расследование.**

## Verification Labels

Отчёт по багу закрывается блоком:

```
Type Safety:            [PASS | WARNING | NOT_VERIFIED]
RLS Coverage:           [PASS | WARNING | NOT_VERIFIED]
Backward Compatibility: [PASS | WARNING | NOT_VERIFIED]
Runtime Tested:         [PASS только если реально прогнано; иначе NOT_VERIFIED]
```

`Runtime Tested: PASS` без фактического прогона воспроизведения — ложь, а не оптимизм.
