## WHY

Longest path отвечает на вопрос «какая цепочка самая длинная», а планировщику нужен другой:
**«что случится с финишем проекта, если эта задача поедет на день»**. Ответ даёт total float.

- MS Project / Primavera: `Total Slack` / `Total Float`, критическая работа = float ≤ 0.
- Bryntum Gantt: `criticalPaths` считается ровно так же — через прямой и обратный проход.
- Smartsheet: «Critical Path» = задачи с нулевым запасом, а не самая длинная цепочка.

Разница практическая, не академическая: longest path подсвечивает **одну** цепочку, тогда как
критических цепочек может быть несколько, а параллельная ветка с нулевым запасом сегодня у тебя
не подсвечена вообще. Плюс float — это то, что реально показывают заказчику: «здесь запас 4 дня,
здесь ноль».

## КЛЮЧЕВОЕ РЕШЕНИЕ: CPM с ограничением «не раньше собственной даты»

Классический CPM выводит даты из длительностей и связей. У нас даты **пользовательские** — это
не баг, а модель проекта (человек ставит их руками, Гант их не пересчитывает без спроса).
Поэтому берём вариант, который в MS Project называется `Start No Earlier Than`:

```
ES(i) = max( own_start(i), max над FS-предшественниками p: shiftDay(end(p), lag) )
EF(i) = shiftDay(ES(i), dur(i) - 1)
PF    = max EF по всем узлам                     // финиш проекта
LF(i) = min( PF-для-стоков , min над последователями s: shiftDay(LS(s), -lag) )
LS(i) = shiftDay(LF(i), -(dur(i) - 1))
TF(i) = diffDaysKey(ES(i), LS(i))                // total float в календарных днях
критическая: TF(i) <= 0
```

Соответствие семантике 1a/1B сохранено: везде тот же `shiftDateKeyByBuckets(..., 'day', ...)`
и то же «lag=0 ⇒ старт в день финиша предшественника легален». Три места, где считается FS
(warn, каскад, CPM), обязаны давать один и тот же `earliest` — при расхождении подсветка начнёт
спорить с предупреждениями.

**Почему TF может быть отрицательным:** если пользователь руками поставил старт последователя
раньше `earliest` (то самое FS-нарушение из 1a), обратный проход даёт `LS < ES`. Это не ошибка
расчёта — это ровно тот конфликт, который 1a показывает стрелкой. Отрицательный float трактуем
как критический и показываем в подсказке как «просрочка: N дн», не «запас: −N дн».

## ЗАДАЧА 1: `computeCpm` в `gantt-schedule.ts`

```ts
export interface CpmNode {
  es: string; ef: string; ls: string; lf: string;
  totalFloat: number;       // дни; < 0 = нарушение FS
  critical: boolean;        // totalFloat <= 0
}
export function computeCpm(
  nodes: ScheduleNode[],
  edges: ScheduleEdge[],
): { byId: Map<string, CpmNode>; projectFinish: string | null };
```

- `dur(i)` — та же формула, что `durDays` в компоненте: перенести её сюда как экспортируемую
  `durationDays(start, end)` и **удалить локальный дубль** в `GanttTimeline`.
- Только `dep_type === 'FS'` (как и каскад). Прочие типы игнорируются до появления их семантики.
- Топосорт переиспользуем из 1B. Узлы вне топопорядка (цикл-мусор) → `critical:false`,
  `totalFloat:0`, в `byId` присутствуют (компонент не должен получать `undefined`).
- Пустой граф → `{ byId: new Map(), projectFinish: null }`, никаких исключений.
- Сводные узлы участвуют как обычные (span = обёртка детей). **Долг:** если ребро повешено и на
  сводную, и на её ребёнка, длительность учитывается дважды и float занижается. В v1 не решаем,
  комментарий в коде обязателен.

- одиночный узел без рёбер → `TF = 0`, `projectFinish = его end`;

## ЗАДАЧА 3: `GanttTimeline` — замена алгоритма

- Удалить inline-DP блока `S-CRIT-PATH` и локальный `durDays`; вместо них
  `const cpm = useMemo(() => computeCpm(nodes, deps), [nodes, deps])` — где `nodes` собираются
  так же, как в 1B (плоский flatMap по свимлейнам).
- `criticalIds = new Set([...cpm.byId].filter(([,v]) => v.critical).map(([k]) => k))`.
- `critSig` строится по **отсортированному** списку id — сигнатура должна быть детерминированной,
  иначе эффект измерения рёбер зациклится (грабля S-CRIT-PATH, не наступать повторно).
- Подсветка рёбер (`EdgePath.critical`) — ребро критическое, если оба конца критические
  (как сейчас), логику отрисовки не трогаем.
- **Подсказка бара:** к существующему тултипу добавить строку
  `TF > 0 → «запас: N дн»`, `TF === 0 → «запаса нет»`, `TF < 0 → «просрочка: N дн»`.
  Цвет — только через CSS-переменные темы, никаких хардкод-хексов.
- Тумблер `showCritical` и его текущее поведение сохраняются как есть.

**Бейдж «Крит. путь: N дн» (GanttTimeline L964).** Сейчас читает `critical.totalDays` —
поле longest-path DP, которого в новой сигнатуре `computeCpm` нет (возвращается
`{ byId, projectFinish }`). Считать N как сумму длительностей критических задач НЕЛЬЗЯ:
при двух параллельных критических цепочках сумма удвоится, а горизонт проекта не изменится.

Правило: N — горизонт критического пути в календарных днях включительно,

```ts
const criticalDays =
  cpm.projectFinish && minES ? diffDaysKey(minES, cpm.projectFinish) + 1 : 0;
```

где `minES` — минимальный `ES` по критическим узлам (`cpm.byId`, `v.critical`).
Для одной цепочки число совпадает со старым `totalDays` — регресс базового кейса виден
в смоуке п.1. Для N параллельных цепочек одинаковой длины остаётся корректным.
Условие показа бейджа не меняется: `showCritical && criticalIds.size > 0`.
