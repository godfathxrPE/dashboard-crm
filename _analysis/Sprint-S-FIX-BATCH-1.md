## ЗАДАЧА 1 — контакты в модалке задачи: только связанные с компанией

`src/components/tasks/TaskModal.tsx:286`

```tsx
{(contacts ?? []).map((c) => <option key={c.id} value={c.id}>…</option>)}
```

Список не фильтруется вовсе — при выбранной компании «ЙУМИ» показываются все
89 контактов организации.

**Паттерн в проекте уже есть**, изобретать не нужно — `ProjectModal.tsx:166`:

```tsx
c.companies?.some((cc) => cc.company_id === selectedCompanyId)
```

Связь M:N через junction (`contact.companies[]`), не поле `company_id` на контакте.
Так же фильтруют `DealStakeholders.tsx:204` и `TodayView.tsx:144`.

Требования:

- Компания выбрана → только её контакты; компания не выбрана → все (поведение
  сегодняшнего дня для этого случая сохранить).
- ⚠️ **Смена компании при уже выбранном контакте**: если контакт не принадлежит
  новой компании — сбросить в «— не указан —», иначе в задаче останется контакт
  чужой компании и это не будет видно на экране. Отдельно проверить обратный
  порядок (сначала контакт, потом компания) — `deriveFromContact` в `CallModal`
  делает вывод компании из контакта, посмотреть, не нужно ли то же здесь.
- Если у компании нет контактов — пустой список с подписью, не молчаливый пустой
  `<select>`.

Тот же дефект проверить в `TaskQuickAdd.tsx` и `CallModal.tsx` — если фильтрация
там уже есть, вынести предикат в общий хелпер (`lib/forms/derive-links.ts` рядом
с `deriveFromContact`), чтобы третьей копии не появилось.

## ЗАДАЧА 2 — прозрачный confirm поверх модалки в тёмных темах

`src/components/shared/Modal.tsx:127`

```tsx
<div className="w-full max-w-xs rounded-xl border border-border bg-surface p-4 elevation-3 …">
```

**Причина найдена:** `bg-surface` в тёмных темах — полупрозрачный
(`--surface: rgba(255,255,255,0.07)` у frost, `rgba(60,140,100,0.07)` у tidal), и
панель подтверждения просвечивает на форму под собой: текст «Есть несохранённые
изменения» ложится поверх полей «Сделка», «Детали».

Сама модалка не виновата — `[data-modal]` уже получает solid `--popover` правилами
`.t-frost/.t-aurora/.t-tidal` (globals.css:1584-1586). Вложенный confirm под них
не попал, потому что красится утилитой, а не токеном.

**Фикс:** `bg-surface` → `bg-popover` (утилита есть в `tailwind.config.ts`,
`--popover` в каждой теме объявлен solid — он для этого и вводился в S-UI-POLISH-1).

⚠️ Это **четвёртый случай одного класса** за две сессии: токен, подобранный под
один контекст, применён в другом (`--danger` только в fuji, `KIND_META.fg` для
текста, `--border` на `--surface2`). Пройтись `grep`-ом по `bg-surface` внутри
элементов, лежащих ПОВЕРХ другого контента (поповеры, дропдауны, тултипы,
`Combobox`, `AssigneeSelect`, `ChatEmojiPicker`) — всё, что перекрывает контент,
обязано быть на `--popover`. Найденное чинить здесь же, список — в отчёт.

## ЗАДАЧИ 3 и 4 — строки плана живут как обычные задачи

### Что видит владелец

| Экран | Что показано |
|---|---|
| Гантт / доска «План» проекта | колонки этапов, в них WBS-строки `1.3`, `2.2`, `3.1`… — так и должно быть |
| Задачи → «Проекты» (176) | те же строки с меткой «Стратек — внедрение» |
| Задачи → **«Личное» (373)** | **те же названия без метки проекта, часть — по два раза** |

На скриншоте «Личное» видно дубли: «Складской учет», «Закупки», «Продажи,
Ценообразование, Скидки» встречаются дважды. Верной в этом списке владелец считает
только первую строку («Уточнить у Рената Кусаметова» — настоящая личная задача).

Подпись «WBS-задачи проектов скрыты» в UI есть (`TasksView.tsx:290`), но она
управляет **источником** (`activeSources.includes('project')`), а не признаком
WBS. Задачи без `project_id` она не отсекает по определению — поэтому личный
список их и показывает.

### 🔴 Сначала РАЗВЕДКА ПО ДАННЫМ, потом код

Это проблема данных, а не только фильтра. Прежде чем править UI, выяснить фактами:

```sql
-- сколько задач с wbs_code и как они распределены по источникам
select
  (wbs_code is not null) as has_wbs,
  (project_id is not null) as has_project,
  count(*)
from tasks where deleted_at is null group by 1,2 order by 1,2;

-- дубли по названию среди личных
select title, count(*) c
from tasks
where deleted_at is null and project_id is null
group by title having count(*) > 1
order by c desc limit 20;

-- есть ли у личных дублей wbs_code и общий created_at (признак одного импорта)
select id, title, wbs_code, project_id, created_at, created_by
from tasks
where deleted_at is null and project_id is null
order by created_at desc limit 30;
```

Ответить в отчёте на три вопроса:

1. У личных дублей `wbs_code` **есть или нет**? Если есть — фильтр можно строить
   на нём; если нет — признака WBS у этих строк не существует, и нужен другой.
2. Это **дубли одного импорта** (два прогона `PlanImport`) или один прогон создал
   обе копии — с `project_id` и без?
3. Сколько строк подлежит чистке и **есть ли среди них живые** — с исполнителем,
   дедлайном, комментариями или событиями в журнале.

### Решение — по результату разведки, НЕ вслепую

- **Если у строк плана есть `wbs_code`**: ввести предикат «строка плана» в домене
  (`lib/domain/`, чистая функция + тесты) и применить его в `TasksView` **всегда**,
  независимо от фильтра источника: план живёт на доске проекта, в списке задач
  ему места нет ни как «проектной», ни как «личной» задаче.
- **Если признака нет**: он нужен — колонка `tasks.is_plan_item boolean not null
  default false` (миграция, аддитивно) + бэкфилл по `wbs_code is not null` и по
  импортированным строкам. Бэкфилл — **отдельным шагом**, не в той же миграции.
- **Дубли без `project_id`** удалять только после явного подтверждения владельца:
  подготовить `select` со списком id и `update tasks set deleted_at = now() where id in (…)`
  **закоммитить в миграцию, не применять** (правило проекта: чистка прода — через гейт).

⚠️ `PlanImport` починить в корне: если он создаёт задачи и с `project_id`, и без —
это и есть источник мусора, иначе следующий импорт нальёт его снова. Разобрать
`src/components/tasks/PlanImport.tsx` и `lib/**/plan-import-helpers` (там уже есть
тесты — `tests/unit/plan-import-helpers.test.ts`, 20 штук: дописать кейс на дубль).

### Гантт (задача 3)

Формулировка владельца — «убрать привязку этапов к задачам». После введения
предиката строки плана уходят из списка задач сами; Гантт и доска «План» продолжают
их показывать — они там и живут. **Ничего в `GanttTimeline` не удалять**, пока не
подтверждено разведкой, что дефект именно в нём: `wbs_code` он только отображает
(строка 1293), а данные берёт из `useProjectSchedule`.
