# Claude Code Prompt — Fix: бюджет по реальному лимиту + прогоны-зомби

Гейт проверил лимит, на котором стоял прошлый фикс, и **лимит был назван мной неверно**.

`processRun` живёт в `EdgeRuntime.waitUntil` (`ai-run/index.ts:1613`). Значит ~90 с,
объявленные «шлюзом Supabase», к нему не относятся: это про синхронный ответ, а `ai-run`
отвечает сразу `{ run_id }` и работает в фоне. По документации Supabase
([Limits](https://supabase.com/docs/guides/functions/limits),
[Background Tasks](https://supabase.com/docs/guides/functions/background-tasks)):

| | значение |
|---|---|
| Wall clock воркера (он же держит фоновые задачи) | **150 с** на Free (проект на Free) |
| Request idle timeout | 150 с — нас не касается, отвечаем сразу |
| CPU time | 2 с на запрос, **без учёта асинхронного I/O** — у нас всё ожидание сети |

`BRIEF_BUDGET_MS = 82_000` зажат вдвое сильнее необходимого. Механика распределения при
этом верна и остаётся — динамический остаток лучше статического потолка при любом бюджете.

## ЗАДАЧА 1 — новые числа

```ts
/**
 * Общий бюджет двухпроходного прогона.
 *
 * Ограничение — НЕ шлюз (ai-run отвечает сразу и работает в EdgeRuntime.waitUntil),
 * а wall clock воркера: 150 с на Free-тарифе. Считается он на ВОРКЕР, а не на прогон:
 * воркер мог обслуживать запросы до нас, и сколько осталось — узнать неоткуда.
 * Отсюда 100 с, а не 150: пятьдесят секунд оставлены чужой работе и запуску.
 */
const BRIEF_BUDGET_MS = 100_000;
const SEARCH_PASS_TIMEOUT_MS = 50_000;   // замер: 27 с; было 55_000
/** Пол, а не порог отказа. См. Задачу 2. */
const STRUCT_FLOOR_MS = 25_000;
```

Худший случай: поиск упирается в свои 50 с, упаковщику достаётся 50 с, итого 100 с при
потолке 150 с.

## ЗАДАЧА 2 — отказ по нехватке бюджета заменить на пол

Сейчас `structTimeoutMs < STRUCT_MIN_MS` ⇒ проход 2 **не вызывается**, летит `LlmError`.
При бюджете 82 с это означало отказ на поиске длиннее 64 с — то есть мы придумали стену и
сами в неё упёрлись.

```ts
const structTimeoutMs = Math.max(BRIEF_BUDGET_MS - searchMs, STRUCT_FLOOR_MS);
```

Обоснование, запиши его комментарием: **превысить бюджет не смертельно, отказать —
смертельно точно.** Бюджет у нас оценочный (см. выше про воркер), а отказ — гарантированная
потеря уже оплаченного поиска. Симметрии между этими исходами нет.

Ветку с `timedOut: true` и текстом «Анализ занял слишком долго» **не удаляй** — она нужна
для настоящего таймаута прохода 2. Уходит только предварительный отказ до вызова.
Соответственно и тест «остаток 12 с ⇒ проход 2 не вызывается» переписывается на «остаток
12 с ⇒ проходу 2 дан пол 25 с, вызов состоялся».

## ЗАДАЧА 3 — прогоны-зомби при выключении воркера

Этого нет в коде вовсе, и это дыра шире бюджета. Если воркер убьют по wall clock, строка
`ai_runs` навсегда останется в `running`: `catch` такое не ловит, потому что исключения нет.
В интерфейсе — вечный спиннер до перезагрузки страницы.

Документация даёт ровно один хук:

```ts
addEventListener('beforeunload', (ev) => { … });
```

Заведи его в `ai-run/index.ts`: держи идентификаторы прогонов, которые сейчас в работе, и на
`beforeunload` помечай их ошибкой — класс `upstream` (повтор осмыслен), текст про то, что
анализ не был завершён. Причину выключения из `ev.detail?.reason` — в лог.

Два ограничения, которые надо учесть и назвать в отчёте:

1. на `beforeunload` времени мало — успеть должен один UPDATE, без ретраев и без лишних
   запросов;
2. параллельных прогонов в одном воркере может быть несколько — набор, а не одна
   переменная. Строку из набора убирай в `finally`, иначе завершённый прогон получит
   ложную ошибку при выключении.

## Границы

- Модель упаковщика не меняем — это следующий заход вместе с остальными шестью пресетами.
- Известный предел прошлого захода (ретрай формы — второй `callLlmSearch` со своим
  бюджетом) при потолке 150 с перестаёт быть теоретической проблемой: два прогона по 100 с
  в него не влезают, но ретрай пропускает проход 1 и стоит ~25 с. Оставляем как есть,
  **но зафиксируй это комментарием** — на платном тарифе (400 с) вопрос снимется сам, на
  Free он остаётся риском.

## Тесты

- поиск 27 с ⇒ упаковщику 73 с;
- поиск 90 с (гипотетический) ⇒ упаковщику пол 25 с, вызов **состоялся**;
- поиск упёрся в 50 с ⇒ упаковщику 50 с, сумма не больше 100 с;
- `beforeunload` при одном прогоне в работе ⇒ ровно один UPDATE со статусом `error`;
- `beforeunload` после завершения прогона ⇒ UPDATE не идёт (набор пуст).
