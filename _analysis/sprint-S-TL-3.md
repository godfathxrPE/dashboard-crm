## Почему `org_timeline` не здесь — прочитать до начала

Вчера планировали `p_kinds` и `org_timeline()` одним спринтом. Разведка показала, что
это разные по природе работы, и вторая тянет за собой UI, которого спринт не выдержит.

**`p_kinds` — дефект в проде.** Фильтр показывает не то, что обещает, прямо сейчас.

**`org_timeline` — новая способность**, и у неё нашлись **живые потребители**:
`useRecentActivity` читает `activity_log` напрямую и питает два места — блок «Последние
действия» на дашборде (20 записей) и `ActivityDrawer` (5). То есть org-лента в проде
уже есть, но она **неполна по построению**: показывает только журнал, без звонков,
встреч, задач и AI-прогонов. Это стоит починить — но это замена двух компонентов с
их собственными табами и рендером, отдельным спринтом S-TL-4.

Здесь — только фильтр. Одна проверяемая ценность.

---

## Что меняется и почему это одна работа, а не две

Перенос фильтра на сервер **обязан** идти вместе с переносом отсечки курсора внутрь
веток. Иначе фильтр сам породит дефект.

**Риск, зафиксированный на гейте S-TL-2.** Сейчас ветка отбирает `limit N` по грубой
отсечке `ts <= p_before`, а точная отсечка по паре `(ts, id)` стоит **снаружи** union.
Пока веток шесть, выброшенное снаружи покрывается запасом (до 300 кандидатов против 50
в выдаче). **`p_kinds` этот запас убирает:** при `p_kinds = ['task']` работает одна
ветка, и если курсор попал в середину блока ничьих, снаружи отбросится почти всё
отобранное. Страница выйдет короче лимита, `getNextPageParam` увидит
`length < PAGE_SIZE` и решит, что достигнуто дно — **при живом хвосте**.

На живых данных это воспроизводимо: у «Хороший вкус — внедрение» **40 задач с одним и
тем же `created_at`**, и все они имеют одинаковый `ts`.

Лечится переносом точной отсечки внутрь каждой ветки — тогда ветка отдаёт ровно N
подходящих строк, и внешний `limit` ничего не теряет.

## ЗАДАЧА 1: миграция `114_entity_timeline_kinds.sql`

### 1.1 Сигнатура

```sql
drop function if exists public.entity_timeline(text, uuid, timestamptz, text, int);

create or replace function public.entity_timeline(
  p_entity_type text,
  p_entity_id   uuid,
  p_before      timestamptz default null,
  p_before_id   text        default null,
  p_limit       int         default 50,
  p_kinds       text[]      default null   -- null = все виды
)
returns table ( … те же восемь колонок … )
```

`drop` первой строкой — по той же причине, что в 113: перегрузка даёт PostgREST
`PGRST203`, вызов с пятью аргументами подошёл бы обеим сигнатурам. Гранты после
`drop`+`create` повторить явно (шесть аргументов в сигнатуре!).

### 1.2 Словарь видов

`p_kinds` принимает шесть настоящих видов плюс **псевдо-вид `note`**:

```
'call' | 'meeting' | 'task' | 'project' | 'activity' | 'ai_run' | 'note'
```

`note` — не источник, а срез внутри `activity_log`: события с
`event_type in ('comment_added')` (значение из `NOTE_EVENT_TYPES`). Сейчас этот чип
живёт на клиенте как производный от `kind='activity'` — на сервере он выражается точно,
и чип перестаёт быть особым случаем.

Правила отбора внутри `src_activity`:

```sql
and ( p_kinds is null
   or 'activity' = any(p_kinds)                                    -- весь журнал
   or ('note' = any(p_kinds) and al.event_type = any(array['comment_added'])) )
```

⚠️ Список типов заметок **продублирован** в SQL и в `NOTE_EVENT_TYPES` (TS). Это
осознанный компромисс — SQL не может импортировать константу, — но он обязан быть
явно отмечен комментарием в обоих файлах: «при добавлении типа заметки править ОБА
места». Ровно тот класс дефекта, что дедуп ОПФ в трёх копиях из S-TG-3.

### 1.3 Отсечение ветки целиком

Каждая ветка получает в `where` первым конъюнктом:

```sql
and (p_kinds is null or '<kind>' = any(p_kinds))
```

Для `src_activity` — условие из 1.2 (два вида могут её включить).

При `p_kinds = ['task']` предикат ветки `src_calls` схлопывается в `false`, и Postgres
отбрасывает её как one-time filter, не читая таблицу.

### 1.4 🔴 Отсечка курсора переезжает ВНУТРЬ веток

**Главное изменение спринта.** В 113 внутри ветки стояла только грубая отсечка. Теперь
рядом с ней — точная, по той же паре, что и снаружи. Пример для `src_calls`:

```sql
    -- грубая отсечка по ts — она индексируемая, её оставляем ради index scan
    and (p_before is null or c.date <= p_before)
    -- ⚠️ ТОЧНАЯ отсечка по паре — ОБЯЗАТЕЛЬНА с появлением p_kinds.
    -- Без неё ветка отдаёт N строк, часть которых внешний фильтр выбрасывает;
    -- при одной работающей ветке (p_kinds=['task']) и блоке ничьих страница
    -- выходит короче лимита, и пагинация встаёт на живом хвосте.
    and (p_before is null
         or (c.date, 'call:' || c.id::text) < (p_before, coalesce(p_before_id, 'zzzz')))
```

Обе отсечки нужны: грубая даёт планировщику диапазон по индексу, точная гарантирует,
что ветка не вернёт ни одной строки, которую выбросит внешний фильтр.

То же — во всех шести ветках, с их собственным выражением `ts` и префиксом `id`:

| Ветка | Выражение пары |
|---|---|
| `src_calls` | `(c.date, 'call:' \|\| c.id::text)` |
| `src_meetings` | `((m.date::timestamp at time zone 'UTC'), 'meeting:' \|\| m.id::text)` |
| `src_tasks` | `(coalesce(t2.deadline, t2.created_at), 'task:' \|\| t2.id::text)` |
| `src_projects` | `(p.created_at, 'project:' \|\| p.id::text)` |
| `src_activity` | `(al.created_at, 'activity:' \|\| al.id::text)` — в **обеих** ветвях union |
| `src_ai` | `(ar.created_at, 'ai_run:' \|\| ar.id::text)` — в **обеих** ветвях union |

Внешний фильтр остаётся как есть — он теперь страховка, а не рабочий механизм.

⚠️ У `src_meetings` грубая отсечка идёт по UTC-выражению, а `order by` — по сырой
`m.date` (решение S-TL-2, приведение монотонно, индекс остаётся рабочим). Точную
отсечку писать **по UTC-выражению**, чтобы обе половины пары жили на одной оси.

## ЗАДАЧА 2: клиент — фильтр становится запросом

`src/lib/hooks/use-entity-timeline.ts`:

```ts
export function useEntityTimeline(
  entityType: TimelineEntityType,
  entityId: string | null | undefined,
  kinds?: readonly TimelineFilterValue[],   // undefined | ['all'] ⇒ p_kinds = null
```

- `queryKey: ['timeline', entityType, entityId, kinds ?? 'all']` — смена чипа даёт
  новый ключ и новый запрос с первой страницы. Курсор при этом сбрасывается сам:
  `useInfiniteQuery` начинает новую запись кеша.
- `'all'` не отправляется в `p_kinds` — там `null`.

`src/components/shared/EntityTimeline.tsx`:

- `filter` перестаёт фильтровать `events` на клиенте — он уходит в хук. Убрать `useMemo`
  с `events.filter(...)` и производный срез `note` (`isNoteEvent` в компоненте больше
  не нужен; сама функция остаётся — её зовёт `rpc-adapter`).
- `kindFilter` (набор чипов, которые вообще предлагать) остаётся клиентским — это
  конфигурация карточки, а не фильтр данных.
- Состояние «фильтр выбран, событий нет» теперь означает **честное** «событий этого

- ⚠️ При смене чипа лента перерисуется с загрузкой. Показать `isLoading` — иначе на

## ЗАДАЧА 3: тест на досрочное дно

Главный тест спринта, и он **обязан краснеть на коде без задачи 1.4**.

`tests/unit/` — проверка чистой функции `nextTimelineCursor` тут не поможет: дефект
живёт в SQL. Поэтому тест — интеграционный по смыслу, но выполнимый юнитом: фейковый
клиент отдаёт **страницу короче лимита при наличии хвоста**, и проверяется, что хук
не останавливается... — нет, так дефект не воспроизвести, потому что при короткой
странице остановка **корректна**.

Поэтому проверка переезжает на гейт как SQL-сценарий (см. ниже), а в юнит-тестах —
то, что проверяемо:

1. `p_kinds` доезжает до RPC: фейковый клиент фиксирует аргументы, `['note']` уходит
   как `['note']`, `'all'` — как `null`.
2. `queryKey` меняется при смене набора видов (иначе React Query отдаст чужой кеш).
3. Смена набора видов сбрасывает пагинацию к первой странице.

## Сверка на гейте

Миграция 114 **не применена**. Ниже — то, что гейт обязан прогнать после `apply_migration`,
и то, что уже сверено на живых данных ДО применения (телом функции как обычным SELECT).

### 1. Досрочное дно — главный сценарий (уже сверен до apply, повторить после)

«Хороший вкус — внедрение» (`73ef7090-4d68-48b3-bd69-1b0f28d17a3b`): **40 задач с одним
и тем же `ts`** (`2026-07-12 17:43:03.178164+00`), лимит меньше блока ничьих.

```sql
-- страница 1
select ts, id from entity_timeline(
  'project','73ef7090-4d68-48b3-bd69-1b0f28d17a3b', null, null, 10, array['task']);
-- дальше циклом: p_before / p_before_id = ts и id ПОСЛЕДНЕЙ строки предыдущей страницы,
-- до страницы короче 10.
```

**Ожидание:** 4 страницы по 10 + пятая пустая, **40 уникальных id, 0 дублей**.

Результат прогона тела функции 2026-08-09 (до apply, read-only):

| | page1 | page2 | page3 | page4 | page5 | uniq | rows | задач в сделке |
|---|---|---|---|---|---|---|---|---|
| с отсечкой внутри ветки (114) | 10 | 10 | 10 | 10 | 0 | **40** | 40 | 40 |
| грубая внутри + точная снаружи (113) | 10 | **0** | — | — | — | 10 | 10 | 40 |

То есть до правки 1.4 лента обрывалась **на первых десяти из сорока** — молча, с видом
достигнутого дна. Это и есть регрессия, ради которой отсечка переехала внутрь веток.
