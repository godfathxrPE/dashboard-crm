# Спринт S-DOCS-PR-1 — `scripts/docs-pr.sh`: документная правка одной командой

**Вход:** `main` = `a4fd0e0` (после #70, #71, #72 и PR правил worktree). **Миграций НЕТ.**
**Ветка:** `feat/docs-pr-script` (кодовая — скрипт; worktree по правилу Шага 0.4,
папка `feat+docs-pr-script`).
**Baseline:** снять в разведке.

---

## Зачем

Правка одной строки в документе стоит сегодня восьми шагов: ветка → коммит → пуш →
`gh pr create` с явной базой → номер PR в реестр вторым коммитом → ожидание CI →
мерж → `git pull`. Для миграции с RLS это оправдано целиком. Для строки «вход спринта
= такой-то коммит» — нет, и 06.09 этот путь пройден дважды подряд.

Ослаблять branch protection нельзя: прямой пуш в `main` отклоняется правилом
`Required status check "checks"`, и это правильно — на нём держится и `status-check`,
и защита от случайной записи в главную ветку. Значит убираем не защиту, а ручную
церемонию вокруг неё.

**Скрипт не даёт новых прав.** Он делает ровно то же, что делают руки, — но без
пропусков шагов и с проверками, на которых 06.09 споткнулись.

### Три ошибки дня, которые скрипт обязан сделать невозможными

| Что случилось 06.09 | Проверка в скрипте |
|---|---|
| `gh pr create` без `--base` взял базой текущую ветку; PR смержился в базу, которой уже не было, изменения в `main` не попали (#67) | база передаётся ВСЕГДА явно; после создания PR сверяется `baseRefName == main` |
| Коммит ушёл из worktree, где лежала копия `_analysis/` до правок по ревью; в PR уехала старая редакция | скрипт отказывается работать из worktree (`git rev-parse --git-common-dir` ≠ `.git`) |
| Ветка отходила от устаревшего `main`, дальше — конфликт и ручной `rebase --onto` | ветка всегда создаётся от свежего `origin/main` после `fetch` |

## ЗАДАЧА 1 — скрипт

`scripts/docs-pr.sh`, стиль как у соседей: `#!/usr/bin/env bash`, `set -uo pipefail`,
русские сообщения с префиксом `docs-pr:`, выход 0 — успех, 1 — отказ с объяснением.

**Вызов:**

```
scripts/docs-pr.sh <ветка> <сообщение коммита> [файл ...]
```

Без списка файлов — берутся все изменённые и untracked под `_analysis/`,
`crm-architect/`, `docs/`. Явный список перекрывает это правило.

**Порядок работы:**

1. **Отказы до единого действия** (ничего не менять, пока не пройдены все):
   - запуск не из корня репозитория (нет `.git` рядом) — отказ;
   - **запуск из worktree** — `[ "$(git rev-parse --git-common-dir)" = ".git" ]`,
     иначе отказ с текстом про Шаг 0.4 `worktree-isolation`;
   - имя ветки не начинается с `docs/` или `chore/` — отказ: скрипт только для
     документных веток, у кодовых свой цикл с worktree и гейтом;
   - рабочее дерево содержит изменения ВНЕ разрешённых путей — отказ со списком
     файлов: «это кодовая правка, ей нужен спринт и гейт»;
   - в диффе есть файл не с расширением `.md` / `.html` — отказ (признак документной
     ветки из `worktree-isolation`, Шаг 0.4). **Исключение — `.sql` под
     `supabase/migrations/`, и только когда правка в нём ЧИСТО комментарная**: все
     добавленные и удалённые строки начинаются с `--` или пусты. Проверять грепом по
     `git diff --cached -U0 -- supabase/migrations`. Без исключения скрипт отверг бы
     самый частый вид документной правки — гейтовую: PR #72 (07.09) нёс шапки 129 и
     130, где «НЕ применена» менялось на `applied`. Любая НЕкомментарная строка в
     `.sql` — отказ: это правка схемы, ей нужен гейт;
   - существует `.git/index.lock` — отказ с текстом «висит index.lock: проверить
     `ps aux | grep "[g]it "`, и если процесса нет — снять руками». 07.09 лок висел
     дважды и валил `git add` уже после успешного `checkout -b`, оставляя ветку
     созданной, а коммит — нет; скрипт в таком состоянии не должен идти дальше;
   - нечего коммитить — выход 0 с сообщением, не ошибка.
2. `git fetch origin`, `git checkout -b <ветка> origin/main` — **всегда от свежего
   origin/main**, не от текущего HEAD.
3. `git add` перечисленных путей, `git commit -F -` (тело через stdin: многострочное
   сообщение через `-m` в zsh владельца глотает `!` — history expansion, урок 06.09).
4. `git push -u origin <ветка>`.
5. `gh pr create --base main --head <ветка> --title <сообщение> --body <тело>`.
5б. **Подстановка номера PR.** Конвенция требует номер PR в реестре STATUS, а до
   `gh pr create` номера не существует — сегодня это делается вторым коммитом руками, и
   при авто-мерже вписывать станет некуда: понадобится ЕЩЁ один PR ради номера
   предыдущего. Решение — плейсхолдер: человек пишет в реестре `| #PR |`, скрипт после
   создания PR заменяет **ровно эту подстроку** (`| #PR |` → `| #72 |`) в файлах диффа,
   коммитит `docs(status): номер PR в реестр` и пушит в ту же ветку ДО мержа.
   Плейсхолдера нет — шаг молча пропускается (документная правка не обязана быть
   закрытием спринта). Плейсхолдер есть, но замена ничего не изменила — отказ:
   значит, текст разошёлся с ожиданием.
   ⚠️ Замена строго по литералу `| #PR |`, без регулярок по `#`: в тексте реестра
   номера PR встречаются в прозе десятками, и широкий шаблон переписал бы историю.

6. **Сверка базы:** `gh pr view <N> --json baseRefName` — не `main` ⇒ громкий отказ
   с номером PR и указанием закрыть его руками. Молча продолжать нельзя: именно так
   ушёл в никуда #67.
7. `gh pr merge <N> --auto --squash --delete-branch`.
8. Ожидание: опрос `gh pr view <N> --json state` раз в 10 секунд, максимум 5 минут.
   Смержился — `git checkout main && git pull --ff-only`, напечатать новый HEAD.
   Не успел — **не ошибка**: печатать «авто-мерж взведён, PR #N смержится сам;
   вернуться на main: git checkout main && git pull --ff-only» и выходить 0.
9. Возврат на `main` в любом исходе, кроме отказа на шаге 1.

**Чего скрипт НЕ делает:**

| | Почему |
|---|---|
| не трогает `--force` и `--admin` | обход защиты не входит в задачу |
| не решает, что писать в STATUS | реестр ведёт человек или CC; скрипт только подставляет номер в готовый текст (см. шаг 5б) |
| не работает с кодовыми ветками | у них worktree, ревью, гейт и cold review |
| не удаляет локальные ветки, кроме своей | чужие ветки — не его дело |

⚠️ **bash 3.2.** Массивы под `set -u` разворачивать через `${arr[@]+"${arr[@]}"}` —
дословно как в `skill-deploy.sh` (там это стоило падения раскатки 29.08).
`mapfile`/`readarray` в 3.2 НЕТ, `${var,,}` тоже — не использовать.

## ТЕСТЫ

Bash-скрипты в проекте юнит-тестами не покрыты, и заводить ради одного скрипта
раннер не нужно. Вместо этого — **прогон отказов вручную**, результат в отчёт
таблицей:

| Сценарий | Ожидание |
|---|---|
| запуск из worktree | отказ, ничего не создано |
| `.sql` с комментарной правкой под `supabase/migrations/` | проходит |
| `.sql` с реальным DDL (`alter table …`) | отказ: нужен гейт |
| плейсхолдер `\| #PR \|` в STATUS | заменён на номер, отдельный коммит в той же ветке до мержа |
| плейсхолдера нет | шаг пропущен молча, прогон успешен |
| ветка `feat/xxx` | отказ: только `docs/` и `chore/` |
| в дереве изменён файл в `src/` | отказ со списком |
| нечего коммитить | выход 0, «нечего коммитить» |
| нормальный прогон на пробной правке `_analysis/` | ветка, PR с базой `main`, авто-мерж взведён |
| прогон при недоступном `gh` | отказ, ветка и коммит остаются локально, объяснение |
| висит `.git/index.lock` | отказ до `checkout -b`, ветка не создана |

Пробную правку после прогона откатить, PR закрыть — в отчёте указать его номер.

Строка в отчёте обязательна: «юнит-тестов нет: bash-скрипт, проверен прогоном
шести сценариев отказа».
