## Зачем

Гейт вскрыл дыру в самом фикс-файле, а не в реализации: правило «отсутствующие ключи
претензией не считаются» опиралось на предположение, что `required` держит сама модель.
Живые данные говорят обратное.

Прогон `3d5e6e70-…` (13.07, `analytic_note`) вернул **один ключ из шести обязательных** —
весь payload схлопнут в `client_situation`. Сегодня он всё же вызовет ретрай, но
**случайно**: только потому, что в нём есть маркер `</`. Не будь маркера — огрызок вместо
записки прошёл бы молча, с вердиктом «форма годна».

Проверка на живых данных (7 строк `ai_runs`, счёт отсутствующих required верхнего уровня):

| Прогон | Дата | Пресет | Пропущено required | Каких |
|---|---|---|---|---|
| `fe583809` | 07.07 | `analytic_note` | 0 | — |
| `3a75cfbb` | 11.07 | `analytic_note` | **1** | `needs` |
| `3d5e6e70` | 13.07 | `analytic_note` | **5** | `needs, stakeholders, deal_risks, recommendations, kp_arguments` |
| `98bf6088` | 27.07 | `deal_progression` | 0 | — |

| `1870ed1f` | 28.07 | `analytic_note` | 0 | — |
| `04e5be64` | 28.07 | `deal_progression` | 0 | — |

**Пять из семи — чисто, пропуски дают ровно те две уже известные испорченные строки.**
Значит правка не начнёт ретраить нормальные ответы.

## Правка

`supabase/functions/ai-run/shape.ts`, внутри `checkResultShape`, **между** типовой и
маркерной проверками:

```ts
  // ── Пропущенные обязательные поля (мягкая) ──
  // `required` модель НЕ держит: прогон 3d5e6e70 (13.07) вернул 1 ключ из 6.
  // Класс мягкий намеренно: претензия обязана вызвать ретрай, но не отказ —
  // частичный ответ пользователю полезнее пустого экрана, а второй попытки
  // обычно хватает. Проверка на живых данных: 5 из 7 прогонов дают 0 претензий,
  // пропуски только у двух уже известных испорченных.
  const required = inputSchema?.required;
  if (Array.isArray(required)) {
    for (const key of required) {
      if (typeof key === 'string' && !(key in input)) {
        claims.push({ kind: 'soft', message: `${key}: обязательное поле отсутствует` });
      }
    }
  }
```

Только верхний уровень. Вложенные `required` (внутри `items` массивов — `['claim','quote']`,
`['what','who','due']`, `['text']` и т.д.) **не проверять**: обход элементов массива ради
этого удваивает сложность модуля, а поштучно битые элементы уже отсеивает клиентский Zod
(`taskSchema.nullable().catch(null)` + filter). Дублировать не надо.

Обновить doc-комментарий `checkResultShape`: сейчас там написано «Отсутствующие ключи
претензией НЕ считаются: `required` держит сама модель» — это ровно то утверждение, которое
опровергнуто фактом. Заменить на описание новой проверки с ссылкой на `3d5e6e70`.

## Тесты (`tests/unit/ai-shape.test.ts`)

Добавить три:

1. **Пропуск одного required → одна мягкая претензия, ноль жёстких.** Фикстура — форма
   `3a75cfbb`: пять ключей верных типов, `needs` отсутствует.
2. **Схлопнутый ответ → пять мягких, ноль жёстких.** Фикстура — форма `3d5e6e70`:
   единственный ключ `client_situation` строкой.
3. **Схема без `required` не роняет проверку** — как уже сделано для `properties`.

Плюс проверить, что существующий тест «корректный ответ → пустой список претензий» не
покраснел: у полных фикстур все required на месте.

## Границы

- Не трогать классификацию: `required` — **мягкая**, не жёсткая. Жёсткая означала бы
  отказ, а отказывать из-за неполного ответа — хуже, чем показать частичный.
- Не проверять вложенные `required`.
- Не менять `SHAPE_MARKERS`, `SHAPE_RETRY_HINT`, логику выбора попытки, `sumUsage`.
- Не деплоить edge и не мержить — за Олегом.
