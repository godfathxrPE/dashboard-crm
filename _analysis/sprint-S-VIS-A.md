## КЛЮЧЕВЫЕ РЕШЕНИЯ (принять как есть)

1. **Расширяется ТОЛЬКО SELECT, только шесть таблиц:** `companies`, `contacts`, `leads`,
   `calls`, `meetings`, `activities`. Новое тело: `org_id = (select current_org_id())` —
   и всё. Роль не проверяем: `current_org_id()` без membership отдаёт NULL → чужие org
   отрезаны, viewer видит в скоупе org (RBAC-матрица: Viewer Read All ✓ в пределах org).
2. **INSERT/UPDATE/DELETE не трогаются вообще.** Менеджер видит всю базу, правит своё.
   Откат всего спринта = 6 `drop policy` + восстановление тел из шапки миграции.
3. **`projects`/`tasks` не трогаются** — у них member-модель из 065, сделки менеджерам
   Олег раздаст назначением (owner_id), это следующий шаг после мержа.
4. **Списки становятся командными НАМЕРЕННО** — это цель спринта. «Компании», «Контакты»,
   «Лиды», «Звонки», «Встречи» показывают всё в org. Ничего не фильтровать.
5. **Бейджи сайдбара — семантика «мои» сохраняется явными фильтрами.**
   Просрочка ЧУЖОГО звонка не должна красить мой сайдбар красным:
   - `calls`-бейдж: считать только по своим (`created_by === myId` на клиенте — id юзера
     в сайдбаре уже есть через useAuth; проверь и возьми существующий источник);
   - `leads`-бейдж: оставить командным БЕЗ фильтра — лиды это общий пул, новый лид
     должен быть виден всем (осознанная асимметрия с calls, так и закомментируй);
   - `tasks`-бейдж: не меняется (RLS tasks не трогаем).
6. **Аудит «мои» — по потребителям, не по хукам.** Хуки отдают то, что видно; фильтрует
   потребитель с семантикой «мои» (бейджи, виджеты «сегодня»). Впихивать `.eq(owner)` в
   сам хук нельзя — спискам нужна команда.

## ЗАДАЧА 1 — Миграция `098_team_read_visibility.sql` (НЕ применять!)

Для шести таблиц: `drop policy if exists <name> on <table>;` → `create policy` с телом
`using (org_id = (select public.current_org_id()))`. Имена политик — фактические
(`companies_select`, `contacts_select`, `leads_select`, `calls_select`, `meetings_select`,
`activities_select`).

В шапке миграции: зачем (команда видит пустую CRM), что НЕ меняется (запись, projects,
tasks), прежние тела всех шести политик (это и есть инструкция отката), ссылка на
бэклог DIRECTIONS как на следующий слой. Отдельным абзацем: `meetings` теряет
attendee-эксклюзивность намеренно — календарь команды это фича, а не утечка (встреча
уровня org видна org).

Perf-примечание: новое тело — один initplan-вызов, дешевле старого (уходят
`current_org_role()` и OR-ветки). Индексы `(org_id)` на всех шести есть по конвенции —
проверь `\d` каждой на гейте не надо, CC достаточно grep по baseline.
