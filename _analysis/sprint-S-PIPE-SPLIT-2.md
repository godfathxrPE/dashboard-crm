# Спринт S-PIPE-SPLIT-2 — вторая воронка направления в интерфейсе

**03.10.2026.** **Вход:** `main` ≥ `5768128` (#158, миграция 136 applied). **Миграций НЕТ.**
**Ветка:** `feat/pipe-split-2`, worktree по `worktree-isolation`. Первым коммитом сохранить этот текст в `_analysis/sprint-S-PIPE-SPLIT-2.md`.
**Решения:** проект Claude, `claude/decisions-iiot-pipelines-2026-10-03.md`; гейт 136 — `claude/gate-S-PIPE-SPLIT-1.md`.

## Зачем

Миграция 136 разделила пресейл IIoT: «IIoT Проект» (`a0000000-…-0001`, `is_default`) и
«IIoT Эксперимент» (`a0000000-…-0005`, не default). Интерфейс до сих пор считает, что у
направления **одна** deal-воронка — берёт `is_default` в трёх местах (`ProjectModal`,
`PipelineBoard`, `StageBoard`). Через неделю у владельца реальный эксперимент: сделку надо
завести в «IIoT Эксперимент», видеть на доске, вести по стадиям и переводить между воронками.

**Найденный дефект, который спринт закрывает:** `PipelineBoard` (`grouped`, ветка
«If direction matches but stage not found — put in first column») кладёт сделку, чья стадия
не из активной воронки, **в первую колонку**. Сделка-эксперимент сейчас всплывёт на доске
проекта в «Привлечении» с чужой стадией. Аналогичную ветку проверить в `StageBoard`.

## Решения (владелец 03.10 + гейт)

1. **Воронка — выбор, а не дефолт.** Если у направления больше одной deal-воронки, рядом с
   фильтром направления появляется переключатель воронки. Одна воронка — переключателя нет
   (ERP выглядит как сейчас).
2. **Перевод между воронками — переход стадии, а не правка формы.** Принцип S-R2-TRANSITION-1a
   сохраняется: стадия (а теперь и воронка) меняется через единственный вход
   `useStageTransition` — с гейтом требований и журналом. В модалке редактирования воронка,
   как и стадия, только для чтения.
3. **Стадия при переводе — по названию.** «Материалы» → «Материалы». Нет такой стадии в
   целевой воронке — первая рабочая стадия. Выиграна/Проиграна → терминальная той же природы.
4. **Захардкоженных id воронок в коде нет и не появляется.** Всё — из `usePipelines()` по
   `direction` + `entity_type = 'deal'`, порядок: default первым, дальше по имени.

## Что НЕ меняется

- БД: ни миграций, ни RPC. `convert_lead` по-прежнему кладёт сделку в default-воронку —
  перевод в эксперимент делается из сделки (п. 2). `spawn_delivery_project` не трогаем: вид
  внедрения в мастере пока выбирается руками (авто-вид из воронки — бэклог, нужен признак
  воронки в БД).
- Кокпит, `DealHeader`, `ProjectCard`, нормы стадий в настройках — уже работают от
  `project.pipeline_id` / по всем воронкам. Проверить, не переписывать.
- Delivery-воронки (`entity_type = 'project'`) — вне спринта.

## ЗАДАЧА 1: Домен — воронки направления и перенос стадии

Новый файл `src/lib/domain/pipeline-choice.ts`, чистые функции (время/рандома нет):

```ts
/** Deal-воронки направления: default первой, дальше по name (localeCompare 'ru'). */
export function dealPipelinesFor(pipelines: Pipeline[], direction: Direction): Pipeline[];

/** Активная воронка доски: id из URL, если он — deal-воронка ЭТОГО направления; иначе default; иначе первая. */
export function resolveActivePipeline(
  pipelines: Pipeline[], direction: Direction, requestedId: string | null,
): Pipeline | null;

/** Стадия в целевой воронке при переводе. */
export function mapStageToPipeline(
  current: PipelineStage | null, targetStages: PipelineStage[],
): PipelineStage | null;
```

`mapStageToPipeline`:
- `current.is_won` → стадия `is_won` цели; `current.is_lost` → `is_lost` цели;
- иначе — рабочая стадия цели с тем же `name` (сравнение `trim().toLocaleLowerCase('ru')`);
- нет совпадения или `current = null` → рабочая стадия цели с минимальным `order_index`;
- в цели нет рабочих стадий → `null` (вызывающий перевод не предлагает).

## ЗАДАЧА 2: Переключатель воронки в разделе сделок

   вернул `resolveActivePipeline` (без параметра — default). Сброс чипа = вернуть default

3. Пропс `pipelineId: string` (уже разрешённый) уходит в `PipelineBoard`, `StageBoard`,
   `ProjectsTable`.

`PipelineBoard.tsx`, `StageBoard.tsx`:
4. `activePipeline` — из пропса, не из `is_default`. Удалить локальный поиск default.
5. **Дефект:** клиентские сделки, у которых `pipeline_id !== activePipeline.id`, на доску не
   попадают вообще (до раскладки по колонкам). Ветку «stage not found → первая колонка»

   прокомментировать, что это аварийная ветка.
6. `HeroMetrics` уже принимает `pipelineId` — передать активный.

`ProjectsTable.tsx`:

9. Чипы трека «Подготовка / Эксперимент / Проект» врут: «Эксперимент» сейчас = группа стадий

   с подписями доски (`PHASE_LABELS`: Привлечение / Проработка / Согласование / Закрытие —

## ЗАДАЧА 3: Воронка в форме сделки

## ЗАДАЧА 4: Перевод сделки между воронками

Домен `src/lib/domain/stage-transition.ts`:
1. `TransitionInput` получает необязательный `pipelineId`. `buildTransitionPatch` кладёт
   `pipeline_id` в **тот же** UPDATE, что `stage_id` (атомарность — см. шапку файла; гейт
   требований стадии срабатывает на этом же UPDATE). Без `pipelineId` поведение байт-в-байт
   прежнее — тест на это.

UI — кокпит сделки (`ProjectStageCockpit`):
2. В строке «N из M · вероятность X%» слева — имя воронки кнопкой-ссылкой
   (`text-meta`, без рамки, `ChevronDown` 12), **только если** у направления сделки больше
   одной deal-воронки и у пользователя есть право двигать стадию (тот же признак, что делает
   кокпит `locked`/интерактивным). Иначе — имя текстом или ничего, как сейчас.
3. Клик → компактный диалог (существующий примитив подтверждения/поповера проекта — найти
   разведкой, нового не заводить): «Перевести в воронку» + выбор целевой воронки (если их
   больше двух) + строка «Стадия: Материалы → Материалы» (через `mapStageToPipeline`) +
   кнопки «Перевести» / «Отмена».
4. «Перевести» → `commitTransition({ stageId, pipelineId, … })`. Ошибка гейта —
   существующим `parseStageGateError` (тост с подсказкой требования). Успех — тост
   «Сделка переведена в «IIoT Эксперимент»».
5. Закрытая сделка (won/lost) — кнопки нет: переводить закрытые незачем.

## ТЕСТЫ

`tests/unit/pipeline-choice.test.ts` — поведением:
- `dealPipelinesFor`: default первым; delivery-воронки и чужое направление отброшены;
- `resolveActivePipeline`: валидный id → он; id чужого направления / delivery / несуществующий
  → default; нет default → первая; пустой список → `null`;
- `mapStageToPipeline`: совпадение по имени без учёта регистра/пробелов; нет совпадения →
  минимальный `order_index` среди рабочих; won → won, lost → lost; `current = null` → первая
  рабочая; цель без рабочих стадий → `null`.

`stage-transition` (найти существующий тест-файл): с `pipelineId` патч содержит
`pipeline_id` и `stage_id` одним объектом; без `pipelineId` — патч равен прежнему.

UI — без юнит-тестов: разметка и связки.
