# Claude Code Prompt — S-FIX-VOICE-1: вычитка не должна ронять расшифровку

Первый боевой прогон S-R3-VOICE-1 на живых файлах (39 мин / 22 МБ и 1:07 / 43 МБ).
Распознавание отработало полностью — 37 фрагментов по 2–5 секунд каждый. **Упала
вычитка, и вместе с ней сгорела вся работа Groq.**

**Ветка:** `fix/voice-followups` от свежего `main`.

## Доказательство из Network (не пересказ, цифры из вкладки)

| Запрос | Статус | Размер | Время |
|---|---|---|---|
| `transcribe` × 37 (Groq) | 200 | 1.5–2.1 kB | 2–5 с каждый |
| `transcribe` (cleanup, блок 1) | 200 | 2.0 kB | **1.5 мин** |
| `transcribe` (cleanup, блок 2) | **502** | 0.8 kB | **1.5 мин** |

Блок вычитки — `BLOCK_CHARS = 5000` символов. Claude возвращает **тот же текст
целиком** (пунктуация + метки говорящих), это 3–4 тысячи выходных токенов. Стриминга
нет: функция молчит до полного ответа, шлюз Supabase рвёт соединение примерно на
90 секундах. Первый блок прошёл впритык, второй — нет.

`CLAUDE_TIMEOUT_MS = 110_000` здесь ни при чём: 502 приходит от шлюза раньше, чем
сработал бы наш `AbortSignal`.

**Жёсткие рамки:**
- Миграций нет. `supabase/migrations/` не трогать вовсе.
- `src/types/database.ts` / `supabase.gen.ts` не трогать.
- Контракт edge-функции (два действия по Content-Type) не менять.
- Зеркала `glossary.ts` / `cleanup-prompt.ts` обязаны остаться байт в байт —
  `tests/unit/transcribe-mirror.test.ts` это проверяет. Правишь одну копию — правь вторую.
- Никаких hardcoded-цветов.

## ЗАДАЧА 1: сырой текст не теряется НИКОГДА

Главная задача спринта. Всё остальное — профилактика, это — спасение уже потраченных
денег и времени.

`src/lib/hooks/use-transcribe.ts`:

1. Распознавание завершилось ⇒ `rawText` **зафиксирован**. Любой сбой на этапе вычитки
   больше не отменяет прогон: `run()` возвращает `rawText`, а не `null`.
2. Ввести в `TranscribePhase` состояние **частичного успеха**:
   ```ts
   | { name: 'partial'; message: string }   // распознано, вычитка не удалась
   ```
   В нём `raw` доступен, `clean` пуст или неполон.
3. Блок вычитки упал — **не прерывать цикл целиком**. Уже вычитанные блоки сохраняются,
   для упавшего в результат подставляется его СЫРОЙ текст (лучше кусок без пунктуации,
   чем дыра), прогон продолжается со следующего блока. В конце — `partial`, если хоть
   один блок не вычитан.
4. `raw` и `clean` не сбрасывать в начале `run()`, если предыдущий прогон закончился
   `partial` и файл тот же — иначе повтор вычитки заново погонит Groq.

⚠️ Инвариант, который нельзя нарушить: **ни один сбой после успешного распознавания не
должен приводить к пустому результату.** Если это условие не выполняется хотя бы в одной
ветке — задача не сделана.

## ЗАДАЧА 2: блок вычитки должен укладываться в лимит шлюза

`BLOCK_CHARS = 5000` даёт ~90 секунд на запрос — это ровно граница, за которой 502.
Нужен запас минимум втрое.

1. `src/lib/transcribe/cleanup-prompt.ts` **и его зеркало**: `BLOCK_CHARS` → **1800**.
   Комментарий обязан содержать факт, а не предположение:
   ```ts
   // 1800, а не 5000: на 5000 ответ Claude занимал ~90 секунд, и шлюз Supabase рвал
   // соединение с 502 (боевой прогон 2026-08-07, файл 1:07:44 — блок 1 прошёл впритык,
   // блок 2 упал). Вычитка возвращает ТОТ ЖЕ текст целиком, поэтому выходных токенов
   // примерно столько же, сколько входных, и время ответа линейно по размеру блока.
   ```
2. `supabase/functions/transcribe/index.ts`: `CLEANUP_MAX_TOKENS` → **3000**
   (потолок под блок 1800 символов с запасом на разметку говорящих).
3. `CLAUDE_TIMEOUT_MS` → **75_000**: наш таймаут обязан срабатывать РАНЬШЕ шлюзового,
   иначе пользователь получает 502 без внятного текста вместо нашей ошибки.

⚠️ Блоков станет втрое больше (часовой разговор — примерно 25 вместо 9). Это ожидаемо:
25 быстрых запросов надёжнее 9 на грани обрыва. Прогресс уже показывает «блок N из M».

## ЗАДАЧА 3: повтор на обрыве

`use-transcribe.ts`, вызов cleanup: **один retry** на 502/504/сетевой сбой, с паузой
2 секунды. Groq-ветка retry уже имеет на своей стороне (в edge), здесь нужен клиентский —
502 приходит от шлюза, до кода функции запрос не доходит.

Retry только на обрыв связи. На 400/422 (наша валидация) повтор бессмыслен — сразу в ошибку.

## ЗАДАЧА 5: галлюцинации Whisper на тишине

На боевом файле первые фрагменты дали **«Продолжение следует… Продолжение следует…»**
шесть раз подряд. Это известный артефакт `whisper-large-v3`: модель обучена на
субтитрах и на тишине выдаёт субтитровые штампы.

Механизм самоусиления: мусор попадает в `parts`, `previousTail` собирается из `parts`,
уходит в `prompt` следующего фрагмента — и Whisper охотно продолжает начатое.

`src/lib/hooks/use-transcribe.ts` (или отдельный чистый модуль в `src/lib/transcribe/`):

1. Список штампов-галлюцинаций, вычищаемый из результата **каждого** фрагмента:
   «Продолжение следует», «Субтитры сделал», «Субтитры создавал», «Редактор субтитров»,
   «Спасибо за просмотр», «Подписывайтесь на канал», «ПОДПИШИСЬ». Сверять
   регистронезависимо, убирать вместе с завершающим многоточием/точкой.
2. **`previousTail` собирать из уже очищенного текста** — это важнее пункта 1: без него
   фильтр чистит вывод, но не разрывает петлю.
3. Фрагмент, от которого после чистки не осталось ничего, в `parts` не добавлять вовсе.

Чистая функция ⇒ покрыть тестами (Задача 7).

## ЗАДАЧА 6: тихие фрагменты не отправлять

`src/lib/transcribe/audio.ts`. Фрагмент, у которого средняя энергия ниже порога, —
это пауза: Groq на нём и галлюцинирует. Не отправлять его вовсе.

1. В `prepareChunks` считать среднюю амплитуду каждого фрагмента (данные уже под рукой,
   второй проход по массиву не нужен — считать в том же цикле, где режутся чанки).
2. Порог вынести константой с комментарием, что число подобрано эмпирически и уточняется
   по боевым файлам.
3. Тихие фрагменты **исключать из списка**, но не ломать нумерацию прогресса: «фрагмент
   N из M» должен считать отправляемые, а не все нарезанные.

⚠️ Осторожно с порогом: тихий, но осмысленный фрагмент (говорят далеко от микрофона)
терять нельзя. Лучше пропустить меньше, чем съесть реплику. При сомнении — не отбрасывать.

## ЗАДАЧА 7: порог прямой отправки

`DIRECT_UPLOAD_LIMIT` = `MAX_CHUNK_BYTES` = 20 МБ — одна константа на два разных смысла
(долг гейта S-R3-VOICE-1, F-01). Файл легче 20 МБ уходит целиком, без нарезки, а значит
и без `previousTail` между фрагментами — теряется контекст, который держит термины.

Развести: `DIRECT_UPLOAD_LIMIT` → **8_000_000** (примерно 8–15 минут сжатого аудио),
`MAX_CHUNK_BYTES` оставить как потолок одного запроса. Комментарий: WAV-фрагмент на
120 секунд весит около 3.8 МБ независимо от исходного формата, поэтому потолок 20 МБ
на размер фрагмента влияет только как страховка.
