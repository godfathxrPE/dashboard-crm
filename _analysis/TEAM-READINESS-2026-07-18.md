- **2 подтверждённых юзера, 2 профиля, 1 membership.** `god4azer@gmail.com` (создан/подтверждён 07-14) — **без membership**, инвайт god4azer/manager в org f063c8ea **PENDING**.

При OTP/magic-link на INSERT `email_confirmed_at` = NULL → гард `p_email_confirmed` (добавлен в W1-040) возвращает 0 → membership не создаётся. Подтверждение приходит на UPDATE, где триггера нет. Инвайт не подхватывается никогда. Документировано самим автором в `040:66-84` (TODO: RPC accept_invitation + /invite).

**Немедленный хотфикс (независим от спринтов):** застрявшего god4azer можно расстопорить сейчас — `apply_pending_invites(<uuid>, 'god4azer@gmail.com', true)` (email уже подтверждён → гард пройдёт, membership создастся, инвайт пометится accepted). Это исполнение уже сделанного инвайта владельца, не новое решение.

## Аудит по осям (severity = «блокирует ли завод команды»)

### 1. Инвайт/онбординг — BLOCKER
Есть: таблица `invitations` (TTL 14д, токен в схеме уже есть — `baseline:1603`), RLS owner/admin, форма/список/отзыв (TeamSection), матчинг по lower(email), «пустая org не создаётся» (handle_new_user не бутстрапит org — корректно). Сломано: приём инвайта (см. live-факт). Нет: `accept_invitation` RPC, страницы `/invite`, доставки письма (S30 — ссылку копируют руками, `TeamSection.tsx:161`). Вторичное: матчинг строго по email (алиас/опечатка → тихий промах), TTL молча роняет инвайт.

### 2. Роли/enforcement — write крепко, UI рассинхронен (MEDIUM)
RLS INSERT требует owner/admin/manager на contacts/companies/calls/meetings/projects/tasks/activities; UPDATE/DELETE — owner/admin ∨ владелец записи; W1 закрыл write-сторону (WITH CHECK org_id + freeze). RLS нигде не слабее UI на контенте. Дыры:
- `useOrgRole`-гейт есть на задачах/сделках (`KanbanBoard:51`, `PipelineBoard:334`, `ProjectBoard:204`, `ProjectDetail:146`), но **НЕТ** на Компаниях/Контактах/Звонках/Лидах/Встречах → viewer видит create-кнопки, жмёт → сырой 42501. UX-дыра под роль viewer, которую реально раздают.
- `TeamSection.tsx:94-104`: кнопка удаления члена без проверки роли строки → **admin видит «корзину» на owner**. RLS `membership_delete`/`membership_update` пускает admin на не-последнего owner; `protect_last_owner` спасает только край. Риск «админ выкинул/разжаловал владельца».
- `leads_insert_own` (`baseline:3445`) — без роль-чека (viewer может создать лид). Рассинхрон.

### 3. Назначение + уведомления — есть каркас, дыры по краям (MEDIUM)
Есть: `AssigneeSelect` на задачах/сделках/компаниях/контактах; `notify_task_assigned`/`notify_project_assigned` (S26, только при реальной смене, не себе); `notify_deal_won` (045); realtime-колокольчик (NotificationBell). Дыры:
- **Тоста нет** — назначение обновляет только бейдж; при открытой вкладке легко пропустить (sonner в проекте есть, к нотификациям не подключён).
- Звонки/встречи/лиды — без поля ответственного (только created_by). «Чей звонок» не назначить.
- Смена owner компании/контакта и смена стадии (кроме won) — не уведомляют.

### 4. Атрибуция «кто что сделал» — пишется, не показывается (HIGH)
`created_by` DEFAULT auth.uid() на всех таблицах; `activity_log.user_id` (актор) пишется на всех событиях. Но: `TimelineEvent` не имеет поля актора (`types/timeline.ts:12-30`), адаптеры не выбирают user_id, лента рендерит только «что»+время — **ни имени, ни аватара автора**. `created_by` не отрисован ни в одной карточке. Смена стадии логируется обезличенно `project_updated {fields_changed:['stage_id']}` без from→to и без показа актора (красивый `log_stage_change` висит на мёртвой legacy-`stage`). Для команды «кто вёл сделку / звонил / двигал воронку» — не видно. Прямой пробел совместной работы.

### 5. Первый вход коллеги — BLOCKER (связан с осью 1)
Нет обработки «залогинен, но нет org»: middleware/callback/layout проверяют только наличие user; при `current_org_id()=NULL` все SELECT пусты (без ошибок), запись падает. Приглашённый видит пустой дашборд без подсказки. Онбординга нет вовсе (grep welcome/tour/onboarding пуст); `EmptyState` с CTA существует, но нигде не подключён. Настройки/тема — localStorage без user-скоупа (`saved-views`, `dashboard-theme`, `focus-*`), не чистятся при логауте; таблица `user_settings` существует, но приложением не используется (мёртвая инфра). Два юзера в одном браузере → общие виды/тема.

## S30 — доставка+приём инвайта, варианты
Цель: коллега по ссылке гарантированно получает membership в нужной org с нужной ролью. Чинить оба разрыва (сейчас сломан именно приём).
- **A. Supabase `auth.admin.inviteUserByEmail`** (edge на service_role): нативная доставка письмом GoTrue, юзер приходит подтверждённым. Минус: завязка на шаблоны GoTrue + нужен SMTP в Supabase; применение membership всё равно переписать (по metadata/подтверждению).
- **B. Resend/SMTP edge-функция** шлёт ссылку: брендированное письмо, независимо от GoTrue. **Сам по себе НЕ чинит приём** — только доставка. B без приёма — ловушка.
- **C. Токен-flow: `accept_invitation(token)` RPC + `/invite?token=`** (уже в TODO 040): коллега логинится обычным OTP → `/invite` зовёт `accept_invitation` (DEFINER: валидирует токен+TTL, вставляет membership для auth.uid(), помечает accepted). **Чинит корневую причину** — приём отвязан от тайминга подтверждения; токен-биндинг закрывает «ввели не тот email». Минус: RPC+страница+guard, доставку добавлять отдельно.

Рекомендация: **C (приём) + B (доставка)**. Но приём (C) самодостаточен: с ним онбординг работает по ссылке, скопированной руками, — **ноль внешних зависимостей**, заводить команду можно в день выката. Доставка (B/A) — additive поверх.

## План (последовательность)

### Sprint T1a — Приём инвайта (BLOCKER, без внешних зависимостей) ← СТАРТ
`accept_invitation(token)` RPC (DEFINER, hardened; валидация токен+TTL+email, идемпотентность, `accepted_at`) + страница `/invite?token=` (после сессии зовёт RPC, редиректит в `/`) + **org-less guard** (при `current_org_id()=NULL` → `/invite` / экран «вас ещё не добавили», а не пустой дашборд). Owner копирует токен-ссылку из TeamSection (уже есть UI, поменять формат ссылки на `?token=`). Закрывает must #1 + #2. После выката — расстопорить god4azer этим же путём (или хотфиксом выше).

### Sprint T1b — Автодоставка письма (additive)
Edge-функция (Resend, вариант B) шлёт `/invite?token=` при создании инвайта. Требует решения по инфре: Resend-аккаунт+API-ключ в secrets, либо вариант A на Supabase SMTP. Не блокирует онбординг (T1a уже позволяет ручную ссылку).

### Sprint T2 — Корректность совместной работы (HIGH)
(1) Актор в ленте: резолв `activity_log.user_id`→имя в `EntityTimeline`/глобальной ленте/карточках; логировать смену стадии с actor+from→to (заменить обезличенный project_updated). (2) Довести роль-гейт UI на Компании/Контакты/Звонки/Лиды/Встречи. (3) Закрыть «admin трогает owner»: UI-условие в MemberRow + сузить RLS `membership_delete`/`membership_update` (owner трогает только owner). Закрывает must #3 + #4.

### Later (заведёт и без этого; сразу после запуска)
Тосты на назначение (sonner ↔ realtime); уведомления на смену owner/стадии; ответственный для звонков/встреч; per-user настройки (`saved-views`/тема → `user_settings` или user-скоуп localStorage + чистка при логауте); онбординг-CTA (подключить `EmptyState`, welcome); мелочи (leads роль-чек, TTL-фидбек, само-исключение notify_deal_won).
