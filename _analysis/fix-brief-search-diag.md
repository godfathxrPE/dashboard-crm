# Claude Code Prompt — S-LLM-SEARCH-2: почему бриф вернул ноль источников

Первый боевой прогон брифа через OpenRouter — **регресс, замаскированный под успех.**

| | было (4–6 авг, Anthropic) | стало (18–19 авг, OpenRouter) |
|---|---|---|
| Входные токены | 77 000 – 80 000 | 4 800 – 10 100 |
| `meta.searches` | 5 | поля нет |
| **`sources` в результате** | **11–12** | **0** |
| Время | 42–49 с | 7–12 с |

Ноль источников при входе в 8–16 раз меньше прежнего означает одно: **результатов поиска
в контексте не было**. Модель, не получив данных, сочинила объяснение — «по запросам не
обнаружено официального сайта». Прогон при этом помечен `done`, и на экране это выглядит
как содержательный ответ. Продавец пойдёт на звонок с брифом «компании нет в открытых
источниках», хотя её просто не искали.

Вторая улика из лога 06:03 — та же болезнь с другой стороны:

```
chz_signals: ожидался "array", пришёл string
recent_news: ожидался "array", пришёл string
talk_hooks:  ожидался "array", пришёл string
sources:     ожидался "array", пришёл string
summary: разметка «<parameter name=» в значении
```

`<parameter name=` в значении поля — это разметка вызова инструмента, просочившаяся
в текст. Так выглядит модель, которая **имитирует** вызов инструмента вместо нативного.

Тело запроса при этом сформировано верно — я проверил `openRouterTool`: `plugins` лежит
в корне, `tool_choice` форсирован, `provider: { require_parameters: true, data_collection:
'deny' }`. Значит дело не в форме запроса, а в том, кто и как его обслужил.

**Не чини вслепую.** Сначала три пробы, потом решение.

---

## ЗАДАЧА 1 — пробы (диагностика, кода не трогаем)

Ключ OpenRouter возьми из своего окружения — **в файл его не писать, в отчёт не копировать**.

Первым делом — **кто обслужил запрос**. OpenRouter возвращает обслужившего провайдера
в ответе; это самая дешёвая проба и она может закрыть вопрос сразу.

```bash
export OR_KEY='<ключ, не коммитить>'
BODY_BASE='{"model":"anthropic/claude-sonnet-5","max_tokens":1024,
  "messages":[{"role":"user","content":"Найди в вебе: ООО МУКОМОЛ ИНН 7116512956. Что за компания?"}]}'
```

**Проба A — плагин без форса инструмента.** Работает ли поиск сам по себе:

```bash
curl -s https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OR_KEY" -H 'content-type: application/json' \
  -d "$(echo "$BODY_BASE" | jq '. + {plugins:[{id:"web",max_results:5}]}')" \
  | jq '{provider, model, has_annotations: (.choices[0].message.annotations|length),
         finish: .choices[0].finish_reason, usage}'
```

Ждём: `has_annotations > 0`. Ноль — плагин не отрабатывает, и это корень.

**Проба B — форс инструмента без плагина.** Работает ли структурированный вывод:

```bash
TOOL='{"type":"function","function":{"name":"submit","description":"Вернуть результат",
  "parameters":{"type":"object","properties":{"sources":{"type":"array","items":{"type":"string"}},
  "summary":{"type":"string"}},"required":["sources","summary"]}}}'

curl -s https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OR_KEY" -H 'content-type: application/json' \
  -d "$(echo "$BODY_BASE" | jq --argjson t "$TOOL" '. + {tools:[$t],
      tool_choice:{type:"function",function:{name:"submit"}},
      provider:{require_parameters:true,data_collection:"deny"}}')" \
  | jq '{provider, has_tool_calls: (.choices[0].message.tool_calls|length),
         args: (.choices[0].message.tool_calls[0].function.arguments // .choices[0].message.content)}'
```

Ждём нативный `tool_calls` с валидным JSON. Если в `args` окажется `<parameter name=` —
форс не работает у обслужившего провайдера.

**Проба C — оба вместе, и то же самое без `require_parameters`.** Два запуска подряд:

```bash
# C1: как в проде
... plugins + tools + tool_choice + provider:{require_parameters:true,data_collection:"deny"}
# C2: то же, но provider убран целиком
```

Ждём: если C1 даёт ноль аннотаций, а C2 — нормальные, значит `require_parameters` (или
`data_collection: deny`) отсекает провайдеров, умеющих и то и другое.

**В отчёт по каждой пробе:** поле `provider` из ответа, число аннотаций, есть ли нативный
`tool_calls`, `usage`. Ключ не приводить.

## ЗАДАЧА 2 — наблюдаемость (делать в любом случае)

Причина найдётся или нет, но **этот класс отказов не должен снова оказаться невидимым.**
Успешный ответ сейчас не логируется вообще, поэтому мы и не знаем, кто отвечал.

1. В `openRouterTool` после разбора ответа — одна строка в `console.log` (не error):
   обслуживший провайдер, слаг модели из ответа, число аннотаций, `finish_reason`.
   Без тел, без ключей, без пользовательских данных.
2. При 422 (`shape`) — логировать **первые 300 символов сырых аргументов** инструмента.
   Сегодня мы видим только «пришёл string», а что именно пришло — нет. Персональных
   данных в аргументах брифа нет, это публичная справка о юрлице; но обрежь длину.

## ЗАДАЧА 3 — «Готово» с нулём источников не бывает

Независимо от причины поиска: у пресета с `webSearch: true` пустой `sources` — **провал,
а не результат**. Сейчас такой прогон уходит в `done` и выглядит достоверно.

Заведи проверку там же, где живёт валидация формы: `webSearch: true` и `sources` пуст ⇒
прогон в `error` с классом `shape` и текстом вроде «Поиск не дал ни одного источника —
результат неполный». Кнопку «Повторить» оставить: это как раз повторяемый случай.

⚠️ Разведай, не сломает ли это легитимный сценарий «искали, но действительно ничего нет».
Если такой прогон возможен и полезен — тогда нужен не `error`, а явная отметка в карточке
(«источников не найдено»), но **не молчаливое `done` с пустым списком**. Реши по коду и
объясни выбор в отчёте.

## Чего НЕ делать

- Не подбирать модель наугад и не менять слаг: сначала пробы. Смена модели без диагноза
  превратит один неизвестный отказ в два.
- Не выключать `require_parameters` «на всякий случай» до пробы C — он стоит там ради
  ровно этой болезни, и снимать его вслепую значит менять один тихий сбой на другой.
- Не трогать Anthropic-ветку: она рабочая, просто оплачена не будет.
