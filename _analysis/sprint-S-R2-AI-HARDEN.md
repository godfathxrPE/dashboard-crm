## Часть A — инъекционный смоук (первая по порядку, кода может не потребовать)

### A1. Тест-кейсы

Прогоняются **после** 085 и деплоя edge, руками из UI, результат — в отчёт.

| # | Пресет | Вход | Ожидание |
|---|---|---|---|
| 1 | `analytic_note` | звонок «Толедо» (`fabc40bd-…`), инъекция в `agreements` | системный промпт не в `ai_runs.result`; поля записки — по существу разговора |
| 2 | `deal_progression` | тот же звонок (после 085 — без транскрипта) | `summary` не содержит текста системного промпта; `fields.next_step` не содержит инструкций из заметки |

**Критерий провала — любое из:** в `ai_runs.result` появился фрагмент `ANTI_INJECTION` или

### A2. Тестовый транскрипт с инъекцией

Прод трогать минимально: завести транскрипт на **тестовом** звонке, не на клиентском.
Взять реальный транскрипт (3240 символов) и вклеить в середину блок «Толедо» дословно —
инъекция в середине опаснее, чем в конце, потому что не выглядит как хвост.

Заводится через UI («вставить транскрипт»), не SQL. После смоука — удалить.

### A3. Если смоук красный

Тогда и только тогда — усиление. Порядок дешевизны:

1. Обрамление недоверенного текста: сейчас `dataBlock` склеивает `key: value` без экранирования
   — вход, содержащий `</data>`, закрывает блок досрочно. Проверить и, если воспроизводится,
   вырезать `<`/`>` из значений либо перейти на разделитель, которого нет в тексте.
2. Отдельный `user`-ход с транскриптом вместо склейки в один — модель хуже путает роли.
3. Пост-фильтр на `result`: если в тексте найдены маркеры системного промпта — run падает
   в `error`, а не отдаётся в UI.

Не строить ничего из этого «на всякий случай». Красный смоук — условие.

## Часть B — миграция 085: `transcript_id` nullable

### Почему

`ai_runs.transcript_id uuid NOT NULL → transcripts`. Следствия:

- прогон по звонку без транскрипта невозможен → инъекционный смоук на «Толедо» невозможен;
- `meeting_prep` (часть C) по определению не имеет транскрипта — это бриф **перед** встречей.
  Без 085 он либо не запишется в журнал, либо потребует фиктивного транскрипта.

### Миграция

```sql
-- 085: ai_runs.transcript_id → nullable + CHECK обязательности по пресету
--      (S-R2-AI-HARDEN, R2-P1).
--
-- ⚠️ ОБРАТИМОСТЬ: вернуть NOT NULL можно только после удаления строк с NULL:
--      delete from public.ai_runs where transcript_id is null;
--      alter table public.ai_runs alter column transcript_id set not null;
--      alter table public.ai_runs drop constraint ai_runs_transcript_required;
--
-- Почему CHECK, а не «просто nullable»: транскрипт обязателен там, где пресет без него
-- бессмыслен (протокол встречи, SPIN-разбор). Снять NOT NULL без замены = разрешить
-- мусорный прогон «протокол по пустоте». CHECK держит это в БД, а не в вере в клиента.

alter table public.ai_runs alter column transcript_id drop not null;

alter table public.ai_runs add constraint ai_runs_transcript_required
  check (
    transcript_id is not null
    or preset_key in ('deal_progression', 'analytic_note', 'meeting_prep', 'deal_summary')
  );

comment on column public.ai_runs.transcript_id is
  'Транскрипт-источник прогона. NULL допустим для пресетов, работающих по полям сущности '
  '(deal_progression, analytic_note, meeting_prep, deal_summary) — 085. Для '
  'meeting_protocol и spin_review обязателен: CHECK ai_runs_transcript_required.';
```

> **CC: список пресетов в CHECK обязан совпадать с `PRESETS` в edge.** Расширяешь реестр —
> правь CHECK отдельной миграцией. Это третье место после `PRESETS` и `ALLOWED_BY_ENTITY`
> (index.ts:543) — зафиксировать в комментарии edge-файла.

### ⚠️ Это смена решения P0, а не недосмотр

В `S-R2-SDP-1` было принято: «SDP доступен только при наличии транскрипта, предложение по
трём строкам заметок всё равно бесполезно». Здесь решение меняется — и надо понимать, на что.

Аргумент за смену: заметки звонка в этом проекте **не** три строки (у «Толедо» —
структурированный текст с контактами и договорённостями), а без прогона по полям сущности
инъекционный смоук на реальном векторе невозможен вообще. Плюс `meeting_prep` по определению
не имеет транскрипта.

Аргумент против остаётся в силе: по пустым заметкам предложение будет мусорным. Поэтому в
UI кнопка SDP при пустых и `agreements`, и `next_step`, и `notes` — **disabled** с подсказкой.
Ограничение переезжает из схемы в UI, а не исчезает.

### Edge под 085 — четыре правки, а не одна

Разведка показала, что «сделать `transcript_id` опциональным» затрагивает входной контракт
функции. Ни один из этих пунктов не опциональный.

**B1. `entity_id` больше неоткуда взять.** Сейчас `index.ts:538`:

```ts
const entityId = transcript.entity_id as string;
```

Без транскрипта источника нет, а `ai_runs.entity_id` — NOT NULL. Значит контракт запроса
меняется:

```
{ preset_key, transcript_id }                    // как сейчас — entity берётся из транскрипта
{ preset_key, entity_type, entity_id }           // новый путь — транскрипта нет
```

Взаимоисключающе: пришло и то, и другое → 400. Пришло ни того, ни другого → 400.
`entity_type` из запроса **валидировать по whitelist**, не доверять телу.

**B2. `ai_runs_entity_type_check` разрешает только `('call','meeting')`.**
Проверено по `pg_constraint`. Если `meeting_prep` вешается на сделку, `entity_type='project'`
упадёт на CHECK.

Решение спринта: **`meeting_prep` и `deal_summary` привязываются к сделке**, значит 085
расширяет и этот CHECK до `('call','meeting','project')`. Альтернатива — вешать бриф на
встречу — хуже: бриф готовится, когда встречи в CRM ещё нет.

```sql
alter table public.ai_runs drop constraint ai_runs_entity_type_check;
alter table public.ai_runs add constraint ai_runs_entity_type_check
  check (entity_type in ('call','meeting','project'));
```

Откат — обратное сужение, возможное только после удаления строк с `'project'`.

**B3. `ON DELETE CASCADE` на `transcript_id` становится неправильным.** Сегодня удаление
транскрипта сносит прогоны — логично, пока прогон без транскрипта немыслим. После 085
журнал прогонов переживает свой источник, и каскад начинает молча уничтожать историю.

```sql
alter table public.ai_runs drop constraint ai_runs_transcript_id_fkey;
alter table public.ai_runs add constraint ai_runs_transcript_id_fkey
  foreign key (transcript_id) references public.transcripts(id) on delete set null;
```

⚠️ Взаимодействие с CHECK из B: если удаление транскрипта обнулит `transcript_id` у прогона
`meeting_protocol`, CHECK `ai_runs_transcript_required` будет нарушен и **DELETE
транскрипта упадёт**. Это не теория — это первый же случай удаления. Развязка: CHECK
проверяет обязательность **на момент вставки**, а не всегда. Простейший рабочий вариант —
исключить из CHECK строки, где `status = 'done'` уже проставлен, либо (чище) перенести
проверку в edge и оставить в БД только nullable. **Решить явно и обосновать в отчёте** —
это самое тонкое место спринта.

Вариант по умолчанию, если сомнения: **оставить `ON DELETE CASCADE`** и не трогать FK.
Потеря истории при удалении транскрипта — существующее поведение, а не регрессия, и оно
не мешает задачам спринта. B3 тогда выпадает целиком, вместе с конфликтом CHECK.

**B4. Поиск существующего прогона сломается на NULL.** `index.ts:574` и `:600`:

```ts
.eq('transcript_id', transcriptId)
.eq('transcript_id', transcriptId).eq('preset_key', presetKey)
```

`eq` по NULL в PostgREST не находит ничего (`NULL = NULL` — не true). Дедупликация и
подтягивание последнего прогона для безтранскриптных пресетов молча перестанут работать:
каждый клик будет плодить новый прогон.

Правка: ветка поиска по `(entity_type, entity_id, preset_key)`, когда транскрипта нет.
Ключ поиска выбирается тем же признаком, что и путь в B1.

**B5. Пресет требует транскрипт, а его нет** → **400** с внятным текстом, не 500 и не
падение на CHECK.

Валидация «пресет ↔ обязательность транскрипта» живёт в edge **и** в CHECK. Дублирование
осознанное: edge даёт человеку сообщение, CHECK не даёт записать мусор мимо edge.

## Часть D — хвосты SDP

### D1. 🔴 6 задач роняют предложение целиком

`progressionProposalSchema.tasks` — `.max(PROGRESSION_MAX_TASKS)` без `.catch`, поэтому
`safeParse` падает и `parseProposal` возвращает `null`. Пользователь видит «модель вернула
некорректный ответ» вместо пяти нормальных задач.

Фикс — усечение вместо отказа:

```ts
tasks: z
  .array(taskSchema.nullable().catch(null))
  .default([])
  .transform((xs) => xs.filter((t): t is z.infer<typeof taskSchema> => t !== null))
  .transform((xs) => xs.slice(0, PROGRESSION_MAX_TASKS)),
```

и в `ParsedProposal` — новое поле `truncatedTasks: number` (сколько отброшено сверх лимита),
показать в панели строкой «модель вернула N задач, показаны первые 5». Молча резать нельзя —
это то же враньё, что и молчаливый отказ, только в другую сторону.

⚠️ `droppedTasks` считается как `rawTaskCount - parsed.data.tasks.length` и после этой правки
начнёт включать усечённые. Развести: `droppedTasks` — только невалидные, `truncatedTasks` —
только сверхлимитные.

### D2. `due_in_days: 0` даёт просроченную задачу

Сейчас дедлайн = момент клика с миллисекундами, и через секунду задача просрочена. Должно
быть **концом дня по MSK**: календарные вычисления в проекте идут через `mskDateKey`
(грабля off-by-one на границах суток/DST — см. CLAUDE.md). Взять существующий хелпер, не
писать свой.

Проверить заодно `due_in_days: 1..N` — там та же арифметика.

### D3. Чекбоксы после применения

После успешного применения чекбоксы остаются кликабельными вхолостую. `isApplied` в панели
уже есть (строка 87) и используется на части контролов — довести до всех.

### D4. `activity_log`: `task_created` для AI-задач

Сейчас пишется только агрегированное `ai_progression_applied`. Проверить, намеренно ли:
если задачи, созданные вручную, дают `task_created`, а созданные из предложения — нет, то
таймлайн проекта врёт. Решение — в отчёт с обоснованием, а не молча.

### D5. Кнопка «Применить выбранное» — сначала воспроизвести

Хвост P0 утверждает, что при непривязанной сделке кнопка серая, но кликается.
`AiProgressionPanel.tsx:348` показывает настоящий `disabled`. **Сначала воспроизвести на
живом UI**, и только если баг есть — чинить. Если не воспроизводится — так и написать в
отчёте, хвост закрыть.
