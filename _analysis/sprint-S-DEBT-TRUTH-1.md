## ЗАДАЧА 3 — `.in()` перестаёт быть миной на длинных списках

PostgREST передаёт фильтр `.in()` в query string. Список из тысячи uuid'ов — это ~36 КБ
URL, и запрос упирается в лимит длины (413/414 в зависимости от прокси). В проекте уже
записана грабля про **пустой** `.in()` (W3 из 068) — про длинный нет.

Сейчас максимум **3 сообщения на канал** (сверено), поэтому это не баг, а мина: сработает
ровно тогда, когда чатом начнут пользоваться, и проявится как «удаление группы молча не
чистит вложения» либо как упавший запрос ленты.

**3.1.** `src/lib/hooks/use-message-attachments.ts`, `collectConversationAttachmentPaths` —
резать `messageIds` на батчи и склеивать результат:

```ts
const IN_BATCH = 200; // ~7 КБ query string на батч — с запасом под лимит URL
```

Цикл по батчам, ошибку каждого батча глотать (функция и сейчас не бросает — поведение
сохранить), результаты конкатенировать.

**3.2.** Проверить по разведке п.4 остальные `.in()` в хуках. Там, где список приходит из
ленты сообщений (`useMessageAttachments`, `useTasksBySourceMessages`), — тот же батчинг.
Там, где список заведомо короткий (выбор пользователя в UI, единицы элементов), — не
трогать, но пометить одной строкой комментария, почему батчинг не нужен.

**3.3.** Вынести константу и хелпер в одно место, чтобы не расползлось третьей копией.

## ЗАДАЧА 4 — ключи кэша включают то, от чего зависит запрос

`src/lib/hooks/use-message-attachments.ts:60-68` и `use-tasks-by-message.ts:53-60`:
результат запроса зависит от `messageIds`, а `queryKey` — нет
(`['message_attachments', conversationId]`).

**Как ломается.** Входящее сообщение с вложением приходит двумя событиями двух разных
realtime-таблиц (`messages` и `message_attachments`), у каждой свой 150-мс дебаунс
(`use-realtime.ts:46-49`). Порядок не гарантирован. Если инвалидация вложений отработает
раньше, чем дорефетчится лента, запрос уйдёт со **старым** `messageIds` (без нового
сообщения) и вернёт пусто. Когда лента дообновится и `messageIds` вырастет, ключ не
изменится — второго запроса не будет.

Пользователь видит: коллега прислал скриншот без текста (097 разрешил пустой `body`) —
в ленте пустой прямоугольник до следующего сообщения, смены канала или F5.

**Что сделать.** Добавить в ключ дешёвый производный маркер: `messageIds.length` и
последний id — лента грузится целиком и монотонна, поэтому пары достаточно.

```ts
const attachmentsKey = (conversationId: string, ids: string[]) =>
  ['message_attachments', conversationId, ids.length, ids[ids.length - 1] ?? ''] as const;
```

⚠️ Инвалидация в других хуках идёт **префиксом** `['message_attachments']` /
`['tasks-by-message']` — удлинение ключа её не ломает, но это надо проверить грепом по
`invalidateQueries` и отметить в отчёте. То же для `use-tasks-by-message.ts`.

## ЗАДАЧА 5 — миграция 101: состав группы перестаёт врать

`096_chat_groups.sql:229-243`, политика `conversation_members_insert`: в `with check`
проверяются `org_id`, `kind = 'group'` и права **добавляющего**. `profile_id` добавляемого
не проверяется ничем, кроме FK на `public.profiles`. При этом комментарий 096:60
утверждает, что «инвариант держит INSERT-политика и RPC» — RPC действительно фильтрует
(`join memberships … where m.org_id = v_org`, 096:368-373), а политика нет. Два механизма
реализуют разные правила под одним именем инварианта.

**Что ломается.** Автор группы может положить строку с `profile_id` человека, у которого
нет `memberships` в этой организации. Утечки нет — `is_conversation_member` сначала
сравнивает `org_id` канала с `current_org_id()` читателя. Но состав группы становится
ложью: `useConversationMembers` показывает человека в списке, счётчик «N уч.» его считает,
сообщений он не получит никогда. Обратный порядок опаснее и достижим без консоли: человека
снимают с `memberships`, строки `conversation_members` не чистятся (FK стоит на `profiles`,
не на `memberships`), и группа продолжает показывать его в составе.

**Файл:** `supabase/migrations/101_conversation_members_membership_check.sql` — **номер
взять разведкой п.1**, не из этого текста.

Содержание (шапка в стиле 094/096/100: ЗАЧЕМ → ЧТО ЗДЕСЬ → ⚠️-блоки → Откат):

```sql
drop policy if exists conversation_members_insert on public.conversation_members;
create policy conversation_members_insert on public.conversation_members
  for insert to authenticated
  with check (
    -- … прежние условия из 096 целиком, без изменений …
    and exists (
      select 1 from public.memberships mm
       where mm.org_id = (select public.current_org_id())
         and mm.profile_id = conversation_members.profile_id
    )
  );
```

⚠️ Прежние условия **скопировать из живой политики**, а не из файла 096: тело в БД —
источник истины (`select policyname, with_check from pg_policies where
tablename='conversation_members'`). Грабля записана в learnings: `convert_lead` в репо
ссылался на несуществующие колонки, прод был сломан, поймали только на гейте.

⚠️ В шапке отметить, почему нет рекурсии: подзапрос идёт к `memberships`, а не к
`conversation_members`; политика `memberships_select` на `conversation_members` не
ссылается.

⚠️ **Что НЕ входит:** чистка `conversation_members` при снятии membership (триггер на
`memberships` AFTER DELETE). Это отдельное решение — оно молча удаляет данные, и его надо
обсуждать, а не протаскивать хвостом. Записать строкой в шапку как известный остаток.

⚠️ Миграцию **не применять**. Написать, закоммитить, статус в `docs/schema.md` —
«НЕ ПРИМЕНЕНА, лежит на гейте». Timestamp впишет гейт.
