### Что важно помнить про вебхуки

- **Подпись:** `X-Torii-Signature: t=<unix>,v1=<hex>`, **без пробела после запятой**.
  `hmac_sha256(secret, "<t>.<raw>")`, где `raw` — сырое тело побайтово. В §3.3 арх-дока
  значение отрендерено с пробелом — это проза, источник правды `transport.ts:315-330`.
- **7 попыток**, паузы 1 м / 5 м / 30 м / 2 ч / 6 ч / 24 ч. `3xx` = провал без ретрая
  (редирект трактуется как обход SSRF-проверки). 408/429 и 5xx — ретрай.
- **20 провалов подряд** гасят endpoint + уведомление `webhook_disabled` владельцам;
  порог настраивается через `organizations.settings.webhook_failure_threshold`.
- **`task_overdue` + webhook не поддержан и не «недоделан».** `run_overdue_automations` (051)
  не зовёт `wf_apply_project_action` вовсе и жёстко режет `action_type not in
  ('notify','create_activity')`. Правило «просрочка + вебхук» молча не сработало бы никогда.
  Запрещено в трёх местах: SQL 051, `RuleEditorModal` (`actionOptions` при `isOverdue`),
  Zod `automation-rule.ts`. Событие `task.overdue` требует своего контракта (payload §3.2 —
  снимок сделки, а у просроченной задачи сделки может не быть: `tasks.project_id` nullable).
- **«Повторить» создаёт НОВУЮ строку**, а не оживляет старую: `id` уходит получателю как
  `X-Torii-Delivery` и служит ключом дедупликации, поэтому повтор с тем же id корректный
  приёмник обязан отбросить. `payload.id` переписывается под новый id, `occurred_at`
  НЕ трогается. Повторить можно только `failed`/`dropped` и только в активный endpoint.
- **`cleanup_webhook_deliveries` не удаляет `pending` ни в каком возрасте** — висящая
  строка это симптом, а не мусор.
- **`payload.data` — закрытый whitelist.** Наружу не уходят `pinned_note`, `loss_*`,
  `won_*`, `do_*`, `delivery_kind`, `progress_*`. Новая колонка в `projects` в вебхук сама
  НЕ попадёт — это свойство, а не забывчивость. `budget` — **в копейках**.
- Точка синхронизации SQL↔TS: `public.webhook_event_name(text)` ↔
  `WEBHOOK_EVENT_BY_TRIGGER` в `src/types/database.ts`.

## 3. Грабли этой сессии — не наступать второй раз

1. **`npm run db:gen-types` писал в `src/types/database.ts`** — файл с 736 строками
   рукописных доменных типов, и реген молча уничтожил бы их; при пустом
   `$SUPABASE_PROJECT_ID` писал пустой файл. Исправлено: скрипт целится в
   `src/types/supabase.gen.ts`, project-id с дефолтом. Реген — **только CLI**, MCP
   `generate_typescript_types` не отдаёт `graphql_public` и даёт 28 ложных удалений.
2. **`pg_net` регистрируется в `public`**, если не написать `with schema extensions`.
   Объекты при этом всегда в схеме `net` (`extrelocatable = false`), вызовы — `net.http_post`.
   Перерегистрация после появления зависимостей потянет их за собой — ставить правильно сразу.
3. **`create or replace` с новым параметром = ПЕРЕГРУЗКА, а не замена.** Добавление
   `p_changes` к `wf_apply_project_action` без `drop function` четырёхаргументной версии
   сделало бы все старые вызовы неоднозначными (`42725 function is not unique`) и уронило бы
   движок автоматизаций целиком. Правило: меняешь сигнатуру — `DROP` + перепись всех
   вызывающих в той же миграции.
4. **`::text` на `timestamptz` зависит от session TimeZone/DateStyle.** Везде
   `to_char(… at time zone 'UTC', …)`. Грабля 079/084/088/090; в вебхуках стоила бы подписи.
5. **`docs/TECH-STACK.md` 12 раз утверждал Netlify**, пока `CLAUDE.md` был прав. Ложный факт
   уехал через Explore-агента в арх-док. Править источник, а не производную.
6. **Vercel Hobby: cron не чаще раза в сутки** (100 джоб на проект — это про количество, не
   частоту). Поэтому планировщик очереди живёт в `pg_cron`, а не в Vercel Cron.
7. `node_modules` в примонтированной папке собраны под macOS — из linux-VM Cowork'а
   `npm test` / `vitest` не запускаются (нативные биндинги rolldown). Проверка тестов —
   всегда на стороне CC/пользователя.
8. `window.confirm` в проекте запрещён: блокирует браузерные смоки (грабля GanttTimeline).
   Подтверждения — inline-блоком или через `Modal` с `isDirty`.

## 4. Протокол работы (принят и работает)

**Цикл спринта:** я пишу спринт-файл → кладу в `_analysis/` на машине пользователя и в
проект → пользователь отдаёт его CC одной строкой → CC делает всё, кроме apply/edge/мержа →
я принимаю на гейте.

**Что делает Cowork (я) на гейте:**
- применяю миграции в прод через Supabase MCP;
- при необходимости деплою edge-функции через MCP (разрешено с 2026-07-30);
- прогоняю смоки в проде, включая ролевые (через подмену `request.jwt.claims` в
  `set_config(..., true)` внутри `DO`-блока — так проверяются гейты owner/admin);
- сверяю тела функций с прод-`prosrc` **до** применения, чтобы поймать «попутные улучшения»;
- читаю advisors;
- правлю статусы миграций в `docs/schema.md`;
- убираю за собой все тестовые данные.

**Что НЕ делает Cowork:** `git commit`, `git merge`, `git push` — это руки пользователя.

**Структура ответа на гейте (соблюдать):**
Итог (одна строка: принято / принято с правками / отклонено) → Что проверено (факты с
доказательством: SQL-результат, версия, счётчик) → Находки (🔴/🟡/🟢, каждая: что, чем
грозит, что делать) → Что я поправил → **Твои действия (нумерованный список, только руками,
строго в порядке выполнения — не по важности)** → Дальше.

**Что делает CC:** код, миграции файлами, тесты, VERIFY (`npx tsc --noEmit`, `npm test`,
`npm run lint`, `npm run build` последним при остановленном dev-сервере), отчёт.
Baseline lint — **15 errors / 34 warnings**; «ни одной новой» проверяется через `git stash`.
Тестов на 2026-07-31 — **576**.

**Безопасность (глобальные инструкции пользователя):** `rm -rf`, force push в shared ветки,
`drop table`, миграции на проде — только с явным подтверждением. `.env` и секреты не трогать.
Перед коммитом — краткий diff.
