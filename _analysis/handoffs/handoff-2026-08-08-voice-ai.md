## 1. Память проекта под версионным контролем

**Проблема.** Скилл `crm-architect` жил в трёх несинхронизированных копиях: репо, локальная
`~/.claude/skills/`, аккаунт Claude.ai. Аккаунтная замерла на «миграции 001–075», когда в
проекте было 104 — гейт построил на ней ложный вывод про несуществующий долг.

**Решение.** Источник истины — папка `crm-architect/` в репозитории. `scripts/skill-deploy.sh`
раскатывает её в локальную копию и собирает `crm-architect.skill` для загрузки в аккаунт.
`scripts/skill-verify.sh` ловит расхождение. Направление одно, обратной синхронизации нет
намеренно.

⚠️ **Гейт поймал регресс в самом спринте:** в репо уехала локальная копия, где не было
раздела «Гейт Cowork» — то есть спринт, вводящий единый источник истины, зафиксировал бы
в нём потерю. Раздел вернули отдельным коммитом до мержа.

**Правило теперь в чеклисте `SKILL.md`:** правка памяти → `skill-deploy.sh` → загрузка
пакета в аккаунт. Без последнего шага гейт следующего спринта читает старую версию.

## 2. Ось 1 — полнота записи (S-R3-TRUST-1)

`src/lib/domain/deal-completeness.ts` — единственная формула полноты. Правила
`{key, label, weight, cost}`, где **`cost` — цена пустоты**: что именно не работает без
поля («Проигрыш не попадёт в анализ причин — считать нечего»). Рисуется в поповере бейджа.

- `score = floor(100 × вес заполненных / вес ПРИМЕНИМЫХ)`; применимость по статусу
  (`loss_reason` только у `lost`) и по типу (`stage_id` — только `client`).
- Веса переопределяет org: `organizations.settings.completeness_rules`, `weight 0` = выключено.
- `completeness_score` — **первое вычисляемое поле сегментов** (`VIRTUAL_FIELDS` в
  `segment-eval.ts`), сид-сегмент «Полнота <60%» (миграция 105).
- Полнота **ничего не блокирует**: принуждение осталось в `check_stage_requirements`.

**Отклонение от роадмапа, осознанное:** SQL-функции `entity_completeness()` и view нет.
Сегменты считаются на клиенте, view их не питает; вторая формула в SQL дала бы дрейф.
Появится вместе с серверным потребителем.

⚠️ Сегмент «Полнота <60%» на текущих данных возвращает **ноль строк** — минимальный score
среди открытых сделок 61 %. Это by design (порог означает «плохо», а не «покажи хоть что-то»),
но чип выглядит пустым.

## 3. Голос: транскрибатор → CRM

Исходно расшифровка жила отдельным приложением (`~/Documents/Projects/trans-app`,
Next + Groq Whisper + Claude). В CRM было **3 транскрипта на 15 разговоров**, все `paste`.

### Архитектура

```
браузер: файл / микрофон → декод 16 kHz mono → нарезка по тишине
   ↓ чанк за чанком, supabase.functions.invoke (FormData, JWT)
edge `transcribe` → Groq whisper-large-v3 (+ глоссарий маркировки)
   ↓ склейка → тот же edge, action='cleanup' → Claude
клиент → transcripts(source='audio', storage_path=null)
   ↓
AI Hub — без единой правки
```

**Почему edge, а не Next-роут:** в проекте нет ни одного `src/app/api/*` и ни одного
серверного ключа. Роут завёл бы второй контур секретов (Vercel env рядом с Supabase secrets)
и самодельную авторизацию. Функция **не читает и не пишет ни одной таблицы** — транскрипт
пишет клиент под своими RLS (контур `ai-capture`).

**Аудио не хранится.** `storage_path` остаётся `null` — решение отложено до появления
потребности вернуться к записи.

### Что сломалось на боевых файлах и как починено

| Симптом | Причина | Фикс |
|---|---|---|
| 502 после 37 успешных фрагментов | блок вычитки 5000 символов → ответ Claude ~90 с → шлюз Supabase рвёт | `BLOCK_CHARS` 5000 → **1800**, `max_tokens` → 3000, свой таймаут 110 → **75 с** (раньше шлюзового) |
| Вся работа Groq сгорала при сбое вычитки | `run()` возвращал `null` | инвариант: **после успешного распознавания результат не теряется НИКОГДА**; упавший блок идёт сырым, фаза `partial`, кнопка «Повторить вычитку» без обращения к Groq |
| «Продолжение следует…» ×6 | Whisper на тишине выдаёт субтитровые штампы, мусор уходит в `previousTail` и разгоняет сам себя | фильтр + **`buildTail` собирается из очищенного** — петля рвётся там |
| «Вопросы на сайте www.vk.com» | список штампов не покрывает класс явления | `verbose_json` + фильтр по метрикам сегментов |

### Фильтр галлюцинаций — структурный, не списочный

`response_format=verbose_json` даёт метрики, которые Whisper выставляет собственной выдаче:

- `no_speech_prob > 0.6` **И** `avg_logprob < -1.0` — только в паре (по отдельности режут
  тихую речь и редкую терминологию);
- `compression_ratio > 2.4` — сам по себе (признак повтора).

Порядок пайплайна обязателен: **сегменты → метрики → список штампов → `buildTail`**.

Плюс домен в короткой фразе (≤ 40 символов) и порог тишины ×4, пока не принят ни один
фрагмент (начало записи — оргшум).

⚠️ **Приоритет ошибки везде один: лучше пропустить мусор, чем съесть реплику.**

## 4. Видимость: транскрипт и AI перестали прятаться

**Главная находка сессии по данным:** транскрипт записывался только внутри `useStartRun`,
то есть в момент запуска пресета. Не нажал пресет — расшифровка умирала вместе с состоянием
компонента. На живой БД это выглядело как **4 транскрипта, из них `audio` — один**, при
десятках минут прогонов и почти сотне рублей.

Что сделано:

- upsert транскрипта вынесен из `useStartRun`, им пользуются **двое**: запуск пресета и
  новая `useSaveTranscript`. Сохранение — по факту готовности, включая `partial`;
- бейдж «Расшифровка · N тыс. знаков» в списках звонков и встреч (один запрос на список);
- клик по AI-событию ленты открывает результат (`case 'ai_run'` раньше молча падал в
  `default`); заголовок — человеческое название пресета вместо `AI: analytic_note`;
- **брифы компании появились в её ленте**: `fetchAiRuns` искал прогоны только по звонкам и
  встречам, а `company_brief` привязан к самой компании — семь брифов были невидимы;
- раздел `/transcripts`: список, серверный поиск по тексту, выгрузка в Markdown с шапкой;
- сводный AI-блок на карточке компании (расшифровки + прогоны, оба источника).

Новой сущности в БД **не заводили**: `transcripts` уже полноценная таблица с RLS и историей
версий. Не хватало витрины, а не схемы.

## Инварианты, которые нельзя нарушать

1. **Дорогой этап не отменяется дешёвым.** Распознавание оплачено — сбой вычитки не имеет
   права его обнулить.
2. **Транскрипт сохраняется по готовности, а не по нажатию пресета.**
3. **Правка текста → новая версия, машинная не затирается.** Дублей при этом нет: тот же
   текст той же сущности переиспользует ту же строку.
4. **AI предлагает, человек применяет.** Автозапуска пресета после расшифровки нет.
5. **Edge-функция не пишет в БД.** Пишет клиент под своими RLS.
6. **Зеркала `glossary.ts` / `cleanup-prompt.ts` — байт в байт**, держит
   `tests/unit/transcribe-mirror.test.ts` (львиная доля файла — текст промпта,
   поведенческий тест правку в нём не заметит).
7. **Тост — не место для сообщения, требующего решения.** Ошибка и `partial` живут в панели.

## Уроки — уже в `crm-architect/references/learnings.md`

Четыре блока за сессию: «ось Слой достоверности», «первый боевой прогон расшифровки»,
«расшифровка аудио», «новый раздел = шесть точек правки». Ключевые: лимит 4.5 МБ был
вериселев, а не провайдерский (перенося чужой модуль, опознавай каждую константу — чья
это граница); серверная формула не питает
клиентский фильтр; шлюз Supabase рвёт синхронный вызов примерно на 90 секундах; фильтр по
подстроке выкусывает живую речь — нужны режимы сверки.

**Пробел закрыт в `1fa2ee3`:** новый раздел приложения — **шесть** точек правки, а не пять.
Шестую даёт `CommandPalette`: там две записи, карта заголовков и пункт навигации. Таблица
«что пропустил ⇒ что сломается» — в `learnings.md`, строка чеклиста — в `SKILL.md`. Важное
в таблице: только страница падает шумно (404), остальные пять деградируют молча — пустой
заголовок, чужая пара цветов у орбов, фолбэк секции в `'dashboard'`.

Память раскатана `skill-deploy.sh`, пакет `crm-architect.skill` (71 352 Б) загружен в
Customize → Skills. Все три хранилища сходятся: репо `crm-architect/` — источник,
`~/.claude/skills/crm-architect/` — для Claude Code, аккаунтная копия — для гейта Cowork.
