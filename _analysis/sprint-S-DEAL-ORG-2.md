## ЗАДАЧА 1 — «отклонено» без причины больше невозможно

**Факт.** 131 завела `quotes.rejection_reason`, `ActiveQuoteCard.tsx:121` его пишет при
отклонении. Но `QuoteModal.tsx:143–150` строит селект статуса прямо из `quoteStatuses`
(`validators/quote.ts:10`), где `rejected` есть — то есть статус ставится руками, минуя
поток с причиной. Ограничения в БД нет.

**Проверено на живой базе (гейт 08.09): отклонённых КП на проде НОЛЬ** — CHECK ложится
чисто, бэкфилл не нужен, legacy-строки не падают.

Три части, порядок обязателен внутри одного коммита:

1. Убрать `rejected` из селекта `QuoteModal`. Не из `quoteStatuses` — тип статуса
   остаётся полным, режется только предложение в форме: отклонение это решение с
   причиной, у него есть свой поток в карточке. Отфильтровать при рендере списка,
   рядом — комментарий, почему именно здесь, а не в константе.
2. Миграция: `check (status <> 'rejected' or (rejection_reason is not null and
   btrim(rejection_reason) <> ''))`. Имя — `quotes_rejected_needs_reason`.
   ⚠️ `not valid` НЕ ставить: строк-нарушителей ноль, отложенная валидация только
   спрятала бы будущие.
3. **Выход из `rejected` чистит причину.** `QUOTE_STATUS_TRANSITIONS.rejected =
   ['draft','sent']` (`validators/quote.ts:45`) — переход обратно оставит причину
   висеть на черновике, и она соврёт в следующей версии КП. Там, где ставится новый
   статус из `rejected`, писать `rejection_reason: null` тем же апдейтом.

Порядок в коммите: сначала правка клиента, потом CHECK. Наоборот — и модалка начнёт
ловить `23514` прямо в форме, как это уже было с `leads_decision_role_check` (#70).

## ЗАДАЧА 4 — «сегодня» и «просрочено» одного цвета в `t-washi`

**Замер, не глаз:**

```
.t-washi  --accent: #C23B3B
          --red:    #C23B3B      ← тот же hex
:root     --danger: var(--red)
```

`DealDeadlineTrack.tsx`: `STATE_CHIP.today = 'bg-accent'`, `STATE_CHIP.overdue =
'bg-danger'`. В легенде эти глифы стоят соседями и в washi заливаются одним цветом —
два из трёх состояний неразличимы. Колонка «сегодня» (`bg-accent/20`) там же даёт
розовую полосу под сегодняшним днём, читаемую как просрочка, и свечение точки
`var(--accent-l2)` = `rgba(194,59,59,0.25)` — тоже красное.

⚠️ **Дефект был известен и закрыт наполовину.** Комментарий над `STATE_TEXT` говорит:
«`today` идёт `--text-main`, а НЕ акцентом: на подписи акцент в `t-washi` стал бы
красным и совпал с просрочкой… Акцент остаётся у колонки и точки, **где рядом нет
конкурирующей семантики**». В легенде конкурирующая семантика — соседний глиф.
Посылка неверна, подпись вылечили, глиф и колонку нет.

**Решение — пара токенов, а не правка темы.** В `:root` рядом с семантическим блоком
(`globals.css:2375`):

```css
--mark-today:    var(--accent);
--mark-today-l2: var(--accent-l2);
```

и переопределение ТОЛЬКО в `.t-washi` на `var(--text-main)` и нейтральную полупрозрачную
подложку. Компонент берёт их в `STATE_DOT.today`, `STATE_CHIP.today` и в колонке
«сегодня» вместо `bg-accent`/`bg-accent/20`/`--accent-l2`.

Почему так, а не иначе: правка `--accent` в washi невозможна — торий-красный это
идентичность темы; отказ от акцента у `today` во всех темах убил бы лаймовую точку в
`t-lime`, которая там единственное место лаймового бюджета и работает; кольцо у
легендного глифа лечит легенду и оставляет врущую колонку.

Проверить глазами все восемь тем — washi обязательно, lime обязательно (там ничего не
должно измениться).

## ЗАДАЧА 5 — `audit-contrast.py` меряет не ту тему

**Найдено замером.** `scripts/audit-contrast.py:99` ищет блок темы так:

```python
re.search(re.escape(selector) + r'\s*\{(.*?)\n\}', CSS, re.S)
```

Для `.t-minimal` первое совпадение — **строка 74**, групповой селектор
`.t-aura, .t-washi, .t-tidal, .t-minimal {`: имя стоит в группе последним, и после него
идёт `{`. Скрипт читает общий блок зональных подложек (`--zone-work-tint`,
`--zone-work-ink`) как весь тёмный набор темы и до настоящего блока на строке 732 не
доходит никогда. Отсюда девять фантомных FAIL из двенадцати.

Прогнано python'ом при разведке: `m.start()` попадает на строку 74, первые строки блока —
`--zone-work-tint: var(--purple)`.

Фикс: якорь начала строки — `(?m)^` + `re.escape(selector)` + `\s*\{`. Групповой селектор
в файле ровно один (проверено грепом по всем `^\.t-…, \.t-…{`), но якорь ставится общий:
второй такой селектор появится молча, и следующий отчёт снова соврёт.

После правки — прогнать и **сверить число FAIL до и после**, оно должно упасть. Каждый
оставшийся FAIL разобрать поимённо: если после починки инструмента останутся настоящие,
их чинить НЕ в этом спринте, а вынести списком в отчёт.

## ЗАДАЧА 7 — `hover:bg-surface-hover` не работает нигде

**Найдено гейтом S-DEAL-EVENT-1, подтверждено генерацией.** Варианты (`hover:`, `focus:`,
`disabled:`) Tailwind делает только для имён из палитры конфига. `surface-hover` там нет —
есть ручное правило `.bg-surface-hover` в `@layer components` (`globals.css:1728`), и на
`hover:` оно не распространяется. Прогон `tailwindcss` на пробнике с тремя классами
(`hover:bg-surface-hover`, `bg-surface-hover`, `hover:bg-surface2`) выдал ровно один —
последний.

Итог: **134 места в 75 файлах** наводятся без визуальной реакции. Кнопки, строки списков,
иконочные действия — везде, где написан этот класс.

Замена механическая: `hover:bg-surface-hover` → `hover:bg-surface2`. Значение то же —
ручное правило и так разворачивается в `var(--surface2)`, так что вид меняется только там,
где сейчас не меняется ничего.

```bash
grep -rl 'hover:bg-surface-hover' src/ | xargs sed -i '' 's/hover:bg-surface-hover/hover:bg-surface2/g'
```

⚠️ После замены проверить `.t-fuji`: `globals.css:681–694` селектит по ЭКРАНИРОВАННОМУ
имени класса (`.t-fuji .hover\:bg-surface-hover ...`) — четыре правила, которые после
переименования перестанут находить свои узлы. Их надо переписать на новое имя тем же
коммитом, иначе тема потеряет свои точечные правки молча.

**Вопрос «оставлять ли `.bg-surface-hover` в `@layer components`» закрыт сверкой:
ОСТАВИТЬ.** Базовый класс без `hover:` живой в двух местах —
`SpinReviewRenderer.tsx:40` и `TranscribeDropzone.tsx:412`; удаление правила сломало бы их.

**НОВОЕ, найдено сверкой входа 08.09 — тот же дефект с модификатором прозрачности.**
Семь мест пишут `bg-surface-hover/40` (шесть) и `bg-surface-hover/60` (одно):
`TranscriptViewModal.tsx:94`, `AiSummaryPanel.tsx:37`, `AiDealPanel.tsx:75`,
`AiRunPanel.tsx:192`, `AiCompanyPanel.tsx:92` и `:278`, `AiRunResultModal.tsx:81`.
Модификатор прозрачности Tailwind порождает только для имён из палитры, а ручное правило
в `@layer components` объявлено без дроби — экранированных `\/40`-правил в `globals.css`
нет (проверено грепом). Значит эти семь подложек **не рисуются вовсе**: не «работают без
hover», а прозрачны всегда.

Замена той же природы, но `sed` из задачи 7 их НЕ ловит — он ищет `hover:bg-surface-hover`:

```bash
grep -rl 'bg-surface-hover/' src/ | xargs sed -i '' 's|bg-surface-hover/|bg-surface2/|g'
```

`bg-surface2/40` компилируется корректно: хелпер `v()` в `tailwind.config.ts` отдаёт
`color-mix(... calc(0.4 * 100%) ...)` при литеральном модификаторе — ровно тот механизм,
который в v2.3 чинили для `bg-red/5` и `border-red/30`; `surface-hover` тогда не попал
в палитру и остался с этим дефектом.

⚠️ **Вид в этих семи местах изменится** — сейчас там прозрачно, станет подложка
`--surface2` в 40/60%. Это и есть то, что автор разметки писал; смотреть глазами вместе
с прогоном по темам из задачи 4.
