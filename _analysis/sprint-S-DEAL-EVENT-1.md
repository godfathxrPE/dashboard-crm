# Спринт S-DEAL-EVENT-1 — последнее событие и следствия в ленте (W5)

**Вход:** после мержа S-DEAL-LAYOUT-1. **Миграций НЕТ** — данные лежат в
`activity_log.payload.changes` с 087. **Ветка:** `feat/deal-event-1`. **Спека:** W5.

---

## Зачем

Лента сделки есть и работает (112–120, `EntityTimeline` + `rpc-adapter`), «было → стало»
по полям уже собирает `describeEvent` (`lib/utils/activity-events.ts:188`). Спека
просит над лентой ещё один слой — **последнее событие крупно**:

> ПОСЛЕДНЕЕ СОБЫТИЕ: grid auto | 1fr | auto. Иконка типа 40 r12 ink/lime · мета 11:
> тип · дата-время · длительность · контакт · автор.
> Текст — тёмное стекло `.glass` r14 14 14 4 p12 16: заголовок 14/600, тело 12.5
> white .78 lh 1.5.
> **Следствия 11 green 600: «→ Следующий шаг обновлён», «→ Дата шага: завтра»** —
> автосвязь события с изменёнными полями.
> Кнопки «Изменить» h30, «Открыть» ghost.

Ценность — в следствиях. Сегодня человек видит в ленте звонок и отдельно, строками
ниже, «Дата шага: 1 сент → 2 сент». Что второе произошло ИЗ-ЗА первого, он
восстанавливает в голове. Спека связывает их явно.

---

## Ключевое решение: чем связывать событие и следствия

Внешнего ключа «событие → изменённые поля» в схеме нет и заводить его не нужно.
Связь — **временная и по актору**: изменения полей сделки (`project_updated` /
`stage_changed`, аудит 087), случившиеся в пределах окна после события, тем же
`user_id`. Окно — минуты, не часы: 087 пишет из триггера синхронно с UPDATE.

Это эвристика, и она обязана быть честной:
- окно и правило — в чистой функции с тестом, не в компоненте;
- следствие показывается ТОЛЬКО при совпадении актора; события от cron
  (`user_id is null`, штатно с 087) следствий не получают;
- если в окно попало больше трёх изменений — показываем три и «и ещё N», как уже
  делает лента для группировки полей;
- **никакой записи в БД**: связь вычисляется на чтении. Появится настоящий
  `source_event_id` — функция схлопнется в один join, потребители не изменятся.

Альтернатива «завести колонку связи» отклонена: она требует, чтобы каждый писатель
`activity_log` знал о причине, а их сегодня четыре (триггеры удаления 009/011,
аудит полей 087, лид-статусы 118, клиентские вставки).

## ЗАДАЧА 1 — домен следствий

`src/lib/domain/event-effects.ts`:

```ts
export interface EffectSource {
  id: string; at: string; actorId: string | null;
  eventType: string; payload: Record<string, unknown> | null;
}
export interface Effect { field: string; label: string; text: string }

/**
 * Изменения полей, случившиеся ПОСЛЕ события в пределах окна, тем же актором.
 * Эвристика, а не связь в БД: source_event_id в activity_log нет.
 */
export function resolveEventEffects(
  anchor: EffectSource,
  candidates: readonly EffectSource[],
  windowMs: number,
): { effects: Effect[]; more: number }
```

Правила: только `candidates` с `at > anchor.at` и `at - anchor.at <= windowMs`;
`actorId` совпадает и не `null`; берутся поля из `payload.changes` (тот же разбор,
что у `describeEvent` — **переиспользовать**, не писать второй); текст — из
`FIELD_LABELS`; максимум три, остальное в `more`.

Дефолт окна — 5 минут, вынести константой рядом с функцией и объяснить: аудит 087
пишет синхронно с UPDATE, а человек, поменявший шаг «по итогам звонка», делает это
в те же минуты, пока карточка открыта.
