# Claude Code Prompt — S-R3-TRUST-1: полнота записи как настраиваемое свойство

Ось 1 роадмапа (`improvements/roadmap.md`, «Слой достоверности»). Полнота сделки
уже существует — но зашита в компонент, не настраивается и не фильтруется. Спринт
превращает её в первоклассное свойство: правила в настройках организации, чистая
доменная функция, цена пустоты в UI, предикат сегмента.

**Ветка:** `feat/data-trust` от свежего `main`.

---

## Отклонение от роадмапа — прочитать до начала

Роадмап предлагал `entity_completeness()` (SQL-функция) + `v_deal_completeness` (view).
**В этом спринте их нет, и это осознанный отказ, а не сокращение объёма.**

1. Сегменты считаются **на клиенте** (`src/lib/domain/segment-eval.ts`, граница v1
   записана в шапке файла). Клиент грузит `projects`, а не view — через view обещание
   роадмапа «`completeness_score < 60` становится обычным предикатом» не выполняется
   вовсе. Значение обязано быть у клиента.
2. Полнота **уже посчитана на клиенте** — `getProjectCompleteness()` в
   `ProjectDetail.tsx`, 8 полей. Добавить рядом SQL-формулу значит завести вторую
   правду и получить дрейф между ней и TS.
3. В базе 13 сделок (`type='client'`). Агрегатный view ради `avg()` по 13 строкам —
   инфраструктура под метрику, которую пока некому читать.

SQL-функция появится тогда, когда появится **серверный** потребитель (дайджест,
аналитика вне сессии) — и будет написана один раз под него, а не заранее. До тех пор
единственная формула живёт в TS и покрыта тестами.

## ЗАДАЧА 1: `src/lib/domain/deal-completeness.ts` — чистый домен

Новый файл. Ноль запросов, ноль React, `now` — параметром, если понадобится.

### Контракт

```ts
export interface CompletenessRule {
  key: string;              // 'company_id' | 'budget' | …
  label: string;            // «Компания»
  weight: number;           // вклад в score
  cost: string;             // ЦЕНА ПУСТОТЫ — что ломается без этого поля
  appliesTo?: DealStatus[]; // правило действует только в этих статусах
}

export interface CompletenessResult {
  score: number;            // 0..100, округление вниз
  filled: number;
  total: number;            // число ПРИМЕНИМЫХ правил, не всех
  missing: CompletenessRule[];
}

export function evaluateCompleteness(
  project: ProjectForCompleteness,
  rules?: CompletenessRules,   // из organizations.settings; пусто ⇒ DEFAULT_RULES
): CompletenessResult
```

### Правила по умолчанию

Переносятся из `getProjectCompleteness` **без изменения состава** плюс три
статус-зависимых. Вес — целое, `cost` — одна строка, конкретная, без воды.

| key | label | weight | appliesTo | cost |
|---|---|---|---|---|
| `company_id` | Компания | 3 | — | «Сделка не попадёт в историю компании и в отчёты по клиентам» |
| `contact_id` | Контакт | 2 | — | «Некому писать и звонить: сделка не появится в работе с контактом» |
| `budget` | Бюджет | 3 | — | «Сделка не считается в прогнозе выручки» |
| `stage_id` | Стадия | 3 | — | «Сделка вне воронки: не видна на доске и в аналитике по стадиям» |
| `deadline` | Дедлайн | 1 | — | «Не считается срок и не работает предупреждение о просрочке» |
| `next_step` | Следующий шаг | 2 | `open` | «Сделка помечается как гниющая и всплывает в напоминаниях» |
| `next_action_date` | Дата шага | 2 | `open` | «Без даты шаг не попадёт ни в один список дел» |
| `owner_id` | Ответственный | 2 | — | «Не видно, с кого спрашивать» |
| `loss_reason` | Причина проигрыша | 3 | `lost` | «Проигрыш не попадёт в анализ причин — считать нечего» |
| `won_reason` | Причина победы | 2 | `won` | «Не видно, что именно сработало, и это не повторить» |

Правила `name` в список **не включать**: `projects.name` — `NOT NULL`, правило
никогда не сработает и только разбавляет знаменатель. (В нынешнем
`getProjectCompleteness` оно есть — это перенос с исправлением, отметить в отчёте.)

### Семантика

- Применимость: правило без `appliesTo` — всегда; с `appliesTo` — только когда
  `project.status` в списке. `total` считается **по применимым**, иначе у выигранной
  сделки score вечно упирался бы в потолок из-за `loss_reason`.
- «Заполнено»: `null`, `undefined` и пустая строка после `trim` — не заполнено.
  Для `budget` — дополнительно `> 0` (как сейчас: нулевой бюджет = не указан).
- `score = floor(100 * sum(weight заполненных) / sum(weight применимых))`.
  Применимых правил нет вовсе ⇒ `score = 100`, `missing = []` (не деление на ноль).
- `missing` отсортирован по `weight` убыванию: дорогая пустота выше дешёвой.
- `type !== 'client'` — считать по тем же правилам, но `stage_id` и статус-зависимые
  правила у `internal` не применяются (`stage_id` там `null` по контракту). Реализовать
  через `appliesTo` уровня типа не нужно: добавить в правило `stage_id` условие «только
  для `type === 'client'`» тем же механизмом, что уже стоит в `getProjectCompleteness`
  (комментарий PCT-1). Способ выбрать по коду; главное — у `internal` полнота не должна
  проседать за поле, которого у него не бывает.

## ЗАДАЧА 2: правила в настройках организации

Точный образец — `stage_dwell_defaults`: миграция 076 уже завела `settings jsonb`,
валидатор умеет `.passthrough()`, запись идёт merge'ом. Повторить ту же обвязку.

### 2.1 `src/lib/validators/org-settings.ts`

- ключ `completeness_rules`: `Record<string, { weight?: number }>` — org переопределяет
  **только вес** правила, включая `0` = «правило выключено». Label и `cost` в настройки
  не выносятся: это тексты продукта, а не конфигурация клиента.
- clamp веса `0..10`, целое. Ключ, которого нет в `DEFAULT_RULES`, при чтении
  игнорируется (не роняет разбор) — тот же принцип, что у `parseOrgSettings`.
- функция-резолвер рядом с доменом (Задача 1): `resolveRules(defaults, settings)` —
  зеркало `resolveDwellThreshold`. Пустые настройки ⇒ **ровно** `DEFAULT_RULES`.

### 2.2 `src/components/settings/OrgSettingsSection.tsx`

Новая секция «Полнота сделки»: список правил, у каждого — label, `cost` мелким тихим
текстом и поле веса (строка, не число — пустое поле обязано остаться пустым, ловушка
уже описана в `dwellFieldSchema`). Вес `0` подписать явно: «0 — не учитывать».

⚠️ Права не расширять: `organizations` UPDATE остаётся owner-only. Секция видна всем,
поля недоступны не-владельцу — как это уже сделано для порогов dwell (посмотреть по коду

## ЗАДАЧА 4: `completeness_score` как поле сегмента

Первое **вычисляемое** поле в сегментах — механику завести аккуратно и один раз.

1. `src/lib/constants/segments.ts` — в `SEGMENT_FIELDS.deals` добавить:
   ```ts
   { field: 'completeness_score', label: 'Полнота, %', kind: 'number',
     ops: ['gt', 'gte', 'lt', 'lte', 'eq'] },
   ```
   Операторов `is_null`/`not_null` у него нет: значение есть всегда.
2. `src/lib/domain/segment-eval.ts` — реестр вычисляемых полей:
   ```ts
   const VIRTUAL_FIELDS: Record<string, (row: SegmentRow, ctx: SegmentEvalContext) => unknown> = {
     completeness_score: (row, ctx) => evaluateCompleteness(row as never, ctx.completenessRules).score,
   };
   ```
   Читать так: сначала `VIRTUAL_FIELDS[clause.field]`, если нет — `row[clause.field]`.
   Контекст (`ctx`) добавить **необязательным** параметром публичных функций: у всех
   нынешних вызовов сигнатура обязана остаться рабочей без изменений.
3. Правила в `ctx` прокидывает вызывающий (страница сделок, `useOrgSettings`).
   `ctx` не передан ⇒ `DEFAULT_RULES`, не падение.

⚠️ Стоимость: `evaluateCompleteness` вызывается на каждую строку при фильтрации.
На 13 сделках это ничто, но граница v1 (~5000 строк) в шапке `segment-eval` теперь
касается и этого — **дописать в ту шапку одну строку** про вычисляемые поля, чтобы
будущий пересмотр видел полную картину.
