## P0 — блокеры для многопользовательской работы

### 1. RLS: UPDATE-политики без WITH CHECK → межтенантная запись [SECURITY, HIGH]
`supabase/migrations/20260712230000_baseline.sql` — `calls_update` (3299), `companies_update` (3330), `contacts_update` (3352), `leads_update` (3453), `meetings_update` (3475), `projects_update` (3611), `tasks_update` (3660), `project_columns_update` (3584); `053_quotes.sql` (~66). Из 20 UPDATE-политик WITH CHECK есть только у 8.

`USING` фильтрует, какие строки видно (свой org), но не ограничивает, каким ряд становится после апдейта. `set_org_id()` — BEFORE **INSERT**, на UPDATE не срабатывает, freeze-триггера нет. Аутентифицированный участник org A через PostgREST делает `PATCH /companies?id=eq.<свой>` с `{"org_id":"<uuid org B>"}` — и строка «переезжает» в чужой тенант: поддельная задача/сделка с произвольным текстом появляется у жертвы. Ровно этот класс вы уже закрыли для `notif_update` в 040 — а по ядру CRM пропустили.

**Фикс:** каждой UPDATE-политике `WITH CHECK`, зеркалящий USING (минимум `org_id = (SELECT current_org_id())`), плюс BEFORE UPDATE триггер `NEW.org_id := OLD.org_id`. Одна миграция, полдня с смоуком по вашей же методике (симуляция ролей).

### 2. Org-fetch: при входе грузится ВЕСЬ датасет организации [SCALE, CRITICAL по мере роста]
- `src/app/(dashboard)/layout.tsx:68–101` — shell монтирует CommandPalette (тянет tasks, projects 'all', companies, contacts, calls, meetings, leads — все, сразу, даже если палитру не открывали), EventReminder (calls+meetings+tasks), ActivityDrawer, TextNavSidebar.
- Все базовые list-хуки — **без limit и пагинации**: `use-calls.ts:56`, `use-contacts.ts:56`, `use-companies.ts:54`, `use-meetings.ts:51`, `use-tasks.ts:22`, `fetchProjects`.
- `use-last-touch.ts:47` строит «Остывают» из **всех** звонков и встреч org — индикатор в списке контактов оплачивается скачиванием всей истории коммуникаций.
- `select('*')` тянет `ai_summary` jsonb для каждой строки списков (`use-calls.ts:49`, `use-meetings.ts:49`).
- Умножитель: realtime-инвалидация (`use-realtime.ts:110`) означает, что когда любой коллега логирует звонок, каждый открытый клиент заново скачивает таблицу целиком.

Сейчас (166 задач, 14 звонков, 260 компаний) это незаметно. Команда 10–20 человек с годом данных — это 8–120 тыс. звонков, 10–100 МБ JSON на холодный старт и почти непрерывный перекач таблиц. Это определяет судьбу проекта как «CRM для компании».

**Фикс поэтапно:** (а) бейджи/счётчики → `count head:true` (паттерн уже есть в `dashboard-content.tsx:29`); (б) Cmd+K → server-side поиск с limit 20, данные не грузить до открытия; (в) EventReminder/Calendar → окно дат `.gte/.lte`; (г) списки → `useInfiniteQuery` + `.range()`; (д) last_touch → view/денормализованная колонка с триггером.

### 3. Таймзона: время звонков/дедлайнов пишется без TZ и читается двумя несовместимыми способами [DATA CORRECTNESS]
Запись: `CallModal.tsx:144` шлёт сырую строку `YYYY-MM-DDTHH:mm` из `datetime-local` в `calls.date` (timestamptz) — Postgres трактует её как UTC. Введённые «15:00 МСК» хранятся как 15:00Z = 18:00 МСК. Чтение расщепилось: модалки читают `date.slice(0,16)` (показывают «15:00» — выглядит согласованно), а календарь, CallLog, TodayView, EventReminder — через `new Date()` в локальной TZ (покажут и напомнят в 18:00). Один звонок — разное время в модалке и календаре, напоминание на 3 часа позже. Для задач: дедлайн 21:00–23:59 через `mskDateKey` уезжает на следующий день в Гантте (`use-project-schedule.ts:36`).

**Фикс:** на сабмите `new Date(formValue).toISOString()`, на префилле `localDateTimeKey(new Date(row.date))`; **обязательно бэкфилл-миграция** существующих значений (−3ч), иначе старые записи поедут. И TZ-тесты с `process.env.TZ` — их сейчас ноль.

### 4. Storage-политики бакета project-files не в миграциях [SECURITY, не верифицируемо]
`use-project-files.ts` работает с бакетом `project-files`, но RLS на `storage.objects` нигде в репо не определена (`archive/014_project_files.sql:3` — «create bucket in Dashboard»). Если бакет публичный или политики шире `auth.uid()` — любой аутентифицированный получает чужие файлы по известному пути (`<user_id>/<projectId>/…` — наблюдаемые). Path traversal закрыт (`crypto.randomUUID()` — хорошо). **Фикс:** вынести storage-политики в миграцию, бакет приватный, путь привязан к uid/org, лимиты MIME/размера.

## P1 — реальные баги и подрыв доверия к цифрам

### 5. Соседние экраны показывают разные цифры по одним данным [PM: доверие]
Скриншот-факт: **Обзор** — «Активные проекты: 1», «Сумма pipeline: 3.6M ₽», «Конверсия: 22%». **Сделки** — «Активные: 2», «Pipeline: 11.0M ₽ (взвеш. 8.8M)», «Конверсия: 67%». Карточка сделки — 80%, деталка той же сделки — 82%.

Причина в коде: две независимые формулы. `DashboardHome.tsx:175–195` (active = `status !== won/lost` по всем client-сделкам, conversion = won/(won+lost) за всё время) vs `PipelineBoard.tsx:119–126` (свой active по стадиям текущего пайплайна, conversion по нему же). Плюс два `formatBudget` (`validators/project.ts:194` и `utils/currency.ts:6`). Руководитель, увидевший 3.6M и 11M на соседних вкладках, перестаёт верить обоим. **Фикс:** один модуль-селектор метрик (active/pipeline/weighted/conversion) с одним определением, обе страницы едят его; в UI подписать срез («по всем направлениям» / «IIoT»).

### 6. Лента активности показывает пользователю технический мусор [PM: качество продукта]
Скриншот-факт (Обзор → «Последние действия» и деталка сделки → «Активность»): «Обновлено: stage_id, stage, won_reason, won_detail, loss_reason, loss_detail», «automation_fired». Причина: `activity-events.ts:22` для `project_updated` джойнит **сырые имена колонок**, `default` возвращает сырой `event_type`; плюс в `DashboardHome.tsx:690–722` живёт **вторая, уже разошедшаяся копия** `describeEvent` (в ней нет `meeting_scheduled` с датой, зато есть `entity_deleted`, которого нет в общей). **Фикс:** убить копию, в общей версии — словарь колонок → русские лейблы и словарь event_type → текст («Сработала автоматизация: <имя правила>»).

### 7. Optimistic-обновления задач не видят кеш проектной доски [UX]
`use-tasks.ts:174–207, 256–264, 417–425` патчат только `['tasks']`, а доска проекта и Гантт читают `['tasks','board',projectId]`. Создание/правка/перенос задачи с экрана проекта «прыгает» назад до рефетча — причём `cancelQueries` префиксом ещё и откладывает этот рефетч. Иронично: `useUpdateTaskDates:293` прямо называет это «ГЛАВНАЯ ГРАБЛЯ» и чинит — но только для дат. **Фикс:** `setQueriesData({queryKey:['tasks']})` во всех мутациях (префикс накроет board), как в use-projects.

### 8. Упавшие запросы неотличимы от «данных нет» [UX/поддержка]
Политика «запросы не тостим» (`QueryProvider.tsx:38`) корректна для страниц с error-стейтом, но `use-alerts`, `useLastTouchMap`, StatsWidget, CommandPalette, DashboardHome, EventReminder используют `data ?? []`: при упавшем fetch — нули в KPI, пустой поиск, молчащие напоминания. Владелец видит «0 звонков за неделю» и не знает, что это сбой. **Фикс:** пробрасывать `isError` в бейдж «данные не загрузились» хотя бы на Обзор и в палитру.

### 9. Ошибки файлового контура глотаются [DATA INTEGRITY]
`use-project-files.ts:81` — результат `storage.remove()` не проверяется (метаданные удалены, файл-сирота висит в бакете навсегда); upload прошёл + insert упал → сирота и непонятная ошибка; `:103` — ошибка скачивания уходит в `console.error`, кнопка молча не работает. **Фикс:** компенсирующее удаление, тост в download.

### 10. Типы: `as never` / рукописные дубли Row-типов отключают компилятор [MAINTAINABILITY]
`use-contacts.ts:99,111`, `use-companies.ts:83,96` — `insert(x as never)` полностью выключает проверку payload; `use-projects.ts:54–94`, `use-calls.ts:10–30` и др. — рукописные интерфейсы поверх codegen с `as unknown as` (`use-projects.ts:166+`). Переименование колонки в миграции пройдёт компиляцию и упадёт в рантайме. **Фикс:** `Tables<'x'>`-алиасы из entities.ts, точечный каст только jsonb-полей.

### Security-хвосты (не блокеры, но дёшево закрыть)
- `netlify.toml`: нет HSTS (добавить сейчас — бесплатно), нет CSP (нужен nonce для theme-init скрипта — вы это знаете; минимум `object-src 'none'; base-uri 'self'; frame-ancestors 'none'`).

- `baseline.sql:3921–4148`: `GRANT ALL … TO anon` + `ALTER DEFAULT PRIVILEGES … TO anon` — защита в один слой; любая будущая таблица без `ENABLE RLS` станет публичной. `REVOKE` default-привилегий у anon.
- `ai-summarize` без rate-limit/дедупа (в отличие от `ai-run` с его unique-констрейнтом) — цикл запросов = счёт Anthropic. Дедуп «не генерировать, если `ai_summary_at` моложе N минут».
