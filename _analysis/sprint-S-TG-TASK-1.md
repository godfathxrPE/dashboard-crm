# Claude Code Prompt — Sprint S-TG-TASK-1: задача из свободного текста (интент `task`)

## Контекст и цель

Третий интент `ai-capture`. Пишешь боту «подготовить КП по маркировке для Тандера,
Андрею, до пятницы» — бот показывает карточку разбора с кнопками, по подтверждению
в CRM появляется задача с текстом, сроком, исполнителем и привязкой к сделке.

Голосовой ввод — **следующий спринт** (S-TG-VOICE-1). Он не добавляет разбора: голос
превращается в текст и падает в эту же ветку. Поэтому разбор отлаживается здесь, на
чистом тексте, где нет шума распознавания.

### Это второй клиент готового кода, а не новая фича

| Компонент | Статус |
|---|---|
| `ai-capture` (разбор текста, tool_choice force, анти-injection) | ✅ прод |
| `telegram-webhook` + идемпотентность + резолв профиля | ✅ прод (S-TG-1/2/3) |
| `telegram_capture_drafts` + `tg_apply_capture` + кнопки | ✅ прод (110, 111) |
| `capture-helpers` (токенное сравнение названий, ИНН, телефон) | ✅ прод |

Строится: интент в схеме tool, ветка вставки в RPC, резолверы упоминаний, карточка.

## ИНВАРИАНТЫ (нарушение = провал спринта)

1. **Модель НЕ резолвит сущности.** Она возвращает `assignee_hint` / `project_hint` /
   `company_hint` — дословные подстроки из текста. Сопоставление с БД делает
   детерминированный резолвер на нашей стороне. Тот же инвариант, что «ИНН не парсит
   модель»: связь с существующей записью — факт БД, а не догадка LLM.

2. **Резолв только при ЕДИНСТВЕННОМ совпадении.** Два кандидата ⇒ поле пустое +
   причина в карточке. В базе 273 компании и 17 сделок — неоднозначность будет
   регулярно, и «выбрать первое» здесь означает «привязать не к тому».

3. **Дедлайн модель считает от ЯВНО переданного «сейчас».** LLM не знает сегодняшней
   даты; без неё «до пятницы» вычисляется от чего угодно. Текущий момент в
   `Europe/Moscow` подставляется в системный промпт функцией.

4. **Карточка показывает все резолвы ДО нажатия «Создать».** Не резолвленное —
   явной строкой с причиной, не молчаливым пропуском. `trg_notify_task_assigned`
   срабатывает `AFTER INSERT OR UPDATE OF assigned_to` — ошибочное назначение
   немедленно уведомляет не того человека, и отката у этого нет.

5. **Запись под правами человека.** RPC с явным `p_actor_id`, гарды внутри. Никаких
   вставок service-ключом «от имени системы».

6. **Миграция пишется и коммитится, НЕ применяется.** Apply — операция гейта.

### 1.1 CHECK на `kind`

```sql
alter table public.telegram_capture_drafts

alter table public.telegram_capture_drafts
  add constraint telegram_capture_drafts_kind_check

```

`duplicate_kind` CHECK **не трогать**: дедупа задач нет (две одинаковые задачи —
нормальная ситуация, в отличие от двух одинаковых компаний).

### 1.2 `tg_apply_capture` — ветка `task`

`create or replace`, тип возврата `jsonb` **не меняется** ⇒ `drop function` не нужен.
Тело брать из `pg_get_functiondef`, менять минимально — дописать ветку, существующие
не переписывать.

Порядок проверок в новой ветке (все NULL-safe):

1. черновик существует и `status='pending'` → иначе `already_applied` / `not_found`;
2. `draft.profile_id = p_actor_id` → иначе `42501`;
3. роль актора **читать запросом к `memberships` по `p_actor_id` и `draft.org_id`**
   (`current_org_role()` в service-контексте возвращает NULL, а `NULL not in (...)`
   даёт NULL ⇒ гард молча пропустит). Роли `viewer` в базе сейчас нет, но гард
   пишется на будущее: создавать может любой член org кроме `viewer`;
4. **валидация ссылок из payload — каждая проверяется на принадлежность
   `draft.org_id`:**
   - `assigned_to` → есть membership `(profile_id, org_id)`; иначе ссылку **обнулить**,
     не падать (черновик мог пережить удаление сотрудника);
   - `project_id` → `projects.org_id = draft.org_id`; иначе обнулить;
   - `company_id` → `companies.org_id = draft.org_id`; иначе обнулить.

   Это не перестраховка: функция SECURITY DEFINER читает и пишет в обход RLS, и без
   явного org-гарда чужой uuid в payload даёт cross-tenant связь. Тот же класс, что
   `check_task_dependency_valid` (048).
5. вставка в `tasks`:

```sql
insert into public.tasks (
  text, lane, priority, deadline, remind_min,
  project_id, company_id, assigned_to,
  created_by, org_id
) values (
  v_payload->>'text',
  'next',                          -- см. ниже
  coalesce((v_payload->>'priority')::public.task_priority, 'normal'),
  nullif(v_payload->>'deadline','')::timestamptz,
  nullif(v_payload->>'remind_min','')::int,
  v_project_id, v_company_id, v_assignee_id,
  p_actor_id,                      -- default auth.uid() в service-контексте = NULL
  v_draft.org_id                   -- trg_set_org_id заполняет только при NULL, а
)                                  -- current_org_id() здесь тоже NULL
returning id into v_task_id;
```

**`lane = 'next'` («Не начата»), не дефолтный `'now'`.** Задача, которую только что
поставили, не находится в работе. Прецедент — delivery-путь (`ProjectBoard` phaseMode,
`copy_delivery_template`), где массовое создание ставит `next` ровно по этой причине.

⚠️ `trg_aa_resolve_board` при непустом `project_id` подберёт `column_id` и **может
переписать `lane`** по категории колонки. Это штатное поведение доски проекта, ему не
мешать; в отчёте зафиксировать, каким `lane` задача оказалась при привязке к сделке.

6. `status='applied'`, `applied_at=now()`, `created_entity_id = v_task_id`;
7. вернуть `jsonb_build_object('status','created','kind','task','id',v_task_id,
   'label', left(v_payload->>'text', 80))`.

Формат возврата обязан совпадать с тем, что уже разбирает бот для contact/company —
сверить по живому телу функции, а не по этому описанию.

## ЗАДАЧА 2: `ai-capture` — третий интент

### 2.1 Схема tool

В `submit_capture` расширить `intent` до `contact | company | task | unclear`
и добавить блок:

```
task: {
  text:          string  — формулировка задачи, императив, без «надо бы» и «мне нужно»
  deadline_date: string  — YYYY-MM-DD или ""
  deadline_time: string  — HH:MM или "" (не сказано ⇒ "")
  priority:      string  — normal | important | critical
  assignee_hint: string  — ДОСЛОВНАЯ подстрока с упоминанием человека или ""
  project_hint:  string  — дословное упоминание сделки/проекта или ""
  company_hint:  string  — дословное упоминание компании или ""
}
```

**`*_hint` — это цитата из входного текста, а не имя из базы.** В описании tool
написать прямо: «не подбирай похожее, не склоняй, не дополняй; если не сказано —
пустая строка». Модель, которой разрешено «вспомнить» фамилию, начнёт её выдумывать.

`deadline_date` и `deadline_time` — раздельно. Слитная ISO-строка провоцирует модель
дописать время, которого не было, и «до пятницы» превратится в «пятница 00:00»,
то есть в четверг вечер по факту.

### 2.2 «Сейчас» в системном промпте

Функция сама считает текущий момент в `Europe/Moscow` и подставляет строкой:

```
Сейчас: 2026-08-19, среда, 14:30 (Москва).
Все относительные сроки («завтра», «до пятницы», «через неделю») считай от этого момента.
Если срок не назван — deadline_date пустая строка. Не придумывай срок.
```

Через `Intl.DateTimeFormat('ru-RU', { timeZone: 'Europe/Moscow', ... })`, не через
арифметику с offset: смещение MSK постоянно сегодня, но захардкоженное `+3` — это
константа без даты сверки, ровно тот класс, что `USD_RUB = 100`.

Параметром из тела запроса «сейчас» **не принимать**: у функции два вызывающих
(веб-виджет и бот), и два источника времени разойдутся.

### 2.3 Правила интента в промпте

| Признак | Интент |
|---|---|
| Глагол действия + (опционально) срок: «позвонить», «подготовить», «отправить», «согласовать» | `task` |
| ФИО, должность, телефон, почта — **без** глагола действия | `contact` |
| Название организации, оргформа (ООО/АО/ИП), ИНН — без глагола действия | `company` |
| И действие, и полные контакты нового человека одновременно; либо непонятно | `unclear` |

Разделитель — **наличие действия**, и это надо написать в промпте примером:
«Иванов Пётр, коммерческий директор, +7 999…» → `contact`;
«позвонить Иванову Петру насчёт КП» → `task`.

`priority = 'critical'` — только на явное «срочно», «горит», «сегодня же».
Само по себе наличие близкого срока критичности не даёт.

аддитивно. Существующие ветки не трогать — **все текущие вызовы обязаны разбираться

## ЗАДАЧА 3: Резолверы упоминаний

Новый файл `supabase/functions/_shared/capture-resolve.ts` + реэкспорт из
`src/lib/utils/capture-resolve.ts` (паттерн `capture-helpers`, вариант 1 из S-TG-3:
один файл, два специфера — Deno с расширением, TS без).

```typescript
export type ResolveReason = 'ok' | 'empty' | 'not_found' | 'ambiguous'
export type Resolved = { id: string | null; reason: ResolveReason; hint: string }
```

Три функции: `resolveAssignee`, `resolveProject`, `resolveCompany`. Каждая:

1. `hint` пустой или короче 2 символов ⇒ `{ id: null, reason: 'empty', hint }`;
2. **два шага, и их нельзя схлопывать в один:**
   - грубый отбор кандидатов в SQL — `ilike '%<самый длинный токен hint>%'`,
     `limit 20`. Не `limit 5`: широкий `ilike` на 273 компаниях легко даёт больше
     пяти, и правильный кандидат отсечётся молча — то есть «не нашлось» будет
     означать «не влез»;
   - точный матч — токенами в JS (ниже), уже по этим кандидатам;
3. после точного матча: ровно один кандидат ⇒ `ok`; ноль ⇒ `not_found`;
   два и больше ⇒ `ambiguous`.

⚠️ Если грубый отбор вернул ровно 20 строк — считать это `ambiguous`, а не выбирать
из усечённой выборки: при упёршемся лимите мы не знаем, что осталось за ним.

Кого ищем:

| Функция | Источник | Условие |
|---|---|---|
| `resolveAssignee` | `profiles` join `memberships` | `memberships.org_id = <org>`, роль ≠ `viewer`, `profiles.full_name` матчит |
| `resolveProject` | `projects` | `org_id = <org>`, `type = 'client'`, `name` матчит |
| `resolveCompany` | `companies` | `org_id = <org>`, `name` матчит |

### Сопоставление — токенами, НЕ регуляркой с `\b`

`\b` в JS определён через `\w = [A-Za-z0-9_]`; рядом с кириллицей границы слова нет
вовсе, и правило молча не срабатывает никогда. Эта грабля уже стоила проекту двух
спринтов (S-CHAT-TASK-1, S-TG-3) и по построению **не имеет симптома**: несработавший
матчер возвращает «не нашлось» — ровно то же, что честное отсутствие.

Поэтому: `split(/\s+/)` → нормализация (нижний регистр, `ё`→`е`, снять пунктуацию) →
`Set` → сравнение множеств. **Функцию нормализации и список ОПФ-токенов взять из
существующего `capture-helpers`, не писать вторую копию.**

Правило матча: каждый значимый токен `hint` находит себе токен в имени кандидата.

Для **имён людей** — по основе, иначе падеж всё сломает («андрею» против «Андрей»):
токены совпадают, если равны первые 4 символа; токен короче 4 символов сравнивается
целиком. `андр|андр` ✓, `моля|моля` ✓ («Молявину» → «Молявин»).

Для **названий компаний и сделок** основы **не применять** — на четырёх символах
«Тандер» и «Тандем» слились бы, а это разные юрлица. Токены сравниваются целиком,
ОПФ-токены (ооо, ао, зао, пао, ип…) выбрасываются с обеих сторон.

⚠️ Тест обязан проверять **положительный** исход («эти пять написаний — один
человек»), а не только отрицательный: матчер, сломанный целиком, все отрицательные
кейсы проходит.

## ЗАДАЧА 4: Бот — черновик и карточка задачи

Ветка `intent='task'` в обработчике свободного текста. **Существующие ветки
(contact / company / unclear) не переписывать.**

1. разбор `ai-capture` вернул `intent='task'`;
2. три резолва (задача 3) под service-клиентом, `org_id` — из профиля отправителя;
3. `deadline` собрать из `deadline_date` + `deadline_time`:
   - время не названо ⇒ **18:00 MSK** того дня. Не полночь: «до пятницы» с дедлайном
     00:00 просрочивается в четверг вечером;
   - дата в прошлом ⇒ `deadline = null` + строка в карточке «срок в прошлом,
     не проставлен». Модель, ошибившаяся с годом, не должна создавать просроченную
     задачу молча;
   - смещение — через `Europe/Moscow`, не арифметикой (`mskDateKey`-конвенция проекта).
4. черновик: `kind='task'`, `payload` — уже с разрешёнными `assigned_to` /
   `project_id` / `company_id` (uuid, не hint) и вычисленным `deadline`;
   `source_text` — исходное сообщение целиком;
5. `editMessageText` карточкой.

### Карточка

```
Задача
Подготовить КП по маркировке для Тандера

Срок: пятница, 22 августа, 18:00
Исполнитель: Андрей Молявин
Сделка: Тандер — внедрение ЧЗ

[ Создать ]  [ Отмена ]
```

Срок — **с днём недели**. «22.08» проверить глазами нельзя, «пятница, 22 августа» —
можно, и именно на этом ловится ошибка модели в неделе.

Не разрешённое показывается строкой с причиной, а не пропускается:

```
Исполнитель: «Андрею» — не нашёл, назначьте в CRM
Сделка: «по тандеру» — несколько совпадений, выберите в CRM
```

Молчаливый пропуск даёт «не поломку, а тихую деградацию»: человек нажимает «Создать»,
считая, что исполнитель проставлен.

### callback_data — новых префиксов НЕ вводить

Черновик уже несёт `kind='task'`, а `tg_apply_capture` принимает `p_kind` третьим
аргументом. Значит работают существующие `tgcap:<draft_id>` / `tgcapx:<draft_id>`,
и ветка выбора (`tgcapc` / `tgcapo`) для задачи не нужна.

Пятый префикс — это пятый шанс на пересечение при разборе; проверить, что
`p_kind` для task-черновика подставляется из строки БД, а не из префикса кнопки.

`answerCallbackQuery` — в каждой ветке, включая отказные.

⚠️ `editMessageText` слать **без `parse_mode`**, как это уже сделано в S-TG-2:
`message.text` приходит с уже снятой разметкой, повторное экранирование даёт `&amp;amp;`.

## Что здесь сознательно НЕ делается

- **Голосовой ввод** — S-TG-VOICE-1, следующим. Разбор обязан быть отлажен на чистом
  тексте раньше, чем в него придёт шум распознавания: иначе при первом сбое неотличимо,
  кто ошибся — Whisper или модель.
- **Журнал прогонов `ai-capture`.** `ai_runs` требует `entity_id NOT NULL` и CHECK по
  `entity_type`, а capture работает до появления сущности. Долг растёт: после этого
  спринта источников три. Отдельная миграция, брать по факту.
- **Веб-виджет `QuickCapture`** интент `task` пока не показывает: `ai-capture` его уже
  вернёт, но ветки открытия `TaskModal` с прифиллом здесь нет. Виджет обязан на
  незнакомый интент вести себя как на `unclear`, а не падать — проверить и записать
  в отчёт.
- **Дедуп задач.** Две одинаковые задачи — законная ситуация.
- **Мультиразбор** («три задачи одним сообщением») — `ai-capture` v1 возвращает одну
  сущность за вызов.
