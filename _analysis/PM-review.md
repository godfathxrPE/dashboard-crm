Ревью dashboard-crm глазами Senior Project Manager

Роль ревьюера: PM с опытом проектов 10–200 млн ₽, команды от 3 до 30+, delivery + presale.
Объект: dashboard-crm (Next.js 15 + Supabase), состояние кода на main (включая Gantt/deps/portfolio/WBS/quotes/workflow — коммиты после 12–14 июля).
Метод: разбор рабочих сценариев PM по коду (ProjectDetail, GanttTimeline, PortfolioView, TodayView, hooks, схема), сопоставление с уже существующими аудитами.
Ограничение по UI: MCP Google Chrome в этой сессии не подключён, локальный localhost:3000 не слушает. Визуал подтверждён структурой UI-кода и прошлыми visual/code-аудитами; где нужен «живой» скрин — отмечено как требует smoke в браузере.

2. Что я делаю как PM в первый рабочий день — и где система помогает / мешает

2.1 Утро: «Что красное?»

Есть:
• /projects?tab=portfolio — health-ранжирование, фильтры at_risk / attention
• виджет PortfolioRiskWidget на /overview
• сигналы: просрочка дедлайна, застой в стадии >30д, «тишина» >14д, низкий прогресс

Мешает:
1. «Сегодня» (TodayView) — не PM-дашборд.
   Там: просроченные звонки, гниющие сделки, лиды, личные lane=now задачи, reconnect контактов.
   Нет: «мои внедрения в риске», «вехи на этой неделе», «просроченные задачи по delivery», «кто из команды перегружен».
   Аргумент: утром РП с 10 внедрениями открывает / и получает sales-очередь. Портфель спрятан на /projects?tab=portfolio или в виджете overview. Это лишний клик и разрыв IA: продукт говорит «Сегодня», а для PM «сегодня» = delivery risk, не funnel.

2. Health — proxy, не план.
   В delivery-health.ts нет: сорванной вехи, срыва FS-связи, отклонения от baseline, % complete по критическому пути.
   updated_at как «активность» даёт ложные зелёные (кто-то переименовал файл → «жив») и ложные красные (тихий, но по плану).
   Аргумент: score 0–100 полезен как triage, не как статус для руководства («мы в зелёной зоне»).

2.2 Планирование запуска (IIoT 4 фазы / ERP 6 этапов)

Есть:
• spawn из won (SpawnWizard)
• фазовая доска (ProjectBoard phase mode)
• Gantt: zoom day/week/month, drag move/resize, вехи, WBS, deps FS, подсветка critical path, undated bucket

Блокеры (с аргументами из кода):

P0 — Зависимости «рисуются», но не управляют расписанием

В GanttTimeline.tsx прямо:

«FS-констрейнт не enforced (см. S-DEPS-1 W7). Полный CPM — возможный v2»

И critical path:

«НЕ полный CPM (ES/EF/LS/LF/float) — даты пользовательские»

Что это значит на практике:
• связал «Монтаж → Пусконаладка» FS;
• сдвинул монтаж на +10 дней;
• пусконаладка остаётся на старых датах → график визуально врёт;
• critical path подсвечивает «самую длинную сумму длительностей», не путь с нулевым float по реальным датам.

Для PM на проекте 20–80 млн ₽ это не «nice to have» — это основной инструмент. Без cascade/reschedule Gantt = красивый календарь, не plan of record.

Доказательство неполноты lag: в БД есть lag_days, create dependency пишет lag_days: 0 хардкодом (use-task-dependencies.ts). UI lag нет → нельзя «FS + 5 рабочих дней на логистику».

P0 — Дефолтная вкладка карточки delivery = «Активность»

const [tab, setTab] = useState<'activity' | 'board' | 'timeline' | 'quotes'>('activity');

PM открывает внедрение → лента заметок/звонков, а не План и не Гант.
Для sales-сделки это ок. Для delivery — неверная информационная иерархия.
Внедрение = план + даты + команда; activity — вторична.

P1 — WBS рвётся по фазам (задокументированный v1)

use-project-schedule.ts: родитель и ребёнок в разных column_id (фазах) → оба корни.
СДР часто: пакет «Документация» тянется через фазы. WBS «1.3 → 1.3.1» в разных фазах не соберётся. Это не баг отрисовки — архитектурный потолок v1.

P1 — Нет baseline / plan vs fact

Нет полей «утверждённый план» vs «текущий».
Нельзя ответить: «на сколько дней уплыл запуск относительно подписанного графика».
Для проектов >30 млн это стандартный вопрос заказчика/руководства.

P1 — Нет effort / estimate / remaining

У задач: text, lane, priority, dates, assignee, parent/wbs, milestone.
Нет planned hours / remaining.
Без effort нельзя: capacity, % complete по трудозатратам, «успеем ли к дате» при 2 FTE.

2.3 Ежедневное исполнение

Есть:
• фазовая доска + личный Kanban /tasks (now/next/wait/done)
• assignee, team roles, files на проекте
• automation (в т.ч. task_overdue), notifications

Мешает:

P1 — Две модели задач без «склейки для РП»

┌──────────────────────┬────────────────────┐
│ Место                │ Модель             │
├──────────────────────┼────────────────────┤
│ /tasks               │ Личные lane (GTD)  │
├──────────────────────┼────────────────────┤
│ /projects/[id] board │ column_id / фазы   │
├──────────────────────┼────────────────────┤
│ Gantt                │ start/end/deadline │
└──────────────────────┴────────────────────┘

Lane и project column синхронизируются триггерами (есть), но UX «мои задачи по всем внедрениям с проектом, сроком, статусом фазы» как единый PM-inbox — нет.
useTasks() тянет все задачи org (RLS), без фильтра «assigned to me / my projects» в UI списка как first-class preset.

На 200+ задачах личный борд превращается в свалку; на 5 внедрениях PM всё равно не видит cross-project load.

P1 — Нет обсуждения на задаче

Есть ActivityComposer на уровне проекта, нет thread/comments на задаче (нет task_comments в модели как first-class).
Согласование «акт vs факт на объекте», замечания монтажника — уходят в Telegram/ДО.
Для распределённой delivery-команды это потеря single source of truth.

P2 — Файлы только на проекте

ProjectFiles — project-level. Нет attachment «к вехе / к задаче приёмки».
Gate закрытия смотрит milestones (DeliveryCompletionModal), но evidence (протокол, акт) не привязан к вехе структурно — только «галочка done».

2.4 Портфель и ресурсы

Есть: Portfolio table + risk widget + aging по фазам.
Нет:

┌────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────────┐
│ Нужно PM                                           │ Статус                                                      │
├────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ Multi-project Gantt / timeline портфеля            │ Нет                                                         │
├────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ Загрузка людей (open tasks / overlapping launches) │ Нет (project_members + assigned_to есть, UI workload — нет) │
├────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ «Мои проекты» (owner / member)                     │ Слабо / не first-class filter                               │
├────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ Internal в том же health-портфеле                  │ Нет (portfolio = только type=delivery)                      │
├────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤

└────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────────┘

Аргумент: при 8–12 внедрениях + internal CRM-доработки PM обязан смотреть людей. Иначе «два launch на одного внедренца» — системный риск, невидимый в продукте.

2.5 Сквозной контур sales → delivery

Сильно:
• won reason + SpawnWizard
• DealDeliveryHub (дочерние delivery, health, do_url, CTA ещё одно внедрение)
• обратная ссылка delivery → parent deal

Слабо:
• 1С:ДО = ручная URL, нет sync статусов/чеклистов
• Analytics не считает lag «won → spawn → first phase complete»
• Руководство не видит «деньги won vs % delivery complete» на одном экране

Это не «ошибка кода» — продуктовый gap для компании, где CRM обещает быть панелью, а ДО — system of record. Сейчас панель неполная.

2.6 Internal-проекты

ProjectsSection → tab internal = DataTable (name, status, deadline, next_step).
Нет: health, board list-level, templates, portfolio, risk widget.
На карточке — ProjectBoard + Gantt (через tabs), но второй сорт в навигации и управлении.

Если компания ведёт «CRM, маркетинг, онбординг» как internal — PM не получит тот же control tower, что по IIoT.

3. Конкретные дефекты / несостыковки (с аргументами)

Ниже только то, что подтверждается кодом и реально бьёт по работе.

3.1 Копирайт ошибки игнорирует тип сущности — High (UX trust)

// ProjectDetail.tsx ~202
<p className="mt.2 ...">Сделка не найдена</p>
// back всегда предлагает «к воронке» логикой error-state

Открыл /projects/{bad-id} или delivery удалён → «Сделка не найдена».
Для PM это сигнал: продукт всё ещё «CRM сделок», delivery — надстройка. Подрывает доверие к routing-контракту client/delivery/internal.

Фикс: текст по type / route: «Сделка / Проект внедрения / Внутренний проект не найден» + back на /deals или /projects.

3.2 Delivery: нет модалки редактирования карточки — Medium

{!isDelivery && (
  <button onClick={() => setModalOpen(true)} ... Pencil
)}

Delivery правится инлайном (deadline, do_url).
Нет удобного edit name, notes, company/contact, owner одним экраном.
При ошибке spawn/опечатке в названии — трение.

3.3 Полная выгрузка таблиц на клиент — High (scale)

useTasks, useCompanies, useCalls и др. — select без server-side pagination (timeline/activity — с limit, основные сущности — нет).
Layout тянет badge-счётчики через полные useTasks/useCalls/useLeads.

Аргумент: при росте history (год звонков + тысячи задач) деградируют все экраны, включая settings.
Для PM это «тормоза на планёрке» — perceived quality падает раньше, чем «формально сломается».

3.4 Progress = count задач, не смысл плана — Medium (management)

progress_done/total — счётчик.
10 мелких «согласовать» = тот же вес, что «монтаж АСУ».
Health «низкий прогресс» на этом базисе легко врёт.

3.5 Dual entry с 1С:ДО без правил — High (process)

Поле do_url + файлы + задачи в CRM + шаблон из ДО.
Нет: что master, кто обновляет фазу, что делать при расхождении.
Риск: РП ведёт Gantt в CRM, инженер — в ДО → два правды.

7. Что сделано хорошо (и это важно не размазать)

Я бы не уходил с продукта как «ещё один таск-трекер» — база сильная:

1. Правильная объектная модель client | delivery | internal + routing — лучше, чем «сделки отдельно, проекты в Monday».
2. Stage gates на sales сильнее типичного HubSpot-lite — дисциплина пресейла.
3. Spawn + DealDeliveryHub + health — осознанный quote-to-delivery, не случайный append.
4. Gantt за короткое время (dates, deps, WBS, crit path visual, drag) — редкий уровень для custom CRM такого размера.
5. Portfolio risk + shared usePortfolioHealth — правильный management signal, не дубли порогов.
6. Инженерная гигиена после аудита: toast, dirty modal, realtime refcount, reorder RPC, stage path B — видно, что продукт чинят системно, не «мажут UI».
7. Automation engine + overdue — путь к «процесс сам напоминает», если наполнить правилами под delivery.
8. Роли/RLS/canManageDelivery — не дают viewer «красивые кнопки → 42501».

Итог: это не сырой MVP 2024-го образца. Это sales-strong CRM с растущим delivery-слоем, который остановился на полпути от «таскборд + картинка Gantt» к «plan of record».
