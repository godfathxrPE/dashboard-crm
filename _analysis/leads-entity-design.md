# Лиды: проектирование сущности до уровня сделок

Дата: 2026-08-09 · статус: **на согласование** (спринт — после выбора варианта)

---

## 1. Диагноз текущего состояния

Таблица `leads` (миграция 016, +018 dedupe) — плоская запись триажа:

```
title · source · status(new/contacted/qualified/disqualified/converted) · direction(erp/iiot)
company_name_raw · contact_name_raw · phone · email · notes · disqualify_reason
converted_{deal,company,contact}_id · converted_at · user_id · org_id
```

Что у лида есть: канбан 4 колонки + таблица, staleness-метки (1 дн / 7 дн, `lib/constants/leads.ts`),
конверсия через RPC `convert_lead` с дедупликацией, полоса «Конвертированы».

Чего нет — и что есть у сделок:

| Измерение | Сделка | Лид |
|---|---|---|
| Ответственный | `owner_id` + AssigneeSelect | `user_id` (legacy, против конвенции проекта) |
| Следующий шаг | `next_step` + `next_action_date` + DealFocusPanel + TodayView | нет |
| История касаний | EntityTimeline: звонки/встречи/задачи/система | нет — звонки к лиду не привязываются вообще |
| Карточка | страница `/deals/[id]` | модалка; deep-link `?lead=<id>` — костыль, конвертированный лид по ссылке недоступен |
| Здоровье/деньги | health 0–8, completeness, budget | стейл-метка |
| Журнал | activity_log + аудит полей 087, `log_delete_*` | лид не логируется нигде, даже удаление |

Ключевой разрыв воронки: **звонок по лиду до конверсии** сегодня либо не фиксируется, либо
создаётся «висячим» без связи. История продажи начинается только со сделки — время реакции
и количество касаний до квалификации невосстановимы.

## 2. Что взято из западных CRM

- **Pipedrive Leads Inbox** — лид как лёгкий «предбанник» пайплайна: labels (hot/warm/cold),
  value, источник/канал, next activity, archive. Конверсия переносит всё в сделку.
- **HubSpot Lead object** — лид = «попытка проработки» (prospecting effort) поверх
  contact/company; стадии двигаются **автоматически от активностей** (залогирован звонок →
  attempting/connected). Несколько лидов на один контакт во времени — нормально.
- **Close** — телефонная воронка: лента звонков прямо в карточке, «action inbox»
  (уже взят в TodayView). Скорость первого касания — главная метрика.
- **Attio/Linear-школа** — минимум обязательных полей, статусы как атрибуты, вся глубина
  в timeline, а не в форме.

Вывод: глубина лида — **не в количестве полей формы, а в связанности** (касания, ответственный,
следующий шаг) и в **скорости обработки**. Раздувать форму до анкеты — антипаттерн.

## 3. Варианты

### Вариант A — «Быстрый инбокс» (Pipedrive-минимум, 1 миграция, ~1 спринт)

Философия: лид живёт дни, его задача — быстро умереть (конверсия или дисквал).

Одна миграция по конвенции org-таблиц:

- `owner_id uuid → profiles ON DELETE SET NULL` — ответственный (+ бэкфилл из `user_id`, RLS на owner/created_by)
- `next_step text`, `next_action_date date` — язык сделок, интеграция в TodayView
- `temperature text` check `hot|warm|cold` — ручная метка приоритета
- `estimated_value bigint` — **копейки**, как `projects.budget`/`quotes.amount`
- `first_contacted_at timestamptz`, `qualified_at timestamptz` — штампы для метрик
  (time-to-first-touch, длительность квалификации)
- `chz_groups text[]`, `regulatory_deadline date` — доменные (см. §5)

UI: карточка канбана дорастает (шаг/температура/сумма), модалка дополняется, секция
«Лиды без реакции» в TodayView, конверсия по источникам в Analytics.

Слабость (честно): звонки по лиду по-прежнему не видны — «глубоко как сделки» не выйдет.
История касаний остаётся в заметках. Это полировка триажа, не новая сущность.

### Вариант B — «Рабочая сущность» (HubSpot-модель, 2–3 миграции, ~2 спринта) — рекомендую

Всё из A, плюс три структурных хода:

**1. Лид входит в граф активностей.**
`calls.lead_id`, `tasks.lead_id` (nullable FK ON DELETE SET NULL + partial index — образец
`activity_log.contact_id` из 042). `activity_log.lead_id` тем же паттерном + лог смен статуса
и `log_delete_lead`. EntityTimeline получает `entityType='lead'` — лента касаний в карточке
бесплатно, инфраструктура уже готова.

**2. Полная карточка `/leads/[id]`.**
Лёгкий лейаут (не клон ProjectDetail): степпер статусов → фокус-панель (следующий шаг /
SLA-индикатор / температура) → квалификация → EntityTimeline + ActivityComposer + кнопки
+Звонок/+Задача → блок конверсии. Убивает костыль `?lead=<id>`; конвертированный лид
становится читаемой страницей со ссылкой на сделку.

**3. Конверсия переносит историю, а не только реквизиты.**
`convert_lead` v2: звонки/задачи лида получают `contact_id`/`company_id`/`project_id`
созданных сущностей; `chz_groups` лида → маркировочный профиль компании; `pain`/notes →
`pinned_note` сделки. Время жизни лида (created → first_contacted → qualified → converted)
остаётся в аналитике.

Плюс авто-прогресс по HubSpot-паттерну: залогирован звонок `done` по лиду в статусе `new` →
статус `contacted` + штамп `first_contacted_at` (в мутации клиента, без триггера — проще
и видимее).

Квалификация — 4 поля, не анкета: `pain text` (боль/задача клиента), `budget_status`
check `unknown|none|estimated|confirmed`, `decision_role text` (кто наш контакт: ЛПР/влияющий/
пользователь — словарь `stakeholders.ts` уже есть), `regulatory_deadline date`.

### Вариант C — «Полный паритет со сделками» (4+ миграций, 3–4 спринта)

Всё из B, плюс: таблица `lead_transitions` (история статусов, аналог 078), SLA-пороги в
`organizations.settings`, скоринг fit/behavior, каденции обзвона (sequences),
`meetings.lead_id`, автоматизации `wf` и вебхуки на события лидов.

Честная оценка: **перебор сейчас**. Скоринг и каденции окупаются от ~50+ лидов/мес на
человека; при текущем потоке это мёртвые механизмы, которые придётся поддерживать.
Всё из C добирается инкрементально поверх B, когда поток вырастет.

---

## 4. Рекомендация

**Вариант B.** Он единственный отвечает на исходный запрос «глубоко как сделки»: глубина
сделки — это её лента и связи, а не форма. A не меняет природу раздела, C строит механизмы
без потока под них. B переиспользует три готовые подсистемы (EntityTimeline, ActivityComposer,
TodayView-очередь) — цена глубины низкая именно сейчас.

Попутно закрывается долг: `user_id` → `owner_id` (конвенция ownership), лид входит в
audit-контур (`log_delete_lead`), исчезает `?lead=` хак.

## 5. Уникальное для домена (нет ни в одной западной CRM)

**Регуляторный дедлайн как источник срочности.** В маркировке urgency создаёт не клиент,
а государство: волны обязательности по товарным группам. У лида поле `chz_groups[]`
(справочник `lib/data/chz-groups.ts` уже в проекте) + `regulatory_deadline` — авто-подсказка
из справочника. Бейдж «обязательная маркировка через N мес.» на карточке лида — сортировка
приоритета, аргумент для звонка и готовый SPIN-implication. При конверсии профиль ЧЗ
переезжает в компанию — цикл замыкается.

**SLA первого касания как first-class метрика.** Сейчас стейл-метки визуальные; с
`first_contacted_at` появляется отчёт: медиана времени реакции по источникам × конверсия
по источникам × причины дисквалификации. Это ответ на «какой канал лидов кормить» —
уровень аналитики, которого нет и у сделок.
