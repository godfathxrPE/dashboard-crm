## Проблема, измеренная фактом

`deal_progression` на транскрипте с инъекцией: **1 отказ из 4** (прогон
`7596c3e0-…`, 10:52 28.07). Вернулось:

```
"tasks":  "\n<parameter name=\"tasks\">[{\"text\":\"Проверить, прислала ли Дарья...\"}]"
"fields": "\n<parameter name=\"next_step\">Получить от Дарьи/Глеба качественные фото..."
```

`tasks` и `fields` — строки вместо массива и объекта; внутри синтаксис tool-use
параметров. Три остальных прогона на идентичных транскриптах (разные звонки) вернули
корректные `array` / `object`. `prompt_version` у всех четырёх = 2.

**Диагноз (проверен, не предположение).** Вход был чистым: в транскрипте ни одного
символа `<`, слова `parameter` нет. Разметку модель сгенерировала сама, сорвавшись со
структурированного вывода. Содержимое при этом правильное — сломалась упаковка.

**Следствие.** `parseProposal` возвращает `null`, панель показывает «модель вернула
некорректный ответ». Данные целы, безопасность цела, но прогон потерян и токены
оплачены. Для атакующего — дешёвый DoS: абзац в заметке ломает каждый четвёртый SDP.

**Проблема шире инъекции — это базовый уровень брака.** Обход всех семи живых строк
`ai_runs` (28.07, после чистки смоука):

| Прогон | Дата | Пресет | `</` в result | `<parameter` |
|---|---|---|---|---|
| `3a75cfbb-c65a-4a10-be57-ac1eb0cbfb1a` | 11.07 | `analytic_note` | **да** | **да** |
| `3d5e6e70-bf5a-4032-9989-5dadb71cd453` | 13.07 | `analytic_note` | **да** | нет |
| остальные 5 | 07.07–28.07 | — | нет | нет |

**2 из 7 прогонов (29%) содержат разметку контракта в данных — и ни один из них не был
под атакой.** Инъекция не причина, а усилитель: она поднимает частоту, но брак есть и
на чистом входе. Оба испорченных — `analytic_note`, то есть страдает не только
`deal_progression`.

В `3d5e6e70` модель вложила в строковое поле `client_situation` текст
`</client_situation>` и `<needs>[{"claim":…`. Типовая проверка это **не поймает** —
`client_situation` строка и должна быть строкой. Нужна вторая, маркерная.

Обе строки живы и не удалялись — это готовые фикстуры для проверки логики,
синтетику придумывать не нужно.

**Чего делать НЕ надо.** Экранирование `<`/`>` во входе (`dataBlock`) — это была моя
рекомендация A3.1 в спринт-файле, и смоук её отменил: вход чистый, проблема на выходе.
Не строить.

## Правка

### 1. Вынести вызов модели в функцию

Сейчас `fetch` к Anthropic зашит в тело `processRun`. Для ретрая его надо звать дважды:

```ts
async function callClaude(
  apiKey: string,
  preset: Preset,
  userTurn: string,
): Promise<{ input: Record<string, unknown>; usage: { input_tokens?: number; output_tokens?: number } }>
```

Тело — дословно текущий блок 722–751, без изменений в параметрах запроса.
`tool_choice`, `system`, `max_tokens` не трогать.

### 2. Проверка формы

```ts
/**
 * Форма ответа модели по input_schema инструмента + маркеры разметки в строках.
 * Возвращает список претензий; пустой список = ответ годен.
 *
 * Две независимые проверки, потому что ломается двумя способами:
 *  • тип верхнего уровня (tasks строкой вместо массива — случай 28.07);
 *  • разметка контракта внутри строкового значения (</client_situation> — случай 13.07).
 */
function checkResultShape(preset: Preset, input: Record<string, unknown>): string[]
```

**Типовая проверка.** По `preset.tool.input_schema.properties`: для каждого
присутствующего в ответе ключа сверить фактический тип с объявленным
(`array` / `object` / `string` / `number` / `boolean`). Отсутствующие ключи —
не претензия: `required` держит сама модель, а частичный ответ лучше отказа.

**Маркерная проверка.** Рекурсивно обойти все строковые значения; претензия, если
строка содержит любой из маркеров:

```ts
const SHAPE_MARKERS = [
  '<parameter name=',      // синтаксис tool-use, случай 28.07
  '</',                    // закрывающий тег — контракт наружу, случай 13.07
];
```

⚠️ `</` намеренно широкий, и это осознанный риск: модель может процитировать кусок
транскрипта, где `</` встречается легитимно. Поэтому претензии делятся на два класса
(см. следующий пункт) — маркерная одна к отказу не приводит.

Фикстуры для проверки — живые строки, не синтетика: `3a75cfbb-…` (11.07, оба маркера)
и `3d5e6e70-…` (13.07, только `</`). Пять остальных прогонов обязаны пройти чисто.

### 3. Два класса претензий — ключевое решение фикса

Одинаково обрабатывать типовую и маркерную претензию **нельзя**: они по-разному
влияют на пользователя.

| Класс | Пример | Что видит пользователь сегодня | Провал обеих попыток |
|---|---|---|---|
| **Жёсткая** (тип не совпал) | `tasks` строкой | «Некорректный ответ», предложения нет | `status='error'`, `result` не пишем |
| **Мягкая** (маркер в строке) | `</client_situation>` в тексте | Текст с мусорной разметкой, но читаемый | **пишем `result`** + `meta.shape_warning` |

Логика: жёсткая претензия означает, что клиент всё равно не распарсит — записывать
нечего. Мягкая означает, что данные читаемы, просто грязные — отказать из-за неё
значит сделать **хуже, чем сейчас**, и ровно этим выстрелит ложное срабатывание
широкого маркера `</`.

```
попытка 1 → претензий нет      → пишем
           → есть любые        → попытка 2 с добавкой к userTurn
попытка 2 → претензий нет      → пишем, result.meta.retried = true
           → только мягкие     → пишем, meta.retried + meta.shape_warning = [...]
           → есть жёсткие      → status='error', result НЕ пишем
```

Добавка ко второму user-ходу — короткая и без упоминания содержимого претензий модели
(не подсказывать ей, что именно «исправить», иначе начнёт чинить данные, а не форму):

```
Предыдущий ответ не соответствовал схеме инструмента. Верни результат строго
через вызов инструмента, каждое поле — того типа, который объявлен в схеме.
Не вставляй в значения полей теги и служебную разметку.
```

**Ровно один ретрай.** Не два и не экспоненциальный: при ~25% независимых отказов один
ретрай даёт ~6% брака, второй — ~1.5%, а edge живёт под wall-clock (`STALE_RUN_MINUTES`
= 10) и каждый вызов `deal_progression` стоит ~10 с. Второй ретрай покупает 4.5 п.п.
ценой третьего таймаут-риска — не окупается.

### 4. Токены и наблюдаемость

```ts
input_tokens:  usage1.input_tokens  + (usage2?.input_tokens  ?? 0),
output_tokens: usage1.output_tokens + (usage2?.output_tokens ?? 0),
```

Иначе журнал занизит расход и метрика стоимости прогона станет врать.

`result.meta.retried = true` при успехе со второй попытки — рядом с существующим
`meta.truncated`. Это единственный способ померить частоту в проде: без флага мы узнаем
о деградации только от пользователя.

При провале обеих попыток — `status='error'`, `error` = «Модель вернула ответ в
неверном формате. Попробуйте повторить.» **`result` не писать**: сегодня мусор
записывается и клиент разбирается с ним сам; после правки мусор до БД не доходит.

### 5. Чего НЕ трогать

- `system` пресетов, `promptVersion`, модели — сравнимость журнала.
- `progressionProposalSchema` на клиенте — вторая линия остаётся как есть. Она
  отработала правильно и должна продолжать: edge может быть не задеплоен, а `result`
  старого формата уже лежит в базе.
- `dataBlock` и экранирование входа — см. выше, смоук эту гипотезу отменил.
- Миграции. Их здесь нет.

## Самопроверка перед сдачей

1. **Корректный ответ проходит без изменений?** Прогнать `deal_progression` и
   `analytic_note` на чистом транскрипте, показать, что `meta.retried` отсутствует,
   а `result` побайтово того же вида, что и до правки.
2. **Жёсткая претензия ловится?** Показать `checkResultShape` на зафиксированном
   result от 10:52 (текст в `claude/smoke-prompt-injection-2026-07-28.md`) — должен
   дать жёсткие претензии по `tasks` и по `fields`.
3. **Мягкая претензия ловится и классифицируется как мягкая?** Прогнать проверку по
   всем 7 живым строкам `ai_runs`: `3a75cfbb-…` и `3d5e6e70-…` → мягкие претензии,
   остальные 5 → чисто. Ни одной жёсткой на живых данных быть не должно.
3a. **`type` в схеме может отсутствовать или быть массивом** (`["string","null"]`).
   Показать, что такие поля пропускаются, а не считаются несовпадением.
4. **Токены суммируются?** Показать прогон с ретраем: `input_tokens` больше, чем у
   однопопыточного на том же входе.
5. **Провал обеих попыток даёт `status='error'` и пустой `result`?**
6. **Сколько стоит худший случай по времени?** Два вызова `deal_progression` ≈ 20 с
   против `STALE_RUN_MINUTES` = 10 мин — запас есть, но показать цифру, а не «нормально».
7. **`spin_review` / `meeting_protocol` / новые пресеты не сломались?** Проверка общая
   для всех шести, значит регресс возможен у любого.
