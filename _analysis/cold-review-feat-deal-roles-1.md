**Что:** пустой слот primary рисуется той же кликабельной `EmptySlotLine`, что и пустая роль, и ведёт в форму **добавления стейкхолдера**, а не в поле «Контакт» сделки — слот, по которому кликнули, после «успеха» остаётся пустым.

**Цитата:**
```diff
+            if (!slot.isFilled) {
+              return (
+                <EmptySlotLine
+                  key={key}
+                  slot={slot}
+                  canManage={canManage}
+                  onAdd={() => openAdd(slot.role)}

```

У primary `role === null`, поэтому `openAdd(null)` — это та же операция, что кнопка «Добавить» в шапке. `resolveRoleSlots` закрывает этот слот только по `projects.contact_id` (`isFilled: !!primaryContactId`), вставку в `deal_stakeholders` он не считает.

**Отказ:** сделка в воронке с ожиданиями, `contact_id IS NULL` → пунктирный слот «Основной контакт» → клик → добавить Иванова (даже с ролью ЛПР) → строка появляется в слоте роли или в «Ещё в контуре», слот «Основной контакт» по-прежнему пустой, `projects.contact_id` не меняется.

**Проверка:** открыть клиентскую сделку без контакта на воронке IIoT/ERP после apply 130; кликнуть первый пустой слот; добавить контакт; убедиться, что слот «Основной контакт» не закрылся и поле «Контакт» в сводке пустое.

## Что проверил и счёл верным

- Словарь только расширяется: `deal_stakeholders_role_chk` и `leads_decision_role_check` сохраняют `role IS NULL` и шесть старых значений, `influencer` добавлен в оба. `NOT VALID` не нужен. Zod берёт `STAKEHOLDER_ROLES`, селект лида — `STAKEHOLDER_ROLE_ORDER`: новое значение появляется у лида, у стейкхолдера и в CHECK ожиданий одним заходом. `convert_lead` (123) копирует `decision_role` как есть — зеркало CHECK'а удерживает конверсию от 23514.
- Воронка без строк `pipeline_expected_roles`: `hasExpectations: false`, виджет рисует прежний плоский список без счётчика; `missingRequiredRoles === null` → сигнал `single_threaded` по `stakeholderCount`. Delivery-воронки (`entity_type = 'project'`) в сид не попадают; internal без `pipeline_id` хук не включает. Это и есть обратная совместимость из acceptance 3.
- Слоты: primary всегда первый и закрыт при заданном `contact_id` даже без строки в карте; один человек закрывает primary и свою роль (счётчик слотов, не голов); второй с той же ролью — в `rest` по `created_at`; без роли и с неожиданной ролью не пропадают. Юнит-тесты это фиксируют.
- Пустой обязательный слот: `roleCoverageSignal` даёт `state: 'warn'`, не `bad` → вердикт не уходит в `rotting`, зона «Риски» не получает `h-rotting`. Фазовый гейт `MULTI_THREAD_PHASES` (`working` / `approval` / `closing`) на пустом слоте сохранён; на `attraction` сигнал `na`. Тесты покрывают warn / na / ok / прежнюю ветку по количеству.
- RLS: SELECT — любой член org (`org_id = (select current_org_id())`); INSERT/UPDATE/DELETE — owner/admin, UPDATE WITH CHECK повторяет USING, `current_org_*` в initplan-обёртке. Уже, чем у `deal_stakeholders` (manager там пишет участников). `anon` отозван. Настройки воронки из карточки не правятся — мутаций в хуке нет.
- Сид: дефолтная org, `entity_type = 'deal'` + `direction`, не имя; `on conflict do nothing`; повтор не падает и не плодит дубли. Миграция только файл, apply нет.
