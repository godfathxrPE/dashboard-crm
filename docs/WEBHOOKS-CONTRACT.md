# Контракт исходящих вебхуков Torii CRM

**Проект:** dashboard-crm / Torii CRM
**Назначение:** описание формата и правил доставки исходящих вебхуков для разработчиков принимающей стороны (n8n, Make, собственный сервис)
**Дата документа:** 2026-07-31
**Версия событий:** 1
**Источник правды:** `supabase/functions/webhook-dispatch/transport.ts` и `index.ts`,
миграции `088`–`091`. Значения ниже сверены с кодом; расхождения с более ранними
архитектурными набросками разрешаются в пользу кода.

---

## 1. Что это

Torii CRM отправляет уведомления о событиях в CRM на указанный вами адрес: `POST`,
тело — JSON в UTF-8, подпись — HMAC-SHA256 в заголовке.

Отправка асинхронная: событие ставится в очередь и уходит отдельным фоновым процессом.
Порядок доставки **не гарантирован** — два события, произошедшие подряд, могут прийти в
обратном порядке. Опирайтесь на `occurred_at`, а не на порядок получения.

---

## 2. Заголовки запроса

| Заголовок | Значение |
|---|---|
| `content-type` | `application/json` |
| `user-agent` | `torii-crm-webhooks/1` |
| `X-Torii-Delivery` | UUID доставки. Ключ дедупликации — см. §4 |
| `X-Torii-Event` | Имя события, например `deal.stage_changed` |
| `X-Torii-Event-Version` | `1` — версия схемы тела |
| `X-Torii-Attempt` | Номер попытки, начиная с `1` |
| `X-Torii-Signature` | Подпись, см. §3 |

## 3. Проверка подписи

Значение `X-Torii-Signature`:

```
t=<unix-секунды>,v1=<hex-hmac>
```

**Без пробела после запятой.** Схема совпадает со Stripe / HubSpot v3.

Подписывается строка `"<t>.<raw>"`, где `raw` — **сырое тело запроса побайтово**, ровно
как оно пришло. Не пересериализуйте разобранный JSON перед проверкой: порядок ключей не
гарантирован, и подпись перестанет сходиться.

```
signature = HMAC_SHA256(secret, t + "." + raw_body)  →  hex в нижнем регистре
```

Секрет вы получили один раз при создании получателя (и при каждой перегенерации).

**Node.js:**

```js
const crypto = require('node:crypto');

function verify(rawBody, header, secret, toleranceSec = 300) {
  const parts = Object.fromEntries(
    header.split(',').map((p) => p.split('=').map((s) => s.trim())),
  );
  const t = Number(parts.t);
  if (!Number.isFinite(t)) return false;
  // Защита от replay: старую подпись отвергаем.
  if (Math.abs(Date.now() / 1000 - t) > toleranceSec) return false;

  const expected = crypto
    .createHmac('sha256', secret)
    .update(`${t}.${rawBody}`)
    .digest('hex');

  const a = Buffer.from(expected, 'utf8');
  const b = Buffer.from(parts.v1 ?? '', 'utf8');
  // Сравнение постоянного времени — обычное === утекает информацию по таймингу.
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

**Python:**

```python
import hmac, hashlib, time

def verify(raw_body: bytes, header: str, secret: str, tolerance_sec: int = 300) -> bool:
    parts = dict(p.strip().split("=", 1) for p in header.split(","))
    try:
        t = int(parts["t"])
    except (KeyError, ValueError):
        return False
    if abs(time.time() - t) > tolerance_sec:
        return False

    expected = hmac.new(
        secret.encode(), f"{t}.".encode() + raw_body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, parts.get("v1", ""))
```

Три обязательных условия: считать от **сырых байт**, сравнивать **constant-time**,
проверять **возраст `t`**.

## 4. Идемпотентность

`X-Torii-Delivery` уникален для доставки и **одинаков у всех автоматических попыток**
одного события. Приёмник обязан дедуплицировать по нему: повторную доставку с уже
обработанным `X-Torii-Delivery` следует подтвердить `2xx` и ничего не делать.

То же значение продублировано в теле как `id`.

**Ручной повтор из интерфейса приходит с НОВЫМ `X-Torii-Delivery`.** Это намеренное
решение, а не дефект: повтор с прежним значением был бы неотличим от автоматического
ретрая, и корректно написанный приёмник молча его отбросил бы — оператор увидел бы
«доставлено», а на вашей стороне ничего бы не появилось.

Если вам нужно опознать именно **событие**, а не доставку, используйте совпадение
`entity.id` + `event` + `occurred_at`: при повторе эта тройка не меняется.

## 5. Ретраи

Максимум **7 попыток**. Паузы между ними:

| После попытки | Пауза до следующей |
|---|---|
| 1 | 1 минута |
| 2 | 5 минут |
| 3 | 30 минут |
| 4 | 2 часа |
| 5 | 6 часов |
| 6 | 24 часа |
| 7 | ретраев нет, доставка получает статус «не доставлено» |

Заголовок `Retry-After` в вашем ответе уважается (и число секунд, и HTTP-дата), но
ограничен сверху сутками.

Что считается успехом и провалом:

| Ответ | Результат |
|---|---|
| `2xx` | успех |
| `3xx` | **провал без ретрая** — редиректы не выполняются (`redirect: manual`): переход по `Location` был бы обходом проверок §6 |
| `408`, `429` | ретрай |
| прочие `4xx` | провал без ретрая — повтор той же ошибки бессмысленен |
| `5xx` | ретрай |
| сетевая ошибка, таймаут | ретрай |

---

## 6. Требования к приёмнику

- **Таймаут запроса — 5 секунд.** Отвечайте `2xx` сразу и обрабатывайте асинхронно;
  синхронная обработка дольше пяти секунд гарантированно даст ретрай и дубли.
- **Только `https`** и только порт `443`.
- **IP-литералы в адресе запрещены** (и IPv4, и IPv6), как и `user:pass@host`.
- **Приватные и служебные диапазоны отклоняются** на нашей стороне — включая
  loopback, RFC 1918 и link-local `169.254.0.0/16`. Проверка выполняется перед
  **каждой** отправкой, а не только при сохранении адреса: DNS может переехать позже.
- Адрес, не прошедший проверку, доставки не получает — она сразу помечается
  «отброшено» с указанием причины.
- Тело вашего ответа читается и сохраняется в журнале **обрезанным до 8 КБ**.

---

## 7. Авто-отключение получателя

Каждый неуспех увеличивает счётчик провалов подряд, любая успешная доставка обнуляет его.
По достижении порога (**по умолчанию 20**, настраивается на стороне организации) получатель
отключается автоматически, а владельцам уходит уведомление. Отключённый получатель
доставок не получает, пока его не включат.

## 8. События

| `event` | Когда отправляется |
|---|---|
| `deal.stage_changed` | Сделка перешла на стадию, указанную в правиле |
| `deal.status_changed` | Сменился статус сделки (открыта / выиграна / проиграна) |
| `deal.field_changed` | Изменилось поле сделки, указанное в правиле |
| `deal.stuck_in_stage` | Сделка провисела на стадии дольше порога правила |
| `webhook.test` | Тестовая отправка кнопкой «Тест» |

Все события, кроме `webhook.test`, порождаются правилами автоматизации с действием
«Отправить вебхук».

**`task.overdue` в этой версии не поддерживается** и не отправляется: движок просрочки
задач работает отдельно от общего механизма действий. Не закладывайтесь на него.

## 9. Схема тела

Верхний уровень:

| Поле | Тип | Описание |
|---|---|---|
| `version` | number | `1` — версия схемы |
| `id` | uuid | То же, что `X-Torii-Delivery` |
| `event` | string | Имя события из §8 |
| `occurred_at` | string | Время события в CRM, UTC, ISO-8601 с микросекундами и `Z` |
| `org_id` | uuid | Организация-отправитель |
| `rule` | object | `{ id, name }` — правило-источник. У `webhook.test` отсутствует |
| `entity` | object | `{ type: "deal", id }` |
| `data` | object | Снимок сделки, см. ниже |
| `changes` | object | Что изменилось. **Присутствует только когда дифф есть** |

Поля `data`:

| Поле | Тип | Замечания |
|---|---|---|
| `name` | string | Название сделки |
| `status` | string | `open` / `won` / `lost` |
| `budget` | number \| null | **В копейках**, целое |
| `probability` | number \| null | 0–100 |
| `direction` | string \| null | Направление |
| `deadline` | string \| null | Дата, `YYYY-MM-DD` |
| `next_action_date` | string \| null | Дата, `YYYY-MM-DD` |
| `next_step` | string \| null | Следующий шаг |
| `stage` | object \| null | `{ id, name }` |
| `owner` | object \| null | `{ id, name }` |
| `company` | object \| null | `{ id, name }` |
| `contact` | object \| null | `{ id, name }` |

Что важно знать про эту схему:

- **`budget` — в копейках**, целое число. Делите на 100 сами; «удобных рублей» не будет.
- **`occurred_at` — UTC.** Это время события в CRM, а не время отправки: у повторной
  доставки оно то же самое.
- **`data` — закрытый whitelist.** Новые поля сделки в вебхук автоматически **не**
  попадают; добавление поля — изменение контракта, о котором вас известят. Внутренние
  данные (заметки, формулировки причин проигрыша, ссылки на внешние системы) наружу
  не уходят никогда.
- **`changes` присутствует только при наличии диффа.** У `deal.stuck_in_stage` его нет
  вовсе — ключ **отсутствует**, а не равен `null`. Формат значения:
  `{ "<поле>": { "from", "to", "from_name"?, "to_name"? } }`; `*_name` появляются там,
  где поле — ссылка (стадия, владелец, компания, контакт).
- `stage`, `owner`, `company`, `contact` могут быть `null` — сделка без компании или без
  владельца допустима.

---

## 10. Версионирование

Версия схемы приходит дважды: `version` в теле и `X-Torii-Event-Version` в заголовке.

- **Добавление поля в `data` версию НЕ поднимает.** Приёмник обязан игнорировать
  незнакомые ключи — иначе он сломается на первом же расширении.
- **Удаление поля, смена его типа или смысла — новая версия.** Старая продолжит
  отправляться в течение согласованного срока.

## 12. Диагностика

В интерфейсе Torii CRM: **Настройки → Вебхуки → Журнал** у нужного получателя. Там видны
статус каждой доставки, номер попытки, код ответа, тело события и ответ вашего сервера.
Провалившуюся доставку можно отправить заново кнопкой «Повторить» — она придёт с новым
`X-Torii-Delivery` (§4).

Журнал хранится **30 дней**.
