# sdd-controller

Адаптация `subagent-driven-development` (obra/superpowers, MIT) под цикл
dashboard-crm: `sprint-S-*` → исполнение → `gate-*` → `handoff-*`.

Роль в этом скилле — **контроллер**. Контроллер не пишет код. Он нарезает
задачи, снаряжает сабагентов контекстом, судит их результат и ведёт журнал.

**Зачем сабагенты:** исполнитель получает ровно тот контекст, который вы ему
собрали, и не наследует историю сессии. Это и держит его в фокусе, и сохраняет
ваш собственный контекст под координацию.

## Когда применять

```
Есть план спринта?           нет → сначала sprint-prompt-builder
   да ↓
Задачи в основном независимы? нет → исполнять вручную, план перенарезать
   да ↓
Остаёмся в этой сессии?       нет → отдельная сессия по плану
   да ↓
sdd-controller
```

## Непрерывность исполнения

Не останавливаться между задачами ради «продолжать?». План дан — план исполняется.
Сводки прогресса между задачами тратят время Олега и ничего не добавляют:
ledger и есть запись.

**Решения, а не паузы.** Конфликт в плане, двусмысленность, дефект формулировки —
решить. Спецификация (`sprint-S-*` + `crm-architect`) — связывающая инстанция,
план — аргумент от неё, ваше суждение закрывает то, чего нет ни там, ни там.
Каждое решение — строкой в ledger:

```
Ruling: <что решено> — <почему> — <цена ошибки>
```

Неверное решение стоит переделки, которую видно и можно откатить. Сессия,
припаркованная на вопросе, стоит рабочего дня и не покупает ничего.

## Шесть стоп-условий

Останавливаться и спрашивать — только на этом:

1. Необратимая или разрушительная операция
2. Действие, затрагивающее безопасность
3. Побочный эффект вне worktree: merge, push в shared-ветку, публикация
4. План сломан настолько, что любой путь вперёд — догадка
5. **Применение миграции.** Из сессии миграции не применяются: пишется файл
   `supabase/migrations/0NN_name.sql`, применяет гейт. Прод-БД не трогаем
6. **Чтение `.env` или секретов.** Не обходить, а сообщить

Первые четыре — из оригинала, последние два — контракт проекта.

## Setup

**Изоляция.** Через `worktree-isolation`. Никогда не начинать реализацию
на `main` без явного согласия.

**Ledger.** Память сессии не переживает компакцию. Контроллеры, потерявшие
место, пере-диспатчили целые завершённые последовательности задач — самый
дорогой наблюдавшийся отказ. Прогресс ведётся в файле.

- Пространство плана: `<repo-root>/.sdd/<имя-файла-плана>/` (в `.gitignore`).
  Там всё по ЭТОМУ плану: ledger, брифы, отчёты, пакеты ревью. Чужое
  пространство не читать и не писать.
- Ledger: `<workspace>/progress.md`. Первая строка — его удостоверение:
  `# SDD ledger — план: <путь к файлу плана>`.
- Задачи со строкой `Task <N>: complete` — сделаны. Не пере-диспатчить,
  продолжать с первой без неё. Задача, чья последняя строка — раунд фикса,
  находится в цикле: продолжать со следующего раунда.
- Ledger с чужим именем плана в первой строке — чужой прогресс. Оставить
  на месте, завести свой.
- После компакции доверять ledger и `git log`, а не собственной памяти.
  Коммиты, которые ledger называет, существуют, даже если вы не помните,
  как их делали.

**Чтение плана.** Прочитать один раз, отметить контекст и глобальные
ограничения, завести todo на каждую задачу. Если план ссылается на
спецификацию — прочитать и её.

## Pre-flight scan

До диспатча Задачи 1 — один проход по плану на конфликты, с записью того,
что проверено.

Результат — **таблица, а не вердикт**:
- строка на каждую пару задач, делящих файл или интерфейс: что одна производит
  против того, что другая потребляет, и что найдено;
- строка на каждую задачу: согласуется ли её текст сам с собой — файлы, которые
  она создаёт, против файлов, которые позже трогает.

«Скан чистый» без этих строк — это не скан.

Специфика проекта, которую скан обязан проверить отдельно:
- две задачи, обе пишущие миграцию → номера конфликтуют; номер берётся
  запросом к `supabase_migrations.schema_migrations`, а не из папки
- задача меняет схему, но не обновляет `docs/schema.md` — по контракту это
  один PR
- задача трогает `src/types/supabase.gen.ts` руками — запрещено, только реген
- задача вводит `deleted_at` — в проекте soft-delete нет, только hard delete
- задача пишет `status`/`probability` из клиента — их владеют триггеры
- задача использует `window.confirm` — запрещено, только `InlineConfirm`

Таблицу — в ledger. По каждой находке — ruling до начала исполнения.

## Цикл на задачу

```
Диспатч исполнителя (references/prompts.md)
  → вопросы исполнителя? → ответить, дать контекст
  → исполнитель реализует, проверяет, коммитит, самопроверяется
  → собрать пакет ревью, диспатчить ревьюера
  → соответствие спеке ✅ и качество одобрено?
       да  → строка завершения в ledger, todo закрыт
       нет → находка противоречит тексту плана? → ruling в ledger
             раунд фикса R из 5:
               R ≤ 3 — возобновить того же исполнителя
               R ≥ 4 — свежий исполнитель на более сильной модели
             → точечное ре-ревью только по находкам
             → все закрыты? да → завершение
                            нет и R = 5 → адъюдикация каждой открытой находки
```

Автомат на R=5 — предохранитель, а не разрешение бросить. На нём каждая
открытая находка судится отдельно: несущая — решить и идти дальше,
остановиться только если любой путь вперёд догадка; ненесущая — припарковать
в ledger с ruling.

## Финальное ревью

После последней задачи — широкое ревью всей ветки на самой сильной доступной
модели. По его находкам: **один** диспатч фикса, одно точечное ре-ревью,
адъюдикация остатков. Не открывать второй круг.

Результат финального ревью ложится в `claude/gate-<sprint-id>.md` по формату
существующих гейтов. Чистое ревью → удалить пространство плана.

## Выбор модели

Самая слабая модель, которая справится с ролью.

| Роль | Модель |
|---|---|
| Механическая реализация (1–2 файла, чёткая спека) | быстрая и дешёвая |
| Интеграция, сопоставление паттернов, отладка | стандартная |
| Архитектура, проектирование, **финальное ревью ветки** | самая сильная |
| Ревью задачи | по размеру и риску дифа; точечное ре-ревью — дешёвая |

Модель у сабагента задаётся **всегда**: опущенная молча наследует самую
дорогую в сессии.

## Нарратив

Между вызовами инструментов — не более одной короткой строки. Запись несут
ledger и результаты инструментов, а не комментарии.

## Verification Labels

Гейт-отчёт спринта закрывается блоком по каждому изменению:

```
Type Safety:            [PASS | WARNING | NOT_VERIFIED]
RLS Coverage:           [PASS | WARNING | NOT_VERIFIED]
Backward Compatibility: [PASS | WARNING | NOT_VERIFIED]
Runtime Tested:         [PASS только если реально прогнано]
```

Контроллер не ставит `PASS` со слов исполнителя. `PASS` ставится по дифу
и по прогону, иначе `NOT_VERIFIED`.

## Источник и раскатка

Источник этого скилла — папка `sdd-controller/` в репозитории dashboard-crm. Копии в
`~/.claude/skills/sdd-controller/` (Claude Code) и в аккаунте Claude.ai (Cowork, гейт) —
производные: правки в них не переживают раскатку и не попадают в ревью.
Цикл: правка в репо → PR → мерж → `scripts/skill-deploy.sh sdd-controller` → загрузить
`sdd-controller.skill` в Claude.ai → Customize → Skills. Повод для правки — изменение
самого процесса (новое правило, фаза, линза), не итог спринта: состояние
проекта живёт в crm-architect, здесь его нет намеренно.
