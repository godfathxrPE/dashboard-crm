# Шаблоны промптов для сабагентов

Три роли: исполнитель, ревьюер задачи, точечное ре-ревью.
Модель указывается всегда — опущенная наследует самую дорогую в сессии.

## Исполнитель

```
Subagent (general-purpose)
  description: "Реализация Задачи N: <имя>"
  model: <выбрать по таблице в SKILL.md — обязательно>
  prompt: |
    Ты реализуешь Задачу N: <имя>.

    ## Задача
    Сначала прочитай бриф: <BRIEF_FILE> — там полный текст задачи из плана.

    ## Контекст
    <Куда это встраивается, от чего зависит, какие решения уже приняты>

    ## Контракт проекта — обязательно к прочтению
    - CLAUDE.md в корне репозитория
    - скилл crm-architect (SKILL.md + references/learnings.md)

    Жёсткое, нарушать нельзя:
    - Миграции НЕ применять. Писать файл supabase/migrations/0NN_name.sql
      и коммитить. Номер — запросом к supabase_migrations.schema_migrations.
    - src/types/supabase.gen.ts и database.ts руками не править — только реген.
    - .env и секреты не читать.
    - window.confirm / alert / prompt запрещены — InlineConfirm, toast, форма.
    - Хардкод-цветов нет — только CSS-переменные. Эмодзи в UI нет — Lucide.
    - any запрещён; для внешних payload — unknown + type guard.
    - docs/schema.md обновляется тем же изменением, что миграция.

    ## До начала
    Есть вопросы по требованиям, подходу, зависимостям или чему-то неясному
    в тексте задачи — задай их СЕЙЧАС, до начала работы. Не угадывай.

    ## Работа
    1. Реализовать ровно то, что задача специфицирует — не больше и не меньше
    2. Проверить: npx tsc --noEmit, npm run lint. npm run build НЕ гонять
       (убивает живой next dev)
    3. Если тронуты политики или функции — прогнать ролевой смок под JWT
       нужной роли, отдельными statement'ами (CTE не видит свой INSERT)
    4. Закоммитить (conventional, можно на русском)
    5. Самопроверка по дифу
    6. Отчитаться — отчётом, а не планом с распределением ответственности

    Рабочий каталог: <path>

    ## Ты не диспатчишь сабагентов
    Всю работу делаешь сам.

    ## Отчёт
    Записать в <REPORT_FILE>: что сделано, какие файлы тронуты, что проверено
    и чем, что осталось неясным, Verification Labels.
```

## Ревьюер задачи

```
Subagent (general-purpose)
  description: "Ревью Задачи N (спека + качество)"
  model: <по размеру и риску дифа>
  prompt: |
    Ты ревьюишь реализацию одной задачи: сперва соответствие требованиям,
    затем качество исполнения. Это гейт уровня задачи, не merge-ревью —
    широкое ревью ветки будет отдельно.

    ## Что просили
    Бриф задачи: <BRIEF_FILE>
    Глобальные ограничения, связывающие эту задачу: <GLOBAL_CONSTRAINTS>

    ## Что заявляет исполнитель
    Отчёт: <REPORT_FILE>

    ## Диф на ревью
    База: <BASE_SHA>   Голова: <HEAD_SHA>   Файл дифа: <DIFF_FILE>

    Прочитай файл дифа один раз — это твой обзор изменения. Контекстные
    строки дифа И ЕСТЬ изменённые файлы: не открывай их отдельно, если
    только нужный кусок не обрезан посреди функции — тогда скажи об этом
    в отчёте. Не обходи остальной кодбейс. Код вне дифа смотри только ради
    конкретного риска, который можешь назвать: один точечный чек на риск,
    и назови в отчёте и риск, и что проверил.

    Ревью — read-only. Не менять рабочее дерево, индекс, HEAD, ветки.

    ## Ты не диспатчишь сабагентов
    Второе мнение не заказываешь — все места ревью в этом процессе уже розданы.

    ## Что проверять — сверх обычного качества
    - RLS: org_id = current_org_id() первым конъюнктом; функции в
      initplan-обёртке ( select ... ); ownership через owner_id/created_by
    - Новая org-таблица: org_id not null cascade, created_by → profiles,
      RLS enabled, гранты authenticated, ручная заморозка org_id
      (trg_aa_freeze_org_id)
    - Триггеры: имя задаёт порядок исполнения (алфавитный)
    - Клиент не пишет status / probability / actual_close_date
    - Нет window.confirm / alert / prompt, нет хардкод-цветов, нет any
    - docs/schema.md обновлён вместе с миграцией
    - Номер миграции не конфликтует и взят из ledger, а не из папки

    ## Вердикт
    Два отдельных: (1) соответствие спеке — ✅ / ❌ с перечнем расхождений;
    (2) качество — approved / changes requested со списком находок.
    Каждая находка: файл, строка, что не так, чем это грозит, как чинить.
    Косметику отделять от несущего.
```

## Точечное ре-ревью

```
Subagent (general-purpose)
  description: "Ре-ревью Задачи N, раунд R"
  model: дешёвая или средняя
  prompt: |
    Раунд фикса R закрывал перечисленные ниже находки. Проверь ТОЛЬКО их.
    Новых тем не поднимать — широкое ревью будет в конце ветки.

    Находки: <список из предыдущего ревью>
    Диф фикса: <FIX_DIFF_FILE>

    По каждой находке: закрыта / не закрыта / закрыта частично — и чем именно.
```
